# 🧭 Haylen — project guide

Haylen is a reusable engine for games, multimedia apps and applications. It is 2D and organized so that 3D can grow next to it without renaming anything. Its core is C++20, and its whole API is exported to Lua through [Varn](https://github.com/varn-org/varn). Lua is the primary way to write apps, and every capability stays fully usable from C++. The repository holds the engine, its command line with the backends of every platform, the scaffolds of apps and plugins, and the sample apps.

This file is binding for every change. It describes the project as it is and the rules every feature and fix follows, so read it before working and follow it exactly instead of re-deriving conventions. When a rule or a design decision changes, update this file in the same change and describe the new state in the present tense. `PROJECT.md` holds the plan of the project: what exists, in short lines with the page of the docs that describes each, and what is missing, in full detail.

## Core principles

- No shortcuts, hacks, kludges, ad hoc workarounds, silent fallbacks, dead or obsolete code, legacy compatibility paths, backward-compatibility shims, or speculative abstractions. Fix root causes instead of masking symptoms. Implement the intended design directly, using the simplest correct, robust, and maintainable solution. Remove superseded implementations rather than preserving parallel code paths. Introduce abstractions only when justified by concrete requirements. Handle errors explicitly, never conceal failures, and never sacrifice correctness or architectural integrity for convenience.
- Nothing is ever silenced or masked. A problem is never hidden, dressed up or worked around: nothing makes a symptom disappear while its cause stays, such as a delay that waits out a race, a clamp that hides a wrong value, a visual cover over a wrong frame or a special case for one device, and nothing bypasses how a part is meant to work. Every warning, error, failed check, lint and flaky test is solved at its root, cleanly: no pragma, flag or attribute that suppresses a warning, no ignored lint, no test disabled or loosened to pass, no swallowed error and no retry that hides a failure. A test skips only where the platform or the hardware lacks the capability it checks, with a sentence that says which. The warnings of a dependency, which only that dependency can act on, are the one exception, through `haylen_disable_warnings`, and code that Haylen generates, such as the shaders of the shader compiler, compiles without warnings too.
- The engine respects the limits of every system it runs on. It never tries to get around a restriction, a permission or a policy of a platform, never guesses what the system decides on its own, and never piles up attempts to beat it. A limit is handled as what it is, through the APIs the platform offers for it: an explicit error or exception with a clear message, a documented requirement, or a documented gap.
- Replace or refactor code that no longer fits instead of carrying it forward, whatever the size of the change. There are no aliases for old names and no checks for how something used to work.
- Only change what makes sense to change. Do not add code, tests, comments or files just to show work, and do not guard against situations that cannot happen.
- Every change is finished only when it is implemented, exported to Lua, tested and documented.
- Performance matters everywhere. Hot paths avoid allocations and per-item calls across the Lua boundary, and heavy work leaves the frame thread. A frame that draws what the frame before it drew allocates nothing in the renderer, the text system or the UI, and the engine tests check it with `test::AllocationTracker`.
- The engine holds general capabilities. The mechanics of a particular game belong in apps and samples, never in the engine.
- The engine holds only what every app needs to run: windows, displays and outputs, rendering, keyboard, mouse, touch, gamepad and TV remote input, text input with the system keyboard and the clipboard, audio output with its session, video, files, storage, the network, the lifecycle, locale, theme, battery and system information, the safe area, accessibility, the mechanisms of plugins and the development tools. Every optional capability of the device or the system, such as location, camera, microphone, bluetooth, notifications, the controls of the system that show what plays, vibration, native dialogs and pickers, links and sharing, lives in a plugin, which owns its permission through the permission contract.
- This repository holds only what is general to the engine. Anything specific, such as the native plugins of system capabilities and third-party SDKs, the runner or the shader compiler, lives in a sibling repository and changes there, so nothing in this repository has to change with it and nothing here names it beyond the description of the sibling repositories.
- Plugins have no limits. A plugin can add, change or replace any capability of the engine, in 2D, in 3D, in the core, in the platform layers, in the Lua layer and in the tooling, down to any detail of any API, and that includes closed and commercial plugins that ship prebuilt binaries for each platform, such as an effects runtime, a lighting system or a library sold under its own license. So every subsystem offers its extension points through the same interfaces that its own built-in parts use, and a capability or a detail that a plugin cannot reach is a defect of the engine, fixed by refactoring whatever surrounds it, whatever the size of the change. Extensibility by plugins is a concrete requirement of every subsystem, so these extension points are never speculative abstractions. The engine keeps no compatibility with code outside it: when a better extension point needs a different API, the API changes and every plugin follows it.
- Code, comments and repository documentation are written in English. `PROJECT.md` is the exception and is written in Portuguese for the project owner.
- Never mention other engines or their tools anywhere in the repository: not in code, comments, docs, test names, commit messages or the project plan, and not even as a comparison or an inspiration. Describe what Haylen does in its own terms.
- Never mention third-party games, apps, companies, studios or artists, and never use images made by others for the samples. A sample may take the idea of something that exists, never its name, its art or its exact look, and the art of the repository is made for it. Sounds of the samples are made for the project or released into the public domain (CC0), so no credit names their authors. Fonts come from open licenses, and their license file, which the license requires, is the only third-party credit the repository keeps. The platforms, systems and stores that apps run on and ship to, such as Steam, the App Store and Google Play, are named where the engine targets them. The tools that the engine and its tooling run or integrate with, such as Xcode, Gradle, RenderDoc, PIX and Blender, are named where the engine uses them.
- The repository never records its own history. Code, comments, docs, `README.md`, `PROJECT.md` and this file describe only what exists now, simply, objectively and cleanly: no lists or notes of what was before, no before and after, no changes of an API, no earlier names or designs, no migrations and no dated change notes, anywhere. Git holds the history. The tests `NoHistoryTest` of `tools/tests/repository/test_no_history.py` fail on the wording of a rename, an earlier name or a change in any tracked file and name its file and line.
- The version of Haylen is 0.0.1 until the owner releases 1.0.0. The file `engine/VERSION` holds it, every build, SDK, library, backend and engine port of the repository takes it from there, and the `pyproject.toml` of the tooling repeats it, which a test of the repository checks. Only the current code exists: nothing keeps compatibility with an earlier Haylen, migrates from one or tells how something was before.
- This file cites a version or a number only when a rule depends on it, such as the C++ standard of the code or the coverage the tests aim for. Secondary values that change often stay out of it: the versions of libraries, tools, SDKs and of the engine itself, and the limits, sizes, counts and durations the code declares. For those it names the kind of bound a rule keeps, such as "a bounded queue", and points to the file that holds the value, such as `engine/VERSION`, `engine/cmake/haylen-dependencies.cmake`, the templates and the CI workflow.

## Working rules

- Every request of the owner goes into the checklist of `PROJECT.md` before the work starts, so nothing is lost, and an item is checked only when it is implemented, tested where possible and documented.
- The engine comes first. Its base, the core, the Lua bindings, rendering, text, the UI, input, audio, assets and content packaging, and the platform hosts, is finished, tested and verified on every platform before work on samples goes on, and samples come second. A sample never hides a flaw of the engine: the flaw is fixed in the engine first.
- Commit and push to `main` after each finished block of work, once the build, the tests and the format check pass. A block that is committed builds and passes its tests on its own, so separate unrelated changes into separate commits and verify a commit from a clean checkout when the working tree holds other work.
- Nothing opens a pull request on its own: no bot, workflow, dependency updater or agent creates one, because a pull request stays in the history of GitHub for good. Changes reach `main` as commits, and a pull request exists only when a person opens it by hand.
- CI only tests and publishes nothing, and the GitHub release of the repository is the source archive alone, because developers build the engine themselves. Every push and pull request runs the small set, the `format` job and the engine tests of the `tests` job on Linux and macOS, which answers in about 10 to 15 minutes, and every other job carries the condition that it runs only in a run started by hand, the full matrix, which runs at the end of each block of work with its failures fixed together afterwards. The full matrix is simple and fast: it builds exactly what the shipped SDKs and apps hold, every slice and architecture that the SDK and app builds make by default, tests only the common platforms, Linux, Windows, macOS on Apple silicon, iOS, Android and the web, keeps the engine tests, the GPU tests, the test project, the sanitizers of memory and threads, the fuzzers, the format and tooling tests and what proves the SDKs and a release, and runs no job that repeats what another proves. Every job and step has a short name that is a fixed string. The jobs of one run hand the engine SDKs that one of them built to the others as artifacts of the run, which nothing outside the run reads and which leave after a day, so no SDK builds twice in a run: the slices of `Haylen.xcframework` build in parallel jobs that one job joins with `haylen sdk join`. The suites that take longest, the sanitizers and the test project, run in shards that together run every test once, through `haylen test --shard` and the variable `HAYLEN_TESTS_SHARD` that the test project reads in the headless player.
- Every job of CI that builds starts from the action `.github/actions/build-environment`, which compiles every source through sccache with the compiler cache of the Cloudflare R2 bucket `haylen-ci`, under its prefix `sccache/`, through its S3 API with the secrets `HAYLEN_R2_ENDPOINT`, `HAYLEN_R2_KEY_ID` and `HAYLEN_R2_SECRET`. Every push and branch of the repository reads and writes it, and a pull request from a fork gets no secrets and compiles without it. Everything about the dependencies and the caches lives in that bucket and never in the cache of GitHub, one layer under each prefix: the objects of sccache under `sccache/`, the sources of the dependencies, the prebuilt packages of the dependencies that build with build systems of their own, such as OpenSSL, which Varn keeps in the folder that `VARN_PACKAGE_CACHE` names, and the Android dependencies that Gradle downloads under `dependencies/`, and the tools that the builds download (sccache, the shader compiler, XcodeGen, the Emscripten SDK with its ports and Gradle) under `tools/`. Each cache is an archive under a key that changes with everything it depends on, so a run compiles only what changed, downloads only what a new pin names, builds a prebuilt package only when its pins or compilers change and no cache hides a failure, while a pull request from a fork downloads and builds everything itself. One job of each of those caches saves it in the runs of the default branch with the action `.github/actions/caches` once the job succeeds with a key that the bucket lacks, while every other job reads it, and the bucket deletes every object of every prefix after 30 days and every aborted upload after a day, as `docs/tools/testing.md` describes. The built libraries and SDKs of Haylen never go into the bucket, so every run builds them from objects of the compiler cache, and every job that builds ends with the step of `.github/actions/compiler-cache`, which reports how many of its compiles came from the cache. The Debug trees of CI compile with `HAYLEN_DEBUG_INFO` set to `LINES`, which keeps only the file and line of each instruction, so the objects that the cache moves stay small.
- Haylen is free for personal and commercial work, forever, under the MIT License of `LICENSE`, and every contribution, whether code, art, sounds or any other content, becomes part of it under the same license, as `CONTRIBUTING.md` states. Nothing in the repository adds a fee, a royalty, a revenue share or a paid tier.
- A commit message is one short lowercase sentence after a type prefix, `feature: ...`, `fix: ...`, `refactor: ...`, `perf: ...`, `test: ...`, `docs: ...`, `build: ...` or `chore: ...`, for example `feature: add scene loading lifecycle`. It has no body, no co-author and no other trailer, and never names Claude or anyone else.
- Before every commit, review what is staged (`git status` and `git diff --cached --stat`) and make sure nothing private or temporary goes in: build outputs, caches, generated projects under `build/`, local tool folders, logs, screenshots, secrets, API keys, tokens, signing keys and keystores, `local.properties`, `.env` files, machine-specific paths or settings, and personal data. Anything like that belongs in `.gitignore`, never in the repository.
- Screenshots used to check a change capture only the app window or the page, never the whole screen.
- Automated checks run emulators and simulators without a window, shut them down afterwards and never send input to a device or window that a person may be using. They use only the simulators and the emulator that already exist on the machine, never create or delete one, and uninstall every app they install when the check ends.
- Features that touch rendering, input, audio, text input, windows or platform code are run on the platforms they affect (desktop player, iOS and tvOS simulators, Mac Catalyst, Android emulator, browser), and a sample shows each of them working.
- A change to rendering, textures, shaders, the UI or text is compared before and after on the test categories it affects, in captures that are looked at closely, and a visual change that nobody asked for is a regression fixed before the change lands. Every visual defect that anyone sees, such as blur, smear, distortion, aliasing, seams or wrong colors, is fixed at its root at once.
- Simulators, emulators and the browser carry the checks. A physical device runs only what they cannot show, such as hardware they lack or limit, real performance, signing and store delivery, and it never repeats a check that already passed on a simulator or an emulator.
- Every check is automatic, here or in the cloud. The checks of a device, its prompts, notifications, home screen, recent apps, back button, remote and sensors included, run as UI tests on the devices of this machine and of AWS Device Farm, and no check asks a person to tap anything. The posture of the foldable iPhone, which no API of the system drives, is the one check that stays out of routine runs.

## What the engine is

- **Library first.** The folder `engine/` is a standalone CMake project that other projects consume with `add_subdirectory`, CPM or `find_package(haylen)`. It exports the `haylen::engine` library of the core, the `haylen::runtime` host library, the `haylen::lua` library of the Lua layer, the `haylen::player` object of the Lua player, which defines the app of a Lua app, the `haylen::native` headers of the native API with nlohmann/json for native libraries, and the `haylen_add_app(<target> LUA|CPP [WITH_LUA] [SOURCES ...] CONTENT <folder> [BOOTSTRAP <file>] [WEB_SHELL <file>])` CMake function. A Lua app links the player and a C++ app defines `core::Application::create` in its sources, so every app holds exactly one, and a C++ app links the Lua layer only with `WITH_LUA`, which the `cpp.lua` of `haylen.json` asks for. The function places the content that the tooling prepares, the staged package or the protected release with its bootstrap, and never builds a release itself, and Xcode builds the apps of Apple platforms, so it builds only plain executables of CMake projects on macOS.
- **The core and the Lua layer.** The engine stands in two layers with a boundary in the repository. The core, `engine/include/haylen/` and `engine/src/` with the contexts, the platform, the GPU devices, the plugins of the engine and the general development tools, is plain C++ in the target `haylen-engine`: it includes no header of Lua, names no `lua_State`, no namespace `lua` and nothing of the Lua of Varn, and links only the scheduler of Varn. The Lua layer in `engine/lua/` is the target `haylen-lua` (`haylen::lua`), which links the core and the Lua runtime of Varn and reaches the core only through its public C++ API, so it proves that every capability is usable from C++: the public toolkit of bindings in `engine/lua/include/haylen/lua/`, the binding of every context in `engine/lua/src/<context>/`, the Lua modules in `engine/lua/src/modules/`, the runtime of the scripts of an app in `engine/lua/src/runtime/`, the Lua debugger and the execution budget in `engine/lua/src/debug/`, the module reload in `engine/lua/src/development/` and the Lua player in `engine/lua/src/player/`. `core::Engine` runs an app without knowing of Lua: the Lua player makes a `lua::Application`, which adds the `lua::ScriptPlugin` and the development tools of Lua, and a C++ app makes its own `core::Application` and links the Lua layer only when the `cpp.lua` of its `haylen.json` is `true`, so a C++ app without Lua holds no Lua, no Lua module of Varn, no module reload and no Lua debugger, and its package holds no Lua modules. The headless player of the core, `haylen::headless-player`, plays a package with the application that `core::Application::create` of its program makes, the Lua player in `haylen-headless` and the application of a C++ app in the program of the consumer project, which `haylen engine consumers` builds, checks for symbols of Lua and runs on the headless host. The tests `LuaLayerTest` of `tools/tests/repository/test_lua_layer.py` fail on a file of the core that includes or names Lua, a file of `engine/src/` named `Scripted*`, `Lua*` or `*Lua.*`, a file of the Lua layer that includes a header of `engine/src/` and an interface of `haylen-engine` that links a Lua target of Varn, and name each one.
- **Layered architecture.** The engine stands on three layers. The platform layer opens the window, runs the frames, reads the input and holds the entry points: the layer of SDL3 in `engine/src/platform/sdl/` on macOS, Windows, Linux, iOS, iPadOS, Mac Catalyst, tvOS, visionOS and the web, the worker layer of `engine/src/platform/worker/` in the Worker mode of the web, where the module runs in a dedicated worker, and the native runtime of `engine/src/platform/android/` on Android. Each one implements a host derived from `platform::NativeHost`, which adds what its window does to the services of the platform, and a `platform::NativeWindow`, which hands the services the native handles of its window, and it calls `platform::Player` as the window opens, draws its frames, receives its events and closes. The render hardware interface is `gpu::Device` of `engine/include/haylen/gpu/Device.hpp`, with one device per graphics API in `engine/src/gpu/<api>/` that `gpu::DeviceFactory` makes, and the platform layer opens its window for the first API of the order of the app that starts on the machine, so a build carries every device of its platform and chooses at run time. A device that is lost gets one replacement through `platform::DeviceRecovery`, and a replacement that is lost too ends the app with the reason, as `docs/graphics/rhi.md` describes. The renderers draw through that interface alone, through `graphics::Device`, which owns the device and makes textures, render targets and readbacks for them: `graphics2d::Renderer` in `engine/src/2d/graphics/` today, and a 3D renderer next to it in its own `3d` folder. The player, the services of each platform folder, the engine and the Lua API stay the same on every platform and graphics API. The file `docs/graphics/rhi.md` describes the contract, the capabilities of each API and the status of every device on every platform.
- **Ports.** The engine implements only what is general, so a platform whose SDK comes under a license that keeps its code private, such as a game console, plugs in without a rewrite of the engine, through three layers. The engine of this repository holds the general mechanisms. The port of the console, in a private repository, brings the runtime, the window, the GPU device, the audio output, the files and the packaging of that console. The plugin of the console, in a private repository too, brings its users and sign-in, achievements, store, saves of each user, storage quota, controller setup and button glyphs through the plugin contract that every plugin follows, with its C++ and Lua APIs. This repository only documents the private layers and never names a console. A port joins the CMake build as a folder outside the repository that the cache path `HAYLEN_PORT_DIR` names, whose `port.cmake` describes it with `haylen_port`: the version of the contract of ports that it follows, which must be `HAYLEN_PORT_CONTRACT_VERSION` of `engine/cmake/haylen-port.cmake`, its capabilities, the function that builds its apps for `haylen_add_app`, the content profile of its releases, the host tools that run on the build machine, the part of plugins that its backend reads and whether it installs the SDK. It brings the runtime, window and services of its platform and, for a graphics API the engine has no device of, the device of the reserved API `gpu::Device::Api::Port` with the reserved shader language `Language::Port`, whose code its shader command writes into the `port` target of each shader package. A port reaches the engine only through the public, versioned API of `engine/include/haylen/port/` in the namespace `haylen::port` and the other public headers, never through `engine/src`, and `port::Contract::kVersion`, which `CONTRACT` of `haylen_port` must match, grows with every change that a port must follow. Every platform runtime, of the engine or of a port, installs the services of its platform by capability once as a `port::Services`, the platform and its displays always and every other service only where the platform has that capability, and `platform::Services` answers in one place for each capability that a platform lacks, so no platform keeps an empty implementation that reads as success. The sound of a platform whose output the audio library of the engine does not know, such as the page of a browser or a console, goes through the service `port::AudioOutput`, whose playback reads the mix of the engine, and the mixer of a port without it keeps time without sound. A platform that halts apps in the background unless they declare that they play audio there registers `port::BackgroundAudioService`, which reads that declaration and runs the frames of an app that plays there, and the engine treats a platform without it as one that keeps every app playing in the background. A port builds the target `port` of Varn with the drivers that its `VARN_DRIVERS` names and external drivers whose sources it brings in `VARN_DRIVER_SOURCES`, and its frames pump the event loop of Varn, whose worker pools run on threads of their own unless `THREADS` is off. A console needs three layers: the engine, which holds only what is general, a private repository with the port of the console, and a private repository with the console plugin, as `docs/platform/ports.md` describes. It joins the tooling as an installed Python package with its engine port and its backend, as **Backends and engine ports** describes. The repository holds only the mechanism, the test port of `engine/tests/data/port`, which `haylen test --port` builds and plays on a desktop, the proof of an external port in `tools/tests/extensions`, which installs that port as a Python package with the backend of `tools/tests/data/test-port-backend` from outside the repository and builds, verifies and runs an app with them, and `docs/platform/ports.md`, and never holds code or facts that an SDK license covers.
- **Lua through Varn.** The core links `varn-runtime`, the scheduler, log, data views, HTTP client and TLS of Varn without Lua, and the Lua layer links `varn-core`, the Lua runtime of Varn and its modules on top of it. Varn stays an implementation detail: no line of the log names Varn, the log of the platform is named `haylen` through `varn::log::Log::setName`, and every record is its time, its level and its message. The `core::JobSystem` of the core owns the one `varn::runtime::Scheduler` with the event loop and the worker pools, and the `lua::ScriptPlugin` of the Lua layer makes on it the one `varn::runtime::Runtime` that owns the Lua state. The `lua::Module` of each Lua module of the engine installs it into that state through `lua::Binding::preload`, which puts it in `package.preload` next to Varn's own modules (`async`, `http`, `socket`, `json`, `fs`, `zip`, `crypto`, `log`, `platform`, `process`, `datetime`, `xml`, `dataview`, `ffi`). Memory that the app and native code share without a copy is the data view of Varn, and the engine reuses it instead of a pointer type of its own: `varn::dataview::DataView` in the `views` of `platform::Bridge::Payload`, `varn_dataview` in `HaylenNativeApi`, `VarnDataView` on Apple platforms, Android and the web, and the `dataview` module in Lua, so the headers of Varn's data view, `varn/varn.h` and the JavaScript class of `src/wasm/varn-dataview.js` reach apps through the SDKs. The JSON names a view with Varn's token, every boundary of the bridge takes its own reference before it returns, and the views of a call belong to it until its handler answers.
- **Everything in C++ is exported to Lua.** Every public C++ capability has a Lua binding in the same change, in the folder of its context in `engine/lua/src/<context>/`, with Lua tests in `engine/lua/tests/<context>/` and a reference page under `docs/lua-api/`. This is a rule, not a goal. The one exception is the bootstrap of protected releases in `haylen/content/` (`Bootstrap`, `KeyProvider` and `EmbeddedKeyProvider`), which handles content keys, and keys never reach Lua.
- **App packages.** The runtime runs an app package, which is either a folder or a `.zip` file containing `haylen.json`, the Lua modules under `source/` and the assets under `content/`. Nothing else in the folder belongs to the package, so the native code that `haylen.json` names, notes and other files can sit next to it. The file `haylen.json` configures the identity, window, design resolution, orientation, splash screen, lifecycle, audio session, debug options, content delivery and updates and native libraries before any Lua runs, and the application names the sections that it reads itself, which `core::AppConfig::sections` keeps for it, such as the `lua` section of the autoloads, the reload mode and the execution budget, which `lua::Config` of the Lua layer reads, so the core never knows a Lua key. Unknown keys and invalid values are errors with clear messages. The same file holds the keys that only the tooling reads, `category`, `kind`, `cpp`, `plugins` and `platforms`, and `tools/haylen/schemas/haylen.schema.json` describes every key. The `category` that every app names, such as `game` or `utility`, has no default, and each backend maps it to the category of its platform, as `docs/tools/distribution.md` lists. Its `version` is the version that people see, and its `build`, a whole number that grows with every upload and is 1 when it is missing, is the one source of every build number: `CFBundleVersion` on Apple platforms, `versionCode` on Android, the last number of the Windows version resource and the app build of protected releases and their content updates, so nothing derives a build number from the version. The file `source/main.lua` is the entry point. Every package reads its files in ranges through `io::PackageReader`, so files of any size stream in bounded memory, and a whole read refuses a file larger than `Package::kMaxReadSize`, as a range read refuses a longer range. A zip package stays on disk and reads each entry when it is asked for. The command `haylen new` gives an app its `.gitignore`, `.editorconfig` and `.clang-format`, which are not part of the package, and the sources of a C++ app, which `cpp.sources` names, are not part of it either.
- **Asset paths.** Every asset path passed to the engine is relative to the package `content/` folder and never includes the `content/` prefix. The function `require("scenes.menu")` resolves Lua modules from the `source/` folder, so it loads `source/scenes/menu.lua`.
- **Engine SDKs.** App builds never compile the engine, which only the engine ports compile into SDKs. The command `haylen sdk build --target <target>` asks the engine port that serves the target to compile the engine and install its SDK into `build/sdk/<port>-<configuration>/`, or into the folder that `--output` names, which the variable `HAYLEN_SDK_PATH` then lists. The manifest `haylen-sdk.json` of an SDK records its port, the version of the engine, the revision of its sources, its configuration, the host tools that run on the build machine, such as the content tool `haylen-content`, and each slice with its system, environment, architectures, binary interface, toolchain, C++ runtime, oldest system version, graphics APIs and capabilities. A port keeps the slices of its folder built from the same revision and configuration, so a slice built later joins them. Every SDK keeps the Lua layer in a library of its own, which only the apps that run Lua link, and `haylen-sdk.json` lists the libraries of each slice. The Apple SDK holds `Haylen.xcframework` with the engine and the runtime and `HaylenLua.xcframework` with the Lua layer and the Lua player, signed ad hoc, with `haylen-frameworks.json`, the engine's `PrivacyInfo.xcprivacy` and its Swift helpers `HaylenBridgeAsync.swift`. The Android SDK holds the `haylen` AAR with the `haylen-plugins`, `haylen-links` and `haylen-coroutines` libraries in a local Maven repository and the CMake package of each ABI. The web SDK holds the web player, which draws through WebGPU or WebGL2, and its Emscripten CMake package, and the desktop SDK holds the desktop player, the content tool and the CMake package of this machine. The app commands that build, `app prepare`, `app build`, `app run` and `app package`, first build through the engine port, as a step of their own that says so and how long a first build takes, the architectures of the target that no installed SDK of the current engine sources holds in the configuration of the engine, as `haylen sdk build` does, while `project inspect` and `app verify` never build and stop with the `sdk build` command to run. An app build then picks the slice of every architecture after it resolves the plugins and before it generates the project, and a slice that runs only on newer systems than the app or lacks a graphics API that it asks for stops it with the reason, so Lua and C++ apps link the prebuilt SDK alike.
- **Generated platform projects.** The native project of an app for a target is generated, disposable and deterministic. The command `haylen app prepare`, which every build runs first, writes it into `project/` of the folder of the product under `build/apps/<app>-<hash>/`, next to the trees of the native tools in `build/`, the built products in `products/` and the staged package in `package/`. It records in `haylen-preparation.json` the version of the tooling, the backend and its version, the digest of its template, the SDK and the digest of every input, so a preparation whose inputs did not change writes nothing, and a deleted project comes back the same. Nobody edits a generated project. What a developer customizes lives in the repository of the app: the sections of `platforms` in `haylen.json` that the backends declare, such as `apple` with its `sources`, `team`, `buildSettings` and `privacy`, `ios` and the other Apple platforms with `infoPlist` and `entitlements`, `android` with its `sources`, `applicationClass` and `manifest`, and `web` with its `scripts`, each also with `minimumSystemVersion` and `files`, which maps paths of the generated project to files of the app that replace the files of the template. Values merge with one precedence: the app defines its identity and the overrides that its sections allow, plugins declare what they need, the SDK and the engine port declare constraints that no override cancels, and the backend translates the result into the project of its platform. A value with one owner, such as the identity, the version, the application ID or the oldest system version, is validated, and a plugin that needs a newer system version than the app sets fails the resolution instead of moving the audience of the app. Contributions that accumulate, such as frameworks, dependencies, permissions and the keys of property lists, merge by their identity or fail with both owners, never by the order the files were read. The command `haylen project inspect` shows every resolved value with its origin and the reason for it, and every error of a preparation names the manifest or the plugin it comes from.
- **Content tool and keys.** The tool `haylen-content`, which `engine/tools/content/` builds from the format library of the engine and its writing side `haylen-content-writer`, which apps never link, builds, verifies, inspects, compares and publishes protected releases, writes the bootstrap that a release build compiles in, and the commands of `haylen content` and every Release build of an app run it from the desktop SDK of this machine. A release build of an app compiles its own bootstrap, with the identity of the app, its public signing key and its content keys sealed so the binary never holds a key in plain form, and the runtime opens the release that ships with the app with it, so no key is shared between apps and no key sits in a resource, a manifest or `haylen.json`. The keys of each app live in its key folder under the configuration folder of the user, or under the folder that `HAYLEN_KEYS_DIR` names in continuous integration, which never creates keys, and never in a repository, a project or a build folder. No tool prints a key, only key IDs and public keys.
- **Release builds.** The Release configuration of `haylen app build`, `app run` and `app package` ships the package of an app only as its protected release, with the Lua modules as bytecode, and a binary of the app that compiles in its bootstrap `HaylenBootstrap.cpp`, which the content tool writes: the executable of the generated Windows or Linux project, linked against the desktop SDK, the app of the generated Apple project, on Android the library of the app, `haylen-app`, linked against the SDK of each ABI, which the activity loads instead of the Lua player, with a release too large for the base module of Google Play in install-time asset packs of the generated project, and on the web a runtime of the app, whose page downloads only the manifests and the app domain and streams the content by range into the content store of the browser. The release binaries that the backends link ship without symbols, which stay in symbol files of the build folder for crash reports, and Release builds of the engine and its SDK compile with link-time optimization, so the link of each app optimizes it as one program, except the SDK of Windows, whose one library would outgrow what a library of Windows holds. Lua and C++ apps ship the same release with the same bootstrap, which `haylen_add_app` receives in `CONTENT` and `BOOTSTRAP` where CMake builds the app, and `haylen app package --format steam` lays a Windows or Linux release out as Steam depots. The verification of a Release build, which `app build`, `app run`, `app package` and `app verify` run, fails when the app holds Lua text, a file of the package as it is, symbol files or a key in any form, as the release builds of the `web`, `android`, `apple` and apps jobs of CI check. The Debug configuration ships the package as it is.
- **Debug and Release declare the same.** A Debug and a Release build of an app declare and integrate exactly the same: the permissions, the keys of the `Info.plist`, the entitlements, the privacy entries, the entries of the Android manifest, the network security configuration and its cleartext traffic, the permissions of the browser, the plugins and the capabilities. They differ only in what development itself is: optimization, symbols, the development session with hot reload, the debugger, the console and the execution budget, and the protected release format of the content with the bootstrap that opens it. The development session reaches the app without adding or removing any declaration of the app, so the page of a web run reads where the development server is from the `config.json` that the site server answers, never from a file of the site. The tests `ConfigurationDeclarationsTest` of `tools/tests/platforms/test_configuration_declarations.py` prepare one app with a plugin in both configurations on every backend and compare what the projects declare.
- **The command haylen.** The command line is the Python package `tools/haylen`, which the launchers `haylen` and `haylen.cmd` run through uv, and its commands name what they do with the words that app developers know: `new`, `doctor` and `devices`, the groups `app` (`prepare`, `build`, `verify`, `run`, `package`, `sign`, `zip`, `shaders`, `serve` and `capture`), `plugin` (`add`, `update`, `remove`, `list` and `new`), `project` (`inspect`), `sdk` (`build`, `join` and `list`) and `content` (`build`, `verify`, `inspect`, `diff`, `publish`, `compact` and `keys`), the command `serve` of a folder, and for the engine itself `test` and the group `engine` (`configure`, `build`, `bench`, `fuzz`, `coverage`, `format`, `clean`, `tools` and `consumers`). The page `docs/tools/commands.md` describes every command with its options and its result. Every command prints its steps, or with `--json` one JSON document with its result or its typed error. A capability that only some targets have, such as a package for a store or a signing key, is a format or an option of `app package` or `app sign` that the backend of the target declares, never a command of its own, so a new platform adds no command. One pipeline serves Lua and C++ apps on every target: the manifest, the target and its capabilities, the plugins of the target, the SDK, the resolved project, then the preparation, the build, the verification and the launch, and the kind of the app changes only what compiles and what loads. The command `devices` lists the identifiers that `--device` takes, and every error about a device points to it.
- **Backends and engine ports.** The core of the tooling never imports a concrete backend. A `PlatformBackend` generates, builds and verifies the apps of its targets and, where it declares the capability, lists devices and runs, packages and signs apps, and an `EnginePort` compiles the engine for its targets into an SDK. They are separate contracts, which register through the entry point groups `haylen.backends` and `haylen.engine_ports` of an installed Python package, the ones of the repository like any other, each with the version of its contract, which the registry checks. A backend target and a port target serve one target when their system, environment, architectures with their binary interfaces, toolchain and capabilities match, never by their names. Each compilation has one owner on each platform: Xcode on Apple platforms, Gradle with its CMake external build on Android, CMake on the desktops, and Emscripten with CMake on the web. The backends of the repository live in `tools/haylen/platforms/<name>/` with the templates of their generated projects, and a new platform is a backend and an engine port, in the repository or installed from outside it, without a change to the core or the command line.
- **The player.** The desktop player `haylen` of the SDK, run as `haylen --dev <folder|zip>`, runs any app package on desktop with hot reload, which reloads changed Lua modules in place with the state of the app and restarts the app only when a change cannot apply in place. Only `--dev` turns on development behavior, watching the package folder, or `--dev-server`, which connects to the development server that pushes saved files instead, and on the web the page field `Module.haylen.development`, which the web backend sets only for the page that a Debug run of `haylen app run --target web` serves, so built apps, shipped apps and the sites of other builds never run in development mode. An app that another app launches with the address of a development server in the option `developmentServer` of `haylen.launch` plays in development with a session of its own, while the app that launched it keeps its own session, or none, for its return, such as an app that downloads the package that `haylen app serve` serves on the local network with its development server. A launched app always leaves through the hold of `platform::ReturnHold`, Escape, play and pause of a TV remote, the back button of Android or of a gamepad, or three still fingers held for a moment, which the app hears as plain input and cannot take, and the release that ends the hold never reaches the app that starts again. The links that open the process belong to the app that the process installed, so a link that arrives while a launched app plays ends every launched app, and the first app hears it as `linkOpened` once it starts again, which on the web is a link that the page or the web module of a plugin hands over with `openLink`, since the page is the link that opened it. A launch with `nativeAccess` set to `false` plays the app and every app it launches without the `ffi`, `process` and `haylen.native` modules and the functions `io.popen` and `os.execute`, so an app that comes from an address reaches the system only through the engine and the plugins of the process. Every argument after `--` of the command line, the extra `dev.haylen.arguments` of the Android launch intent and each `argument` of the address of a web page reach the first app of the process as `haylen.launchArguments`. The command `haylen app run` hands `--dev-server` to the player of this machine and, in the Debug configuration, to apps on simulators, devices and the Android emulator as a launch argument, or an intent extra that only a debuggable Android app reads, with an address that needs no permission of the app: the loopback address of simulators and of the port that `adb reverse` forwards, and the address of the Mac on the CoreDevice tunnel of an Apple device, which `devicectl` reports and which is no broadcast-capable network, so no local network permission or usage description of the app is involved, and an app with a release bootstrap ignores it. Development lives in the `platform::DevelopmentSession` of the host, which outlives every app that restarts under it, and nothing of hot reload, of the Lua debugger or of the execution budget, such as the module graph that replaces `require` and the hooks of Lua, exists without it. The core keeps the session, its connection, the reload of assets and the restarts, and the Lua layer gives the session its `DevelopmentSession::Extension`, the `lua::Development` with the debugger and the execution budget, which the first app that runs Lua in the session makes. The execution budget, `lua::debug::ExecutionBudget`, is the `core::Engine::EntryObserver` of every engine of a Lua app and times every call of the host into the engine with the `lua.executionBudget` of `haylen.json` and bounds the Lua memory with `lua.memoryBudget`, and once either runs out it cancels the app through `core::Engine::cancel`, so every later instruction of the app raises the error again, no `pcall` or coroutine keeps it and only a restart runs the app again, while its count hook and the hooks of the debugger share each coroutine and `debug.sethook` is refused in development.
- **The debugger.** The Lua debugger of `engine/lua/src/debug/` belongs to the development session, so its breakpoints outlive reloads and restarts of the app. Editors attach to it with the Debug Adapter Protocol on a port of `haylen app run`, `--debugger-port`, and the development server carries its messages to the app through the development connection, on every platform. It offers breakpoints with conditions, counts of hits and log messages, pauses, steps that follow a coroutine across the `await` of the async library, halts on errors that no protected call of the app catches before their stack unwinds, the stack with its scopes and values, and evaluations. Coroutines have no hook while nothing is watched, and watched ones report lines only in the functions whose lines hold a breakpoint or while a step needs them. Looking at values reads them raw and holds the collector, so it never runs code of the app, and the only code the debugger runs is what the person writes, evaluations, conditions and log messages, on a coroutine of its own with a time bound. A web page cannot halt, so it keeps only the log points.
- **The developer tools.** In development, the terminal of `haylen app run` reaches every running app on every platform: its keys reload, restart, open the developer console, show the statistics, the inspector and the debug drawings of the app and capture a frame of its GPU, and the console is a line at the bottom of the terminal, completed from the commands that the app sends, which the log of the app never mixes with. The app draws the statistics window and the inspector as windows of `debug::DebugWindow`, which have one dark and translucent look of their own in the default font of the engine that no theme of the app changes, stay inside the safe area, move by their title bar and scroll under a finger, and it has no console window of its own.
- **Plugins.** Every subsystem is a plugin: a self-contained unit with a name and a uniform lifecycle (`start`, `event`, `beginFrame`, `fixedUpdate`, `update`, `render`, `renderUi`, `renderOverlay`, `endFrame`, `packageChanged`, `stop`, `isCapturingBack` for the back button, `isFrameComplete` for the first frame that shows the app and `isAnimating` for what a plugin moves by itself in an app that redraws on change), which knows nothing of Lua. The Lua modules of a plugin are a `lua::Module` (`getName` and `install`) of its own, which `lua::modules::BuiltInModules` registers in dependency order and the `lua::ScriptPlugin` installs once the plugins of the engine started, and projects add theirs with `ScriptPlugin::addModule`. The engine registers its plugins and then lets the `core::Application` add the plugins of the app with `addPlugins`, as `lua::Application` adds the script plugin and the development tools of Lua. Built-in subsystems use exactly the same plugin and module interfaces that other projects use to extend the engine, every subsystem offers its extension points to plugins through the interfaces its built-in parts use, as the core principles require, and plugins never reach into each other's internals.
- **Native access.** Apps reach anything native through native plugins, which package a Lua API with its Swift or Objective-C, Kotlin or Java, JavaScript and C or C++ implementations and their SDK dependencies. Underneath, plugins talk through the asynchronous platform bridge, whose JSON calls native handlers answer with typed errors, timeouts and cancellation. Apps can also call native libraries from Lua through `haylen.native` and Varn's `ffi` (for example the flat C APIs of game platform and online services SDKs), and apps that compile the engine add C++ engine plugins. Answers and native callbacks always reach Lua on the frame thread. The engine library never bundles or calls a third-party SDK itself, because SDKs such as those of ads or analytics live in native plugins.
- **Every kind of desktop app.** Besides normal windows, the engine supports frameless, transparent, always-on-top and click-through windows that apps move themselves, for apps that live on the desktop or above the taskbar, and every mode can change while the app runs. macOS apps are regular apps with the standard main menu, and every request to quit, from the menu, Command+Q, the Dock or the system, closes the window through the engine as its close button does.
- **Errors never stop the runtime.** An error in app code shows the error screen with the message, the file and line, the source around it and the Lua stack, which the user can scroll, copy and restart from. The web page receives the same error, and hot reload restarts the app from the error screen.
- **Sibling repositories.** Three repositories of https://github.com/haylen-org sit next to this one and follow the same rules, each with its own `README.md` in the pattern of this one and its own `AGENTS.md`: `haylen-shader-compiler`, the Haylen shader compiler that the engine pins, `haylen-runner`, Haylen Runner, a Lua app of Haylen that runs other Haylen apps from an address, a QR code or a link, which anyone builds and installs on their own devices, and `haylen-plugins` (https://github.com/haylen-org/haylen-plugins), the native plugins of system capabilities and third-party SDKs, one folder each, which apps take with `git` and `path`. The runner and the plugins each keep exactly one commit on `main`, which every change amends and force-pushes, with no tag and no release. They use only the documented Lua API, the plugin architecture and the general capabilities of the engine, so a flaw they show is fixed in the engine, and nothing else of this repository names them.
- **Web editor ready.** A website edits Lua code, JSON and assets in the browser and runs the app with the precompiled WebAssembly runtime (WebGPU or WebGL2). The web runtime therefore offers the versioned editor contract of `Module.haylen.editor`, whose requests each answer a promise once they completed: atomic batches of writes, removes and renames that make numbered revisions of the package that plays under an overlay, changes applied by hot reload in development with the revision and the rejected files in the answer, runs without reloading the page, pause, stop, the console, a read-only inspection and a dispose that closes the player, its graphics device, its audio contexts and its storage. It forwards logs, statistics and error records with a stable `code`, a `phase`, the project-relative file and line and the Lua stack to JavaScript, keeps the user data of each `storageNamespace` in a database of its own, which one tab of the site holds at a time through the lock of the Web Locks API, so a second tab gets an error from its storage and `hello` reports it, and shows the error screen instead of stopping when a script fails. A page that names `Module.haylen.hosting = "worker"` loads the page side of the runtime, `haylen-page.js`, alone, which starts the module in a dedicated worker through `haylen-worker.js` with the canvas as an `OffscreenCanvas`: the page keeps everything of the document and posts the worker the input, the state of the page and the requests of the editor, the worker posts the calls of the engine into the page and a heartbeat, and the editor ends a worker that stopped answering with `Module.haylen.editor.terminate()`. The engine side of `haylen-runtime.js` and the page side are the same scripts in both modes. Every native function bounds the work and the memory that a number of a script or an asset asks for, so the execution budget of development stops whatever runs too long. The website itself lives in another repository.

## Platforms

- The engine runs on macOS, Windows, Linux, iOS and iPadOS, Mac Catalyst, tvOS, visionOS, Android (phones, tablets and Android TV from one APK) and the web (WebGPU with WebGL2 as the alternative where WebGPU does not start). Scripts see Mac Catalyst and visionOS apps as iOS apps, and watchOS is not possible because its SDK lacks the graphics, input and audio frameworks the engine needs. The file `docs/tools/distribution.md` records the support table and the minimum versions.
- Minimum operating system versions are as low as the toolchain and the dependencies allow, and each limit is explained in `docs/tools/distribution.md`.
- Every feature works on every platform, or the docs say exactly where it does not and why. Input covers mouse, touch, keyboard, gamepads with their motion sensors and touchpads, whose sensors stay off until a request of the app wants them and stop while the app is in the background, and TV remotes, and text input uses the native text field of each platform so input methods, composition and on-screen keyboards work everywhere.
- The text input of the system is on only while a field edits or the plain keyboard of `window.setKeyboardVisible` is open, so keys pressed in play never open the accent menu of macOS or a composition window, and only one text input of a platform reads each key: the native field on macOS, iOS, Android and the web, where the runtime never starts the text input of SDL, and the text input of SDL on Windows and Linux. Every host shares that one input through `platform::SharedTextInput`: a field that edits holds it until it finishes, and the plain keyboard that the app asks for shows only while no field holds it, so neither closes the keyboard of the other.
- The native text field that edits a field of the UI stays hidden on every platform, never transparent, so the system draws none of its caret, selection, autocorrection bubbles or predictions, and it never predicts, completes or rewrites text, which the user would not see. Autocorrection is off unless a field asks for it with `autocorrect`, and then only the on-screen keyboard offers it. A finger edits a field only once it taps it, a field that the accept of a keyboard, a gamepad or a remote opens reaches the platform once the press ends, so the release never types into the keyboard of the system, such as on the Apple TV, a drag that starts on a field scrolls the area around it, a finger ends the editing only with a tap outside the field, since the UI backend holds a finger that presses outside the field being edited from ImGui until it lifts within the slop of `ScrollArbiter`, as a tap that ends the editing and presses what it tapped, or travels past it and scrolls the area under it while the field keeps editing, and the GUIs hold their place under the keyboard while a press is down, so a press that closes the keyboard lands on what it pressed.
- The languages the person prefers come from the API of each platform, `NSLocale.preferredLanguages` on Apple platforms, the locales of the configuration on Android, `navigator.languages` on the web, `GetUserPreferredUILanguages` on Windows and the variables of gettext on Linux, and reach `platform::System` through `SystemState`, which keeps every tag once in the canonical form of BCP 47 that `localization::LanguageTag` writes, such as `pt-BR` for `pt_br`. The engine publishes `systemLanguagesChanged` when the list changes while the app runs, the current language of `localization::Catalog` follows the list until the app picks one, in the order of matching of `docs/core/localization.md`, and `languageChanged` tells of every change of it. The section `localization` of `haylen.json` loads the folder of the languages before any Lua runs.
- Displays are known by ids that stay the same while a display stays connected, never by their place in the list, and `platform::Displays` publishes each display that connects, disconnects or changes. The app runs in one window with one engine and one Lua state, and it shows more on other displays through outputs of `platform::Outputs`: each one a render target that the app draws into and that the engine presents into another swapchain of the same `gpu::Device` at the end of the frame, on the frame thread. Every GPU device draws into several surfaces, OpenGL and OpenGL ES through other drawables of the one context of the window, so one set of objects serves every output. From iOS 27, UIKit connects the scene of an external display only for an app that registers the scene accessory of external displays, which the engine does at every start of an app whose `window.externalDisplays` of `haylen.json` is `true`, while the display mirrors any other app, and a browser lists every screen only once the person allows it through `display.requestEveryScreen` and opens the window of an output only shortly after a gesture of the person. The file `docs/platform/displays.md` records where outputs work and why they do not elsewhere.
- A swapchain takes the turn of a turned display, such as the Vulkan swapchain of an Android phone held across its panel, so the window system shows its images without turning them on the GPU and every present matches the surface: the device turns the viewports and scissors of the pass and the renderer turns its positions in clip space by `gpu::Device::getPassTurns`, through `gpu::SurfaceTurn`.
- An app caps the framebuffer pixels in each point of its window with `window.maxPixelDensity`, and on a denser display the drawable shrinks to the cap while every size in points and design units stays the same. The platform hands the GPU device the drawable and its window in `gpu::Surface::Size`, the system stretches the drawable where it can, as the `CAMetalLayer`, the swapchain of DXGI and the native window of Android do, and the devices of Vulkan, OpenGL and WebGPU scale it into a window whose size the system fixes, as `docs/graphics/rendering.md` describes.
- The `Info.plist` of iPhones and iPads lists exactly the orientations of `haylen.json`, from which the system picks the orientation that the app launches in, so a landscape app opens in landscape without turning. An app whose `orientation` is `any` lists every orientation, and the foldable iPhone shows an app that lists fewer in a box on its inner screen, as it does for every app. The application delegate answers the orientations of a lock that `window.lockOrientation` asks for while the app runs.
- Mobile apps follow the platform lifecycle: app states (`active`, `inactive`, `background`), audio sessions and interruptions, low-memory warnings with their level and orientation. Every moment of the system, the app and its screen that a platform reports reaches the app as an event of the one lifecycle vocabulary of `core::LifecycleEvent` with a state it reads, such as `powerSavingChanged` with `system.powerSaving()` and `timeZoneChanged` with `system.timeZone()`, and `docs/core/lifecycle.md` lists the source of each event on every platform. Every link that opens the app reaches it as `linkOpened` through `platform::LinkRelay`, on every platform but the web, whose page is the link that opened it, besides the native parts of the plugins that declare it. The engine keeps the audio output of an app running in the background while a voice plays exactly when the app declares to the system that it plays there, which the engine reads at run time, while the rest of the app halts as its lifecycle options decide: the mode `audio` of `UIBackgroundModes` in the `Info.plist` of the bundle on iOS, iPadOS, tvOS and visionOS, where UIKit runs the frames from a timer, and a service of the type `mediaPlayback` in the merged manifest on Android, which `PackageManager` reports, while a Mac, the desktops and the web keep every app running in the background. The plugin that plays in the background, such as one that shows what plays in the controls of the system, brings that declaration, and `audio.setBackground` turns the background off and on within it. UI positions itself in the safe area the engine reports. An app whose `orientation` is `any` turns its design with the screen, so a rotation keeps the size of its design units and the UI lays out again like a native app. The status bar stays hidden unless `window.statusBar` of `haylen.json` or the app shows it with `auto`, `light` or `dark` content, the Info.plist and the Android manifest launch the app with that value, and the engine paints `statusBarColor` behind it, since the app draws under it. The system gestures at the edges of the screen follow `window.systemGestures`, which lets them act at once unless the app defers them to a second swipe, as a game with touch controls does, or hides the home indicator until a touch, through the root view controller on iPhones and iPads and through the navigation bar and the gesture exclusion of `HaylenActivity` on Android, within the height of each side edge that Android lets an app keep. Foldable and dual-screen devices report their fold, posture and screen areas, through Jetpack WindowManager on Android, the division region and the hinge of UIKit on the foldable iPhone and the viewport segments of the browser on the web, and `debug.fold` of `haylen.json` simulates them on any screen. The cutouts of the screen, such as a notch, a dynamic island or the hole of a camera, reach `viewport.cutouts` where the platform reports their shapes, through the occluded regions of UIKit on iPhones, the display cutout of Android and the camera housing of notched Macs, and the device presets of the safe area simulation bring theirs.
- The Apple backend generates an XcodeGen spec `project.yml` with one app target for the platform of the target and a target for each app extension of the plugins, and `App.xcodeproj` from it, which compiles the sources of the app and its plugins and links `Haylen.xcframework`, with `HaylenLua.xcframework` for an app that runs Lua. Every target compiles its Swift in the Swift 6 language mode, so the Swift of the engine, the templates and the plugins builds without a warning of data races, and the Apple headers of the engine tell Swift which blocks run on the main actor and which types are `Sendable`. The `Info.plist`, entitlements and privacy manifest join the template of the backend, the engine, the plugins and the sections of the app as layers with their origins: objects join key by key, arrays gain the items they lack, and two owners that give one key different values stop the preparation with both named.
- Android apps run in `dev.haylen.HaylenActivity`, a GameActivity of AndroidX (an `AppCompatActivity`, so also a `FragmentActivity` and a `ComponentActivity`) that draws the app into a `SurfaceView`. The native runtime of `engine/src/platform/android/` runs GameActivity through its callbacks, with the frames on a thread of its own, and draws through Vulkan or, where Vulkan does not start, through OpenGL ES, whose EGL context asks for the newest version the device declares and lasts while the activity lives. Plugins therefore use the Activity Result API with stable keys, fragments and Compose, and native views are normal views above the game. The activity launches as `singleTop`, and links and notification taps enter through `HaylenLinkActivity`, which only the `haylen-links` library declares, so the launcher icon never destroys a screen opened above the game and an app without link or notification plugins exports nothing besides its launcher. The activity registers the Activity Result launchers of the screens of plugins under the keys `haylen.<id>.<screen>`, and keeps the screen that shows in its saved state, so a result that arrives after the end of the process reaches the next app as `screenRestored`. Java looks up a native method only when it first calls it, so every JNI function of the runtime lives in `engine/src/platform/android/AndroidJniExports.cpp` next to `JNI_OnLoad`, which every library that links the runtime keeps, and the verification of an Android build fails when the library that the activity loads lacks the JNI function of a native method that a class of the engine declares. The runtime looks up the Java classes and methods of the `haylen` library only through `JavaBridge::findClass` and `findMethod`, and `tools/tests/repository/test_android_keep_rules.py` fails when the R8 rules of `consumer-rules.pro` do not keep one of them.
- The desktop backend generates the CMake project of a Windows or Linux app from the template of its platform, with an `app.cmake` that finds the desktop SDK and builds the executable with `haylen_add_app` from the Lua player or the sources of a C++ app, and the bootstrap in Release, and it installs the app into the products of its build folder. The Windows project embeds the icon, the version resource with the values of `haylen.json` and the application manifest, signs release builds with `signtool` and the certificate that the environment names, and stays unsigned with a note without one. The Linux project installs the executable with a `RUNPATH` of `$ORIGIN` and `$ORIGIN/lib`, and the desktop entry, the AppStream metainfo and the hicolor icons named after the identifier, which is also the class of the window, and the backend completes the desktop entry and the metainfo, those of the template or those that `files` gives, with the values of `haylen.json`. Windows and Linux start a new process of the app for every link of a URL scheme, with the link after `--link`, which hands the link to the instance that runs, through a named pipe of the session on Windows and the method `Open` of `org.freedesktop.Application` on the session bus on Linux, and the installer of Windows and the desktop entry of Linux register the schemes that the `urlScheme` contributions of the plugins declare, which `haylen app run` also registers for the installed app of the build folder. The command `haylen app package --format installer` makes the installers through CPack: the Inno Setup installer of Windows, and the `.deb` and the AppImage of Linux. Desktop apps reach native code through the native libraries of the `native` section of `haylen.json` and of the plugins.
- The scaffolds of apps are layers: `templates/common` holds what Lua and C++ apps share, `haylen.json`, the logo, the bridge handlers under `native/` and the `.gitignore`, `.editorconfig` and `.clang-format` of an app, and `templates/lua` and `templates/cpp` hold what only their kind has, `source/main.lua` or `src/App.cpp`. The command `haylen new` with `--kind lua` or `--kind cpp` takes the common layer first and then the layer of the kind, whose file replaces a common file of the same path, and no file repeats between the layers. The templates of the generated projects are inputs of their backends and live with them in `tools/haylen/platforms/<name>/template/`. Both kinds ship a working example of the bridge, the method `app.greet` and the event `app.greeted`, which Lua or C++ calls and native code answers: Swift with its Objective-C loader in `native/apple/`, Kotlin in `native/android/App.kt`, JavaScript in `native/web/app.js`, and C++ on Windows and Linux in `src/App.cpp` of a C++ app.
- The Android backend generates a Gradle project that depends on the haylen AAR of the Android SDK, whose modules find the engine version in the extra property `haylenEngineVersion` and whose external native build compiles `haylen-app` and the native libraries for every ABI against the SDK of that ABI. The native code of an app registers its bridge handlers and sends its events from the files that `haylen.json` names: the `sources` of `platforms.apple`, the `sources` and the `applicationClass` of `platforms.android`, the `scripts` of `platforms.web` and the `cpp.sources` of a C++ app. Android release builds sign with the upload key that `haylen app sign --target android` writes into `platform/android/keystore/` of the app, which the `.gitignore` of the app keeps out of its repository, or with the key that CI gives through Gradle properties or environment variables, and stop with a clear message without one. Build products go to `build/apps/<app>-<hash>/`, outside the app, and Apple apps declare the APIs with required reasons of the engine in a privacy manifest merged from the engine, the plugins and the app. The web backend generates a loading page with the app or engine logo, a progress bar with its percentage, the graphics API that the address asks for, the error screen and the turn screen that covers a phone or a tablet held in an orientation that the app does not take, since a browser locks the orientation only in fullscreen, and the variables at the top of its `loader.css` restyle the splash through a `loader.css` of the app that `platforms.web.files` names. The default shell of `haylen_add_app` for the web apps of CMake projects shows the same splash, which the progress that the runtime reports through `onLoadProgress` feeds.
- Splash screens follow `haylen.json` and work in landscape and portrait on every device. The splash screen, and on desktops the window, which opens hidden except on Wayland, where a hidden window takes no frames, gives way only to the first complete frame of the app, which `core::Engine::isFrameComplete` reports: the first scene loaded, every picture of the UI arrived and every GUI laid out in an earlier frame, so no empty frame and no picture that pops in follows the splash. On iOS, iPadOS, Mac Catalyst and tvOS the app starts while its scene connects, so its window, covered by the launch storyboard whose logo is centered in the whole view, is in the first frame of the scene, and the logo never moves or blinks from the launch screen of the system to the app.

## Async and threading

- The frame thread owns the GPU, the Lua state, scenes, UI, audio control and physics. It never blocks, so the audio device opens on a thread of its own and the app runs without sound until the system answers.
- The one exception is a halt of the Lua debugger in development, at a breakpoint, a step, a pause or an uncaught error, which holds the frame thread inside the code of the app until the editor lets it go on. While it halts, the host keeps processing the events of the window and the system through `Host::pumpHaltedEvents`, so the platform never marks the app as hung, and those events reach the app only after the halt. The platform layer runs no frame, nothing else of the app runs, the development connection carries only the messages of the debugger, and the sounds that already play go on in the mixer. A quit, a window that goes away or an activity that ends lets the frame finish without halting, and a web page, whose one thread delivers every message, never halts.
- The platform layer plays a frame at every refresh of the display, at the highest refresh it has, or at the frame rate the app asks for with `window.frameRate`, which displays that vary their refresh follow through the system API of each platform, while `platform::FrameRateGate` picks the refreshes of a faster display that play, and iPhones get past 60 hertz through the `CADisableMinimumFrameDurationOnPhone` that the tools add to the `Info.plist`.
- An app whose `window.redraw` of `haylen.json` is `onChange` updates and draws only the frames that something changed in, as user interface toolkits do, while games keep the default `always`. The platform layer still plays a frame at every refresh, `Engine::frame` always runs the news of the platform, the event loop, the clock and the time of the timers, and the updates, the drawing and the present run only when an event, work of the event loop, a timer, a tween, a scene change, a change of the window, held input, `Engine::requestRedraw` or a plugin that answers `isAnimating` asks for the frame, followed by `Engine::kSettleFrames` frames. Every part of the engine that moves by itself answers `isAnimating` or asks for frames, the UI through `ui::Context::requestFrame`, a frame that draws nothing presents nothing, so every swapchain keeps its last image, and the platform layer paces it at the refresh of the display.
- Varn's event loop is advanced once per frame with `Scheduler::poll(budget)`, whose budget is a share of the frame time within bounds that `core::Engine` declares, so no amount of ready work holds a frame up. Promises resolve, coroutines resume, timers fire and socket and HTTP callbacks run inside that call, on the frame thread, in passes that repeat while they make progress and the budget lasts, and what the poll reports reaches the debug overlay and `debug.stats()`.
- Long-running CPU work (image and audio decoding, map parsing, path finding, procedural generation, data-parallel updates) runs on the `taskPool()` of Varn's scheduler through `core::JobSystem`. Blocking I/O runs on its `ioPool()`. Results return to the frame thread through the event loop and, for Lua, through a Varn `Promise` that a coroutine can `:await()`. Slow Lua APIs offer an asynchronous version that returns a promise.
- A GPU device that compiles a shader when its program is made, such as the Metal device, starts compiling the programs of the renderer and of every `.shader` file on the I/O pool as soon as they are known through `gpu::Device::prepareProgram`, and each program is made the first time a draw needs it. Apple builds of the engine precompile the programs of the renderer into Metal libraries with the Metal toolchain of Xcode, so the Metal device loads them and compiles only the `.shader` files of the app.
- A compilation that its graphics API cannot stop, such as one of the compiler of Direct3D, runs on threads of its GPU device that nothing waits for, so a quit or a restart never waits for a program that was prepared ahead.
- Lua code never runs on worker threads. Long Lua computations run as `haylen.jobs` coroutines that share a time budget each frame.
- Never iterate a container while the loop body can run Lua or a user callback. Snapshot first, into storage that the next snapshot reuses, then iterate the snapshot, or reach a container that only grows by index up to the count it had before the loop.
- A job posted to a pool or to the loop never lets an exception escape. The job system hands failures to the frame thread, where they become engine errors.
- GPU resource creation and destruction stay on the frame thread. Handles released on any thread hand their GPU objects to the device, which destroys them after the frame is submitted.
- Static objects that other threads may still use at process exit are created with `new` and never destroyed.
- The web build is single-threaded like Varn. Pool jobs run when the poll drains them, and `JobSystem::parallelFor` runs inline there, so pages need no cross-origin isolation.

## Lifecycle and ownership

- One `core::Engine` owns every service of one running app, and one engine runs at a time in a process, which the engine enforces. Restarting an app destroys the engine between frames and creates a new one with a fresh Lua state once the platform prepared its GPU device, which WebGPU hands over only in a later turn of the event loop of the page, and the engine shuts down in a fixed order that releases Lua values before the Lua state closes.
- Scene changes run as one pipeline: the transition covers the current scene, the next scene loads asynchronously in its `load` hook (with progress, optionally behind a loading view), enters, and the transition reveals it. Effects that show both scenes at once load first. Transitions are optional and scenes pass through the states `created`, `loading`, `loaded`, `entering`, `active`, `covered`, `exiting`, `exited` and `unloaded`.
- Everything a scene or another owner creates (timers, tweens, event listeners, signal connections, async tasks, GUIs) belongs to it and ends with it, so no callback or coroutine ever runs for an owner that is gone. APIs that register callbacks take an `owner`, and without one they take the default of `lua::Owners::pushDefault`, which in development is the owner of the module that runs its top level, so a reload of the module ends what it registered.
- The game pause gates scenes, autoloads, timers, tweens and audio buses through process modes (`inherit`, `pausable`, `whenPaused`, `always`, `disabled`), and the app states halt the app in the background as the lifecycle options decide.
- The engine holds the start of an app with `Engine::holdStart` while the content it needs to start downloads behind the update screen, and the app starts in the first frame after the last hold ends.
- Engine and app events travel on the `EventBus` with one lifecycle vocabulary for the app, scenes, windows, input devices, network and objects, and signals connect objects directly. Both support priorities, one-shot and deferred delivery, and connections that end with their owner.
- Autoloads are app-wide singletons that live for the whole app and receive the lifecycle callbacks. The ones that `lua.autoloads` of `haylen.json` lists load in order before `source/main.lua` runs, and `haylen.autoload` adds more while the app runs.

## Naming

- Types, enums and enum values use `PascalCase`. Functions, methods, variables, parameters and members use `camelCase`. Constants use `k` + `PascalCase`.
- Members have plain names with no prefix or suffix: never `m_`, `_` or a trailing underscore.
- Accessors: getters use `get` (`getPosition`), boolean queries use `is`, `has` or `can` (`isVisible`, `hasFocus`), and setters use `set` (`setPosition`). Container-like classes keep the standard library names (`size`, `empty`, `begin`, `end`, `clear`). Plain data structs without invariants expose public fields instead of accessors.
- A parameter or local variable never reuses the name of a member of its class, so nothing shadows a member (setters take `value`).
- Names say what something is. A plugin, class or module named after a verb or a vague word (like a plugin called `save`) is renamed to the thing it owns. Names use the common terms of the field, the words that developers of games, graphics and apps already know, such as `Mat4`, `slerp`, `frustum`, `normalMap` or `navMesh`, never an invented word or a rename of a known idea, so nothing reads as confusing.
- The product name is Haylen, written `haylen` in identifiers, targets, modules and files. Things the engine runs are apps, never games: `haylen.json`, `haylen_add_app`, `core::Application`.
- Every app of the repository, its samples, templates, benchmarks and the apps of the tests, has the identifier `com.haylen.<product>` with a short product name, such as `com.haylen.music`, and the native code of the plugins of the samples and of the plugin template lives in packages under `com.haylen.plugins`. The prefix `dev.haylen` names only the engine itself: its Java and Kotlin packages, its Android libraries and the keys it reads from manifests.
- A class of the Lua layer that implements an interface of the core with Lua values takes the prefix `Scripted`, such as `lua::ScriptedScene` and `lua::ui::ScriptedPageSource`, and no class of the Lua layer repeats `Lua` in its name, such as `lua::Config` and `lua::content::BytecodeCompiler`.
- A tree of UI components mounted and shown together is a GUI: `ui::Gui` in C++, `haylen.Gui` in Lua, `gui` in fields, variables and event tables, such as `self.gui` of a scene.
- Lua names use the same words as the C++ API: modules are `haylen.<module>`, functions, methods, fields and option keys use `camelCase` and types use `PascalCase`. Accessor prefixes do not reach Lua: a C++ `getX`/`setX` pair is the Lua property `x` (`sprite.x`), and a read-only getter is a Lua property or method without the prefix (`world.bodyCount`, `world:stats()`).
- Every name the Lua API takes or returns as a string is `camelCase` too: enum values, which are the C++ enum value with a lowercase first letter (`ProcessMode::WhenPaused` is `'whenPaused'`), event names, input control names, cursor names, easing names and asset type names. The keys of `haylen.json` and of engine data files are `camelCase` as well.
- A type that exists in both dimensions takes the dimension in its name, with the common forms of the field. Vectors and matrices take the digit, as in shader languages: `Vec2`, `Vec3`, `Vec4`, `Mat3` and `Mat4`. Every other type that exists in both dimensions takes `2D` or `3D`, such as `Transform2D`, `Spline3D`, `Ray2D`, `Geometry3D`, `Noise3D` and `Physics2DPlugin`, and a type that exists in one dimension only keeps its plain common name, such as `Quat`, `Plane`, `Sphere` and `Frustum`. A 3D type that arrives with the name of a 2D type renames both in the same change, with no alias, and their Lua names follow the type, such as `m.vec3`, `m.spline2d` and `m.transform2d`.
- Lua modules of 2D subsystems end with `2d`, such as `haylen.graphics2d`, `haylen.physics2d` and `haylen.animation2d`, and Lua modules of 3D subsystems end with `3d`, such as `haylen.graphics3d` and `haylen.physics3d`, so the modules of the two dimensions never conflict. Dimension-agnostic modules keep plain names, such as `haylen.graphics` for textures, render targets, fonts and shaders, and `haylen.tiled` keeps its name because Tiled maps are 2D by nature.
- C and C++ source files (`.h`, `.hpp`, `.c`, `.cpp`, `.mm`) use `PascalCase` named after their class, for example `FrameClock.hpp` and `Renderer.cpp`. Lua files use `dash-case`, for example `main-menu.lua`, and every package keeps `source/main.lua` as its entry point. Lua modules are required with the same name, for example `require("scenes.main-menu")`.
- CMake module files use `dash-case`, for example `haylen-dependencies.cmake`. Sample folders use `dash-case`, for example `samples/games/tiny-island`.
- Every CMake target, project and install component, and every library, executable and other file that the build generates, uses dashes, such as the targets `haylen-engine` and `haylen-tests`, the install component `haylen-sdk`, the library `libhaylen-app.so` of Android release builds and the desktop library `native-demo` of a plugin. An underscore appears only where a name must be an identifier: CMake functions and variables, such as `haylen_add_app` and `HAYLEN_PLATFORM`, C and C++ symbols, such as the init function `native_demo_haylen_init` of that library, Java and Kotlin packages, Python modules that other files import and Android resources, while a prebuilt library of a third party keeps the name of its files. The tests of `tools/tests/repository/test_cmake_names.py` fail on a target, project or install component with an underscore in a tracked CMake file or in the CMake text that the backends write, and name it.
- All folders are lowercase. File and folder names, assets among them, use dashes and never underscores, such as `docs/platform/platform-bridge.md` and `content/audio/fire-loop.ogg`. An underscore appears only where a name must be an identifier or a platform requires it: Python modules and the tests that pytest discovers by `test_*.py`, while a script run only as a command takes dashes, and Android resources under `res/`, whose names allow only letters, digits and underscores. GitHub reads the issue templates only from the folder `.github/ISSUE_TEMPLATE` and the funding links only from `.github/FUNDING.yml`, so those two keep the names GitHub requires, while the templates inside that folder use dashes, such as `bug-report.md`. The tests of `tools/tests/repository/test_file_names.py` fail on any other tracked file or folder with an underscore and name it.

## Code organization

- Every context has its own namespace, matching its folder: `haylen::core`, `haylen::math`, `haylen::io`, `haylen::assets`, `haylen::graphics`, `haylen::text`, `haylen::input`, `haylen::audio`, `haylen::ui`, `haylen::platform`, `haylen::localization`, `haylen::conversation`, `haylen::storage`, `haylen::ai`, `haylen::debug`, `haylen::net`, `haylen::content`, `haylen::gpu` and `haylen::plugins` in the core, and `haylen::lua` with the toolkit of bindings in the Lua layer, whose bindings live in `haylen::lua::<context>`, such as `haylen::lua::physics2d::BodyBinding`, with the types of the core written with `haylen::` in front, and whose Lua modules live in `haylen::lua::modules` with the dimension in their names, such as `Physics2DModule`. The code of the platform layers of SDL and of the worker and of each GPU device lives in the namespace of its folder, `haylen::platform::sdl`, `haylen::platform::worker` and `haylen::gpu::<api>`, such as `haylen::gpu::vulkan`. Folders under `2d/` map to namespaces with the `2d` suffix, the same names as their Lua modules: `haylen::graphics2d`, `haylen::animation2d`, `haylen::particles2d`, `haylen::lighting2d`, `haylen::physics2d`, `haylen::navigation2d`, `haylen::spatial2d`, `haylen::procedural2d`, `haylen::nodes2d`, plus `haylen::tiled`. Nothing lives directly in the `haylen` namespace.
- A type name does not repeat its namespace when a precise name exists: `haylen::physics2d::World`, `haylen::physics2d::Body`, `haylen::tiled::Map`, `haylen::graphics2d::Camera`, `haylen::text::Layout`, `haylen::lua::Promise`. Types in the shared `haylen::plugins` namespace name their dimension (`Physics2DPlugin`).
- One class per file. A header and its source file hold one class and are named after it. Types owned by a single class (its options, events, results and enums) are nested in that class. A type shared by several classes gets its own file.
- There are no free functions. Every function is a method of a class: utilities are static methods (`math::Easing::apply`, `math::Geometry2D::intersects`), helpers of a source file are private methods of its class, operators are hidden friends defined inside the class, and each Lua binding is a class whose Lua entry points are static methods. There are no anonymous namespaces either. The only exceptions are entry points whose names the platform or the language dictates (`main`, `WinMain`, `JNI_OnLoad` and `Java_*` JNI functions, Emscripten exports, C callbacks with fixed signatures and other functions of C linkage, and the replacements of the global allocation functions that `test::AllocationTracker` installs), and each one only forwards to a class. The tests of `tools/tests/repository/test_namespace_scope.py` fail on an anonymous namespace or a function or variable at namespace scope in any C or C++ source under `engine/`, tests included, and name it.
- There are no namespace-scope variables or constants in source files. They are static members of the file's class.
- Every enum has exactly one table of its string names, and every Lua binding and file parser uses that table.
- Plugins live in `engine/include/haylen/plugins/` and `engine/src/plugins/`, in the `haylen::plugins` namespace, together with the `Plugin` interface. A plugin wires its subsystem into the engine, the subsystem itself stays in its context folder, and the `lua::Module` of its Lua module lives in `engine/lua/src/modules/`. Plugins that apps construct or reference have public headers, and the others keep their headers in `engine/src/plugins/`. The class `plugins::BuiltInPlugins` registers the built-in plugins in dependency order.
- Everything specific to 2D lives in a `2d` folder (`engine/include/haylen/2d/`, `engine/src/2d/`, `engine/tests/2d/`, and `engine/lua/src/2d/` with the bindings of the 2D modules and `engine/lua/tests/2d/` with their tests), and dimension-agnostic code never depends on it. Everything specific to 3D lives the same way in a `3d` folder of each of those places, `engine/include/haylen/3d/<context>/`, `engine/src/3d/<context>/`, `engine/tests/3d/<context>/`, `engine/lua/src/3d/<context>/` and `engine/lua/tests/3d/<context>/`, whose folders map to the namespaces `haylen::graphics3d`, `haylen::lighting3d`, `haylen::nodes3d`, `haylen::animation3d`, `haylen::physics3d`, `haylen::navigation3d`, `haylen::particles3d`, `haylen::spatial3d`, `haylen::procedural3d` and `haylen::terrain3d`, with their bindings in `haylen::lua::<context>3d`. The reader of glTF keeps the name `haylen::gltf`, as `haylen::tiled` does, because glTF is 3D by nature, and the common core of XR is the context `haylen::xr` in `engine/src/xr/`, whose hosts live in `engine/src/platform/<platform>/xr/`. A folder of a context exists once code of that context fills it. 2D and 3D never depend on each other, `gpu` and `graphics` depend on neither, the 3D renderer depends on no physics and no navigation, and the public headers of XR include no header of SwiftUI, ARKit, Java or OpenXR, which `tools/tests/repository/test_layer_isolation.py` checks, while `tools/tests/repository/test_lua_layer.py` keeps the Lua of 3D in the Lua layer as it keeps that of 2D.

## Lua bindings

- Each context keeps its Lua binding class in the folder of the context in the Lua layer, such as `engine/lua/src/2d/physics/Physics2DBinding.cpp` with the class `haylen::lua::physics2d::Physics2DBinding`, built with the public toolkit in `engine/lua/include/haylen/lua/` (`Binding`, `ClassBuilder`, `Userdata`, `Stack`, `Converter`, `Table`, `Promise`, `Reference`, `TypeConverter` and `Runtime`), whose `Converter` passes every enum by the names of its `core::EnumNames` specialization. Projects that extend the engine use the same toolkit.
- Every public C++ and Lua API follows `docs/tools/api-policy.md`, which says what is public and stable and how an API grows without breaking apps: options in a trailing table, returns that describe something as tables, event payloads as one table or at most two values in a fixed order, the same words for the same ideas across modules, and an `owner` on everything that registers a callback, a task or a job.
- The Lua API is the same on every platform and graphics API. A Lua binding never includes a host or a platform folder, which `tools/tests/repository/test_layer_isolation.py` checks, so what a script sees never depends on what draws the app.
- Options are passed as tables whose unknown keys raise `Unknown option "<key>".`, and enums are passed as their string names.
- Option tables read on every draw or for every item go through `Table::readFields`, which reads the keys a table holds in one pass with `Table::readValue`, instead of one `Table::readField` per known option.
- Error messages are complete sentences that start with a capital letter and end with a period, and they say what was wrong and what is expected, such as `No canvas is active. Call "beginWorld", "beginScreen" or "beginTarget" before drawing.`. The only exceptions are the short reasons of `luaL_argerror` and `luaL_typeerror`, which Lua wraps into its own `bad argument` sentence.
- A yield of Lua jumps straight back to its `lua_resume` with `_longjmp` on every compiler but MSVC and except in thread sanitizer builds, and runs no destructor of the C++ frames it leaves. A C++ function that calls `lua_callk`, `lua_pcallk` or `lua_yieldk` therefore keeps no destructible local alive across that call, never makes it inside a `catch` block or inside `Binding::guarded`, and hands what its continuation needs over the Lua stack, an upvalue or its `lua_KContext`. An error stays a C++ exception and runs every destructor. Each such function has a test that yields through it.
- Userdata keep their Lua callbacks in their user value, so a callback that refers back to its owner never keeps it alive. C++ code that keeps a Lua value alive uses `lua::Reference` and releases it in `stop`.
- Hot paths offer fast Lua access: number fields next to vector properties, native properties that tweens animate in C++, float buffers shared with C++ and bulk APIs that move many objects in one call.
- App code loads Lua chunks only as text (`"t"` mode): `load` and `loadfile` refuse bytecode, `dofile` runs only text, and `string.dump` and `package.loadlib` do not exist. The one exception is the module loader of the engine, which loads a module as bytecode only when the authenticated catalog of a protected release holds it as `LuaBytecode`, compiled by the content tool with the Lua of the engine for the ABI that the app manifest records.
- Code that may fail runs in an `Engine::Phase`: lifecycle steps, such as the start of the app, scene hooks that load, enter, exit, unload, pause or resume, autoloads that start or stop and tasks that failed, open an `Engine::PhaseScope` of `Lifecycle`, so their errors restart the app in development, while errors of frame code and of reloads resume it once a fix reloads.
- Every failure that no caller receives reaches the error screen through the handler of `async.onFailure` that the engine installs, and a promise that rejects while nothing awaits or catches it is such a failure. A binding rejects with `lua::Promise::reject` when the promise is the only way its failure reaches the app, and with `rejectHandled` when the engine reports the failure another way or the app asked for it, such as a cancellation.

## Native plugins

- A native plugin is a folder named after its dash-case id with `plugin.json`, a `README.md` with the complete Lua API and the setup per platform, the Lua API in `source/` (`init.lua` is `require('<id>')`), and one folder per implementation: `apple/` (Swift or Objective-C), `android/` (a Gradle library module in Kotlin or Java), `web/` (an ES module) and `native/` (a CMake project of a C++20 library for desktops, which finds the installed SDK with `find_package(haylen CONFIG REQUIRED)`, compiles against `haylen::native`, reads and writes its JSON with nlohmann/json and keeps the C interface of `HaylenNativeApi` only in its init function and the handlers it registers, which forward to a class). The file `docs/platform/plugins.md` describes every field of `plugin.json`.
- The file `plugin.json` follows `tools/haylen/schemas/plugin.schema.json`: the version of the plugin interface in `interface`, the identity and release version, `implementations`, which says for each platform it supports whether its native part runs there (`native`) or its Lua API works alone (`lua`), the plugins it depends on in `dependencies` with the oldest version of the same major that it works with, the permissions it owns, typed parameters with their platforms, defaults and descriptions, and `contributions`, a list of typed contributions, each with the platforms it applies to, that the backends of those platforms declare: the Objective-C class of the native part (`appleClass`), sources, Swift packages pinned to one exact version, system frameworks, the binary frameworks it ships, Info.plist keys, entitlements, privacy declarations, resources, build scripts and app extensions on Apple, the Gradle module, the Maven repositories of its SDKs, Gradle plugins, manifest placeholders and project files on Android, the asset packs of the stores, the module on the web, the URL schemes of the links that open the app on Windows and Linux, the native library and the oldest system version it needs. Each type of contribution declares its fields, the fields that identify one contribution and how the contributions of several owners merge: `unique` keeps one per identity and fails on two different ones, `accumulate` keeps every one, `dictionary` joins objects key by key and fails on two different values of one key, and `exclusive` lets one owner alone give the type. A platform that `implementations` does not list does not support the plugin, so a build for it fails, and a contribution of a type that no backend of its platform declares fails too. The placeholder `${parameter}` in those values is replaced with the app's value.
- Apps list their plugins in the `plugins` section of `haylen.json`, each entry an object with the parameter values under `parameters` and where the plugin comes from: the folder `plugins/<id>/` of the app without `path` and `git`, which `haylen plugin add` copies, a folder that `path` names, absolute or relative to the app folder, or a git repository that `git` names at `ref`, which the tooling checks out into a cache under `build/` at the commit that `haylen.lock` pins. The file `haylen.lock` of the app holds `{"git", "ref", "commit"}` for every plugin of a repository, which `plugin add --reference` and `plugin update` write, so every build takes the same code, and a Release build takes such a plugin only at a pinned commit. The resolver orders the plugins so every plugin follows the plugins it depends on and otherwise keeps the order of `haylen.json`. The `id` of the `plugin.json` equals the key of its entry, and `plugin add --reference` writes a reference instead of a copy. A value that differs per platform uses parameters with different names (`iosAppId`, `androidAppId`), so nothing resolves platform values at runtime. Missing parameters take the defaults of `plugin.json` on every platform.
- The package carries `plugins/<id>/plugin.json` and `plugins/<id>/source/` of every listed plugin, wherever it comes from, so the runtime never resolves a reference. Nothing else of a plugin reaches the package. A folder that the player runs directly and that lacks a referenced plugin fails with a sentence that says to run the app with `haylen app run`, which on this machine runs a copy of the package in the build folder of the app, whose development server watches the referenced folders and pushes their files under `plugins/<id>/`.
- The tooling validates every manifest and the app's values once, in the resolution of the project of a target, before any backend runs, and the backend of the target brings every contribution into the project it generates: on Apple the sources, packages, frameworks, resources, scripts and app extensions of the XcodeGen project with the joined `Info.plist`, entitlements and privacy manifest, on Android the modules of the plugins with their repositories, Gradle plugins, placeholders and project files, on the web the modules of the site with `config.json`, and on desktops the native libraries and the URL schemes. A C++ app takes every part of every plugin too, through the same projects as a Lua app.
- A plugin repository keeps the `.gitignore`, `.editorconfig` and `.clang-format` of `templates/plugin`. The skeleton of `templates/plugin` answers its method and sends its event on every platform, so a new plugin runs everywhere from its first build, and its desktop library takes the id, the name that `native.load` finds, while its init function takes the id with underscores, such as `native.load('camera-scanner', {init = 'camera_scanner_haylen_init'})`.
- Native plugin methods are named `<id>.<method>` and events `<id>.<event>`, with camelCase method and event names, and a plugin offers the same Lua API on every platform it supports. Calls a platform cannot serve fail with the code `unsupported` and a clear message.
- Native parts carry data in the form the bridge gives it: bytes, such as images, recordings and files, travel next to the JSON in the byte type of each language and never as text, large data that changes often, such as the frames of a camera that the app works on, crosses as data views whose memory every language shares, continuous video and audio go through the streams of the plugin, which keep the newest video frame and a lock-free ring of samples, and events that fire many times per frame are sent batched, so Lua receives one list per frame. A plugin declares the permissions it owns in `plugin.json`, a camelCase name that no other plugin of the app declares, and its native part asks the system for each one through the API of its platform before it uses the capability, after it checked the requirements of the permission, so the engine owns, asks for and answers no permission. The plugins that share one vocabulary of states, one queue of prompts and one launcher of the Activity Result API do so through a plugin that they depend on, whose native part theirs reaches directly: the sources of every plugin compile into the one Apple app target, the Android backend adds `api(project(":<dependency>"))` to the module of a plugin for each plugin with a module that it depends on, and the web module of a plugin imports the module of a dependency as `haylen-plugin:<id>`, which the import map of the page resolves, while a desktop library stands alone and reaches other plugins through Lua. A plugin that posts notifications links UserNotifications and makes itself the delegate of the notification center while the app launches on Apple platforms, or depends on the plugin of the app that owns that delegate, and starts `HaylenLinkActivity` from its taps on Android, sending the tap as a retained event so it reaches an app that the tap launched. The demo plugin of the test project tests each of these mechanisms on every platform.
- The Apple runtime reads the plugins, their order by their `dependencies`, their parameters and the class of each native part from its `appleClass` contribution for the platform from the bundled package (`haylen.json` and each `plugin.json`), never from a list in the platform project. The Android runtime loads its plugin classes when the process starts, before the engine opens the package, so it reads them from `haylen-plugins.json`, which the Android backend writes into the assets of the generated project with only the ids, versions and parameter values of the plugins with an Android part, and never from `haylen.json` or a `plugin.json`, which a protected release keeps encrypted.
- An Android plugin module depends on `dev.haylen:haylen-plugins`, plus `haylen-links` for links and notifications and `haylen-coroutines` for suspending handlers.
- The plugins of system capabilities, such as the camera, the location or notifications, and the plugins that bring third-party SDKs, such as ads, analytics, crash reporting, sign-in, purchases or game services, live in the sibling repository `haylen-plugins`, one folder each, and never in this repository, which uses no third-party library beyond the dependencies of the engine. This repository holds the plugin architecture, the engine and platform capabilities they build on, and the demo plugin of the test project, built on platform APIs alone, which tests every capability. The command `haylen plugin add` takes a plugin folder, or a plugin repository at a branch, tag or commit that holds the plugin at its root or in the folder that `--path` names, and an entry of `haylen.json` references the same with `path`, or with `git`, `ref` and `path`.

## Architecture rules

- Engine code lives under `engine` and never depends on samples, templates or apps.
- Apps consume only public engine headers from `engine/include` and the Lua API.
- The portable engine library never calls SDL, a graphics API or OS APIs. It reaches them only through the internal `Host` interface in `engine/src/platform/Host.hpp` and the `gpu::Device` it creates. The target `haylen-runtime` implements the host for real platforms with the native host, the player, the services of the platform folder and the platform layer, the target `haylen-gpu` holds the GPU devices, and `haylen-headless-host` implements it for tests with the null GPU device `gpu::NullDevice`, which checks every call against the contract of `gpu::Device` and records what each frame did.
- The portable code of the engine never asks which system it compiles for, with no condition on a macro of a system such as `_WIN32`, `__APPLE__` or `__EMSCRIPTEN__`, which `tools/tests/repository/test_system_macros.py` checks. Code of one system lives in the platform folders of `engine/src/platform/`, in the public headers of the native parts of plugins on Apple platforms in `engine/include/haylen/platform/apple/`, which tell AppKit from UIKit, in the folder `posix` that Apple platforms, Linux and Android share, in the folders `posix` and `windows` of a context, such as `content/posix/StoreFile.cpp`, which CMake picks one of by the system interface `HAYLEN_SYSTEM_API` of the build, in the folders `unavailable` that a platform without a capability takes, and in the folders of the GPU devices. What a platform allows, its capabilities `dynamicLibraries`, `executableMemory` and `processes` and whether it runs threads besides the one of the frames, is a fact of the build that `port::Contract` tells, and the engine answers a missing one with a clear sentence where an app reaches it.
- Only `engine/src/platform/sdl/` and its tests include the headers of SDL or call it, and only the GPU devices in `engine/src/gpu/` and their tests include the headers of a graphics API, which `tools/tests/repository/test_layer_isolation.py` checks.
- Rendering goes through the Haylen graphics API down to the `gpu::Device` that draws, whose graphics API every device names with the one table `gpu::Device::kApiNames`. Apps never include SDL, a graphics API, Box2D, miniaudio, Dear ImGui backend, Varn internals, JNI, UIKit, AppKit or Emscripten headers, while the public headers of Varn's data view are part of the API of the bridge.
- Every GPU device captures frames with the capture tool of its graphics API, which `gpu::Device::getCaptureSupport` names with what is missing where it has none: the frame capture of Metal, which the Debug runs of `haylen app run` turn on with `MTL_CAPTURE_ENABLED` when they start an Apple app or the player, PIX on Direct3D 12 and RenderDoc on Direct3D, Vulkan and OpenGL, while browsers and the null device have none. The engine never bundles or loads RenderDoc or PIX, which hook the graphics API only when they launch the app, and `debug.captureGpuAsync`, the console command `gpuCapture`, the key `g` of `haylen app run` and `haylen app capture` write the capture into the storage of the app.
- The fragment stage of the 2D programs does only the work a draw needs, since a modest phone pays for every pixel of every layer: the renderer hands each draw the form of its texture, with levels, a single level or the white texture, and the count of the edges of its fade, sprites, meshes and shapes read their texture at their own coordinate with the mip level the hardware takes from it, without slopes or a lookup by gradients, the values of an instance reach the fragment stage flat, a shape measures its coverage once for each pixel over the size of a pixel that its vertex stage hands it, and a glyph finds the texels of its source once for the lookups of its distance field, while a glyph without an outline, a synthetic bold or softness draws with the `text_plain` variant, which skips that work. A modest GPU reads the textures that a branch on a uniform guards even where the branch does not run, so a step that reads textures and that many draws skip compiles into a variant of its own, as compositing, lights with shadows and the lights of a canvas whose draws all take them as its background does, which draws its scene without the emission, surface and info images, instead of a uniform branch. A change to the shader library keeps the image the same and is measured by the GPU time of a layer that covers the screen on a modest GPU, such as the Adreno 610.
- Every part of 3D follows one set of conventions, which `docs/3d/coordinates.md` draws: right-handed axes with `y` up and a camera that looks along negative `z` (`math::Vec3::right`, `up` and `forward`), one unit for one meter in physics, audio, XR and light, so every distance, size and position of the 3D API is in meters and every speed in meters per second, with mass in kilograms, force in newtons, torque in newton meters, density in kilograms per cubic meter, gravity of 9.81 meters per second squared toward negative `y` by default and only the lens and sensor of a physical camera in millimeters, angles in radians as in 2D, matrices stored by columns and multiplied as `projection * view * model`, rotations as normalized quaternions `(x, y, z, w)`, front faces that run counter-clockwise, reversed depth in a float depth buffer where the graphics API allows it, the range of depth of each graphics API kept in its `gpu::Device` (`0` to `1` on Metal, Direct3D, Vulkan and WebGPU, `-1` to `1` on OpenGL and WebGL2, corrected in the projection, with `glClipControl` where the driver has it), the same origin of textures and render targets on every graphics API, light in linear space with base and emissive colors in sRGB, normal and ORM textures linear and tone mapping only at the end of the frame, while 2D keeps its own units. No module converts a convention anywhere but in the place that owns it.
- glTF 2.0 is the one model format that the engine reads at run time, supported in full and measured in meters: the `model` asset reads any valid `.glb` or `.gltf` file as it is on every platform, with the buffers and images of a `.gltf` beside it inside the package, and any other format reaches an app either through the import tool, which converts it to GLB through Blender run without a window on the developer's machine, or through a plugin that loads it at run time. WebP images are supported everywhere, also inside glTF through `EXT_texture_webp`, and AVIF is not, so a glTF file that requires `EXT_texture_avif` fails with a sentence that names the image format.
- Every curve has an edge that fades over one pixel of its destination at any size, zoom, rotation, density and graphics API, without multisampling. Circles, rings, arcs and shapes draw as one quad of the shape program, whose shader turns the exact distance to the edge into coverage, with the border inside the same edge, and polygons and meshes fade their outline over a fringe one pixel wide. Paths flatten their curves and arcs within a quarter pixel of the destination, resolve their outlines by their fill rule into simple outlines and holes, and fill and stroke through the same fringes, keeping their triangles between draws. The UI draws every curve of its components, their borders, focus rings and shadows as these shapes through callbacks of the ImGui draw list, and ImGui tessellates and fades what it draws itself in pixels of the screen. Nothing depends on the `sampleCount` of the window, which render targets and captures never have.
- A glass draw reads what its canvas and the canvases before it drew into its destination behind its shape: it ends the pass of its destination, an end that the later glass draws share while nothing drawn since then reaches what they read, and blurs only the region it needs through images of half the size and smaller, discarding the rest of those images, so its cost follows its area and never loops over its radius, and a screen whose canvases hold glass draws into an image of its own that reaches the swapchain in one copy. Effects of apps on glass are materials whose shape program reads `haylen_backdrop`, and the dithered fades of groups and masks pattern their share in cells of the canvas.
- Services the engine offers on every platform, such as system information, the clipboard and every screen of a browser, go through the `Host` interface and the services that each platform runtime installs by capability, and complete asynchronously on the frame thread. The engine exposes them as its own C++ and Lua APIs (`platform::System`, `haylen.system`), never as bridge methods.
- A font family draws what none of its fonts holds with the fonts of the system, which the host finds and reads on the I/O pool through the API of each platform, CoreText, DirectWrite, the font matcher of Android and fontconfig, which the engine loads at run time, never reading what the system does not hand an app. The engine asks for each character once, keeps one font for each face, reads each face through HarfBuzz and refuses one whose glyphs it cannot draw, such as a face of bitmaps alone, and lays text out again when a face arrives, and a web page has none, as `docs/graphics/text.md` describes.
- The engine owns, asks for and answers no permission and declares none in the projects it generates. Every capability that at least one platform gates behind a permission, a prompt or a policy has one API shaped for the strictest platform, as `docs/tools/api-policy.md` describes: asynchronous everywhere and answered with a state of one vocabulary instead of a boolean, so an app runs the same complete flow on every platform. A permission belongs to the plugin that declares it in the `permissions` of its `plugin.json` and offers its check and its request in its own Lua API. The calls of the engine that a system may refuse, fullscreen, the mouse lock, keeping the screen on, the clipboard, the persistence of the storage of a browser and every screen of a browser, answer with a `platform::SystemAnswer` of `Granted`, `Prompt`, `Denied` or `Unsupported` with the requirements that the project lacks and the sentence that says why, which a promise of Lua resolves or rejects with the code `denied` or `unsupported`.
- The `platform::Bridge` carries only the methods and events of apps and native plugins, as JSON requests and asynchronous callbacks delivered on the frame thread. It has no built-in methods.
- The engine libraries carry only what every app needs, and the backend templates declare the rest, such as the normal permissions of Android for the network, the network state and the rumble of gamepads, which Android grants without asking, as defaults that an app removes with `platforms.android.manifest.removedPermissions`. A feature checks its platform requirement before it calls the system API, and when the requirement is missing it logs once what is missing and how to add it, then fails with `unsupported` and `data.missing`, or does nothing when it answers nothing. Plugins check theirs with `HaylenRequirements` on Apple platforms and Android and with `context.require` on the web.
- The engine links no framework or library that only some apps need, and the frameworks that only plugins use, such as UserNotifications and MediaPlayer, come with the `frameworks` of their `plugin.json`. The build of every slice of the Apple SDK checks with `AppleFrameworkCheck` that each framework of the list of its platform in `engine/cmake/haylen-app.cmake` gives the merged `libhaylen.a` a symbol that it leaves undefined, and fails with the frameworks that give none, and `docs/tools/distribution.md` gives the reason of every framework and library that the engine links. The tests `EngineBoundaryTest` of `tools/tests/repository/test_engine_boundary.py` fail on a source of the engine that names the permission system of plugins, the notification center or the controls of what plays, on a manifest of the Android libraries of the engine that declares a permission, on an Apple template that declares a usage description, a background mode or an entitlement, and on a framework list that names a framework the engine does not use.
- Every JNI call from C++ into Java checks for a pending exception, which is described to logcat, cleared and logged as an engine error that says where logcat shows its stack.
- A finger that travels past the slop of `ScrollArbiter` or shares the screen with another finger never clicks: the UI backend lets go of the item it pressed, unless the component that holds it calls `Context::keepDrag` because it follows the finger, and the gestures of `haylen.input` never end as a tap a finger that shares the screen or that once travelled past their `tapMaxMovement`. The mouse that a finger drives through `input.touchAsMouse` reaches the app alone, so the UI follows the finger and a drag always scrolls the area under it.
- All gameplay input goes through the action map, and UI input goes through focus navigation that works with every device. The game and the UI share the devices through the play area of a GUI: while the play area has the focus, the directions, accept and menu reach the action map, while a control has it, the UI captures every navigation key, button and stick, and a press stays with the side that took it until it is released.
- UI positions itself in the engine-provided safe area.
- The GUIs of the app share one ImGui window, so the backend gives the pointer to one GUI at a time: the GUI that drew last over it in the last frame, with an item, a surface or a scroll area, or the GUI that holds a press. A GUI of a higher layer therefore always takes the pointer from the items and scroll areas of the GUIs under it.
- Apps move between their screens through the navigation of `ui::Navigation`, which `docs/ui/navigation.md` describes. A screen, `ui::Screen` or a table of `ui.Screen`, builds its GUI the first time it shows and keeps it while it lives. A `NavigationStack` shows its screens in the area of a node of a GUI, a frame or another screen, and plays the transition of a change inside that area while the GUI around it stays, with the screens of the change inert, once the GUI of the screen that comes laid out with every picture it shows, or after the bounded wait of `Navigation::kReadyWait`, so no picture pops in while a screen moves. `NavigationTabs` keep a stack for every tab, a `NavigationSplit` shows a list and its detail in two areas or moves the detail onto the list as one stack when the app collapses it, and a `Presentation` shows a screen over every GUI as a sheet with detents, a full screen cover, a dialog, a drawer from the start edge or a popover that points at a node and becomes a sheet on a compact screen, one narrower than a form sheet in UI units or in points, while a form sheet on a wide screen is a card without detents. A modal presentation parks the focus of the GUIs under it, which then draw in an ImGui window of their own without input and without elements for screen readers and give the focus back once it leaves, while a sheet that is not modal draws in a window of its own above the GUIs of the app, which keep their input. The `ui::PresentationView` of the UI plugin draws the backdrop, the surface, the arrow and the grabber and follows the drags and taps, and what the person asked for that runs code of the app waits for the next update. Alerts and action sheets are presentations of screens that the engine builds with `Navigation::presentAlert`, whose card is the `dialog` component, so no overlay component opens a modal flow of its own. Messages are the navigation too: `Navigation::showMessage` shows a `ui::Message`, a toast, a snackbar or a banner with the defaults of its style, above every GUI and every presentation, and the `ui::MessageView` of the UI plugin draws each message in an ImGui window of its own in the `ui::MessageStack` of its position, where a style shows a bounded number at once and the others wait by priority, a snackbar or a banner of a higher priority replaces the one that shows, the time stops while the stack is held, and every message that comes on screen is announced to screen readers and joins their tree as an alert with its action and its close button as buttons that `AccessibilityTree::addButton` lets them press without the focus, so no component shows notices of its own. The stacks lie in the safe area, or in the area of a node that `Navigation::setMessageArea` names while it draws and no modal presentation covers it, so the messages of an app keep clear of its bars. A presented flow hands its result, a JSON value, to whoever presented it, and the `back` hook of a screen hears every way the person goes back, the system back, a tap on the backdrop and a drag that dismisses, so a screen with unsaved work keeps its place and asks first. Scenes are the flows of the app, and the navigation lives inside them: a stack lives until it closes, its owner ends or the GUI of its area unmounts. The system back goes through the layers from the top, each presentation and then the app: in each layer it pops the innermost stack that can pop, then goes to the first tab, then a modal presentation is dismissed and keeps the back from the layers under it, while a sheet that is not modal goes down to its lowest detent. Only then does it reach the root of the GUI with the focus or leave the app, so `UiPlugin::isCapturingBack` answers for the navigation and an app built on it never sets `window.setBackLeavesApp`. A `Router` of the navigation turns the links that `linkOpened` reports, and locations from code, into the state they name through routes with typed parameters: the tab, the root of the tab with the screens of the parents of the route and its own screen, a detail or a presentation. Every screen it shows keeps its location, so the router saves the state of the navigation as locations, which the storage plugin keeps in `navigation-state.json` while the app is in the background or restarts, and builds it again at the next start. Links keep the flow of `platform::LinkRelay` and the plugins, and the routes only decide the screens. The navigation keeps the last link that arrived before the app created a router that opens links, such as the link that launched it while its first scene loads, and that router opens it in its first update.
- A UI node names its ImGui items by its id, or by its kind and its place among its siblings, never by its address, so a node that its GUI builds again keeps its focus, the text being edited with the keyboard, a press in progress and the place of its scroll, and new children draw in the frame they arrive in.
- Screen readers read the UI through the tree of accessible elements that the GUIs build as they draw, only while the platform or the app wants it, and the host receives it only when it changed. Every component kind describes itself with its role, label, value and state, and the actions of screen readers reach the controls through the focus navigator, the way the keyboard and gamepads do. An element covers only the part of its node that the clip of its window shows, so nothing that finds elements by their place, such as touch exploration or the taps of UI tests, lands on a node that a scroll area hides, while a node scrolled out of sight keeps its element as a line without area on the edge of the clip, which a screen reader still moves to and the focus then scrolls into view.
- The UI and the motion of the engine follow the accessibility settings of the system: the text scale scales the fonts of the UI, higher contrast switches to the high contrast theme of the active theme, reduced transparency draws the surfaces of the theme opaque and its glass surfaces as plain ones, and tweens and transitions that opt in shorten or skip their motion.
- Areas that scroll show no scroll bar by default, since a finger, the wheel, the trackpad and the focus scroll them and their fades show that the content continues. The property `scrollbar` of a `scroll`, a `collection` and a `textArea` is `false` unless the app asks for a bar where the position in the content matters, such as a long document, a log or a code viewer, the popups and the body of a `dialog` never show one, and only the windows of `haylen.imgui` and the debug windows of the engine, which are tools with long lists, keep their bars. Every area of the UI that scrolls fades the alpha of its content out to transparent along each edge where it continues past the area, over the theme metric `scrollFade`, through the fades of `graphics2d::Renderer`, so whatever lies below shows through and no color is painted over the content. A bar that the app asks for never covers or touches its content and runs in a lane of its own along its end edge, with the theme gap `scrollbarGap` between the content and the bar, which never spans fewer than 4 points of the screen at any UI scale, and the lane takes room from the content only while the content is longer than its area. Every area that scrolls moves by the points of the screen that a trackpad reports, at once, and by the theme metric `scrollLine` for each step of a wheel, gliding there, through `Context::takeWheel`, never by the steps of ImGui, and `input.scrollSpeed` multiplies both. A trackpad that reports the phases of its gestures, as macOS does through `Event::scrollPhase` and Android 14 and later do for the two-finger swipe of a touchpad, which the activity turns from its fake finger into a scroll, drags the content of a `Scroller` the way a finger does and releases it when the fingers leave, so the inertia and the bounce are the motion of the engine, while the momentum of the system reaches only the areas without a motion of their own, and a precise device without phases moves the content within its range without stretching it. An item that the player drags scrolls the innermost area under it near its ends through `Context::takeEdgeScroll`, and a finger lifts an item only after a long press, so it never takes a scroll from the area or loses its item to one. A gesture of the wheel or the trackpad keeps the axis it starts along and the area it starts in, the innermost area under the pointer that can move along that axis, until it pauses, fingers touch the trackpad again or, on a device that reports no phases, its motion turns clearly to the other axis, and a finger goes to the innermost area it pressed whose axis its drag follows, through `Context::takeDrag`, so a vertical gesture over a horizontal list scrolls the vertical area around it. The area takes the finger in the frame after it passes the slop and moves the content at once by everything it travelled past the slop, so the content follows the finger one to one at any frame rate, a flick that lifts before the area took it still gives the area the finger as it lifts, so the content flings, and a finger that lands on content that glides stops it, takes its area at once and presses nothing.
- Videos decode with the decoder of each platform through `Host::openVideo`, never with a decoder the engine ships, open on the I/O pool and decode ahead of the playback on the task pool, so the frame thread only presents the frame of the current time, and their sound plays through the mixer.
- Physics goes through the Haylen Box2D wrapper, whose handles detect a destroyed world. A world runs the tasks of each Box2D step on `core::JobSystem` once enough of its bodies are awake, and the helpers that act on a world every step, such as vehicles, force fields and fluids, run in C++ through its step hooks, never as a Lua call per body.
- Every common physics problem, such as tunneling, ghost collisions at tile joints, slopes, moving platforms and stretching joints, has an engine option or helper that solves it, explained in `docs/2d/physics.md`, and a test of the test project shows the problem and the solution side by side.
- Protected content goes through `haylen::content`: immutable HPAK shards of chunks that are compressed and encrypted one by one, signed manifests and encrypted catalogs, as `docs/content/content.md` describes. Its cryptography comes from Monocypher alone, and nothing in the repository implements a cryptographic primitive. Every parser of a binary format treats its bytes as hostile, checks every offset, size and count before it uses them, and has hostile input tests and an entry for the fuzzer that `HAYLEN_BUILD_FUZZERS` builds. Font files are read only through HarfBuzz, by `text::FontFile`, both for the distance fields of `text::TrueTypeFont` and for Dear ImGui through the font loader `ui::ImGuiFontLoader`, so no reader that trusts the bytes of a font is in the build. Image files decode only through `graphics::Image::decode`, which refuses a size its header declares beyond `Image::kMaxSide` or the longest side the caller names before it allocates a pixel, caps every buffer of the decoder at what that size needs and keeps the pixels the decoder wrote without a copy.
- Content reaches the device through `content::ContentManager`: the `content` section of `haylen.json` makes an asset `required`, `prefetch` or `onDemand`, a synchronous load never waits for the network and fails for an asset that is not on the device, and every asynchronous load and preload brings what is missing first. The content that the engine reads before any Lua runs, the group manifest of the delivery rules and the languages of the `localization` section, is read only once the content manager has it on the device, while the start of the app holds, so the start never assumes that a file of the content domain is local. Stores that deliver packs plug in as the `content::PackSource` of their native plugins, which the manager asks before the content server, so app code never knows where an asset comes from. Downloads and updates go through the local content store, never write a plain byte, and an update becomes active only as one transaction that plays from the next start. Development applies the same delivery to the folder of the app.
- Tiled runtime code targets current Tiled JSON files and does not read obsolete formats.

## Dependencies

- The engine compiles its shaders, and apps theirs, with the Haylen shader compiler `haylen-shaderc` of the repository https://github.com/haylen-org/haylen-shader-compiler, pinned in `engine/cmake/haylen-shader-compiler.json` to a release and its commit. The script `engine/cmake/haylen-shader-compiler.cmake` provides it for CMake, whenever `HAYLEN_SHADERC` names no build, and for the tooling, which keeps it in `.tools/` and hands it to CMake unless `HAYLEN_SHADER_COMPILER` names a build: it downloads the binary of the release for the system and processor of the machine, checking its SHA-256, and builds the compiler from the source of the commit, checked the same way, only on a machine whose binary the release does not ship. The releases of the compiler, unlike those of this repository, carry prebuilt binaries, so app developers never build the compiler. It compiles the Haylen shader language into `.shader` packages with the reflection and the code of every shader language, and the engine embeds only the languages of the graphics API of its build. A change to the language or the package format lands in the compiler first and reaches the engine with a new pin. The compiler keeps one commit and one version, `1.0.0`, whose release, named by the version alone, every change of the compiler rebuilds, so a new pin names a new commit and new hashes under the same version, and the script keeps each pinned commit in a folder of its own.
- Dependencies are declared with CPM in `engine/cmake/haylen-dependencies.cmake`, pinned with a SHA-256 hash to their latest release or, when a project has no releases, to its latest default-branch commit. Every dependency, tool and SDK of the engine, the templates and the CI stays at its latest version, and a newer release is adopted as soon as it exists.
- The package the engine shares with Varn, nlohmann/json, is declared before Varn, so Varn reuses it and the whole build resolves a single copy of it.
- A change to a dependency's source is a patch in `engine/cmake/patches/` that CPM applies, documented in `docs/tools/distribution.md` or `docs/tools/build.md` with the reason. The patch fixes the real problem and stays as small as possible. A patched package keys its source cache with `haylen_patched_package_key`, from the hash of its archive and the contents of its patches, so an edited patch reaches every checkout.
- When a dependency is updated, adopt its current API everywhere and drop patches it no longer needs. Do not keep code paths for the previous version.

## Mandatory formatting standard

- Preserve the visual, structural, and architectural style already present in the project.
- Keep code compact, professional, and consistent.
- Avoid excessive vertical whitespace.
- Use only the spacing required to separate reading contexts.
- Organize complex methods and functions into logical blocks that are easy to scan.
- Separate blocks with different responsibilities with one blank line.
- Do not visually glue multiple conditions, validations, loops, state mutations, and returns together.
- A function's flow must be understandable at a glance.
- Complex functions must have a visually clear beginning, middle, and end.
- Important blocks inside genuinely complex functions may have a short comment that explains intent.
- Comments explain context or intent. They do not restate the code.
- Do not add obvious, decorative, artificial, or redundant comments.
- Do not add artificial section comments such as helpers, validators, or public methods.
- Extract focused functions when one function is accumulating unrelated responsibilities.
- Do not extract functions only to reduce the visible line count.
- Avoid abstractions that make the main flow harder to understand.
- Code is written for the person who reads and debugs it later. Every important step is observable: intermediate results have descriptive names, calls are not chained into long lines, one line holds one responsibility, and closures do not nest.
- Prefer explicit code to hidden mechanisms. Behavior never hides in macros, reflection, operator overloads, implicit conversions or side effects of properties and hooks.
- Prefer the simple, conventional solution and concrete code. An interface, a template parameter or an extension point exists only for a need that is real today.
- Logic is never duplicated. What repeats goes into a helper class of its context, named after it, such as `TextHelper`.
- C++ uses the best of the standard of the project and no C idioms. Code that talks to a C library wraps its pointers and handles in C++ ownership types, such as `std::unique_ptr` with a deleter. Native code is C++, and C appears only in the C ABI that native libraries share, such as `HaylenNative.h`.
- Avoid unnecessary nesting.
- Prefer early returns when they simplify control flow.
- Do not use an unnecessary else after return.
- Keep includes direct, minimal, and ordered.
- Do not keep dead code, legacy code, generic fallbacks, or unexpected implicit behavior.
- Avoid macros, unsafe casts, and raw owning pointers when a safer project-consistent alternative exists.
- Use const, references, RAII, and smart pointers when they improve ownership and safety.
- Keep headers, implementation files, namespaces, types, names, and responsibilities consistent.
- The code must look like product code written by an experienced C++ engineer.
- Do not add comments in headers merely to describe methods, sections, or members.
- The build is warning-free on every platform with the warnings of `engine/cmake/haylen-warnings.cmake`. Those warnings apply to the targets of the engine alone, and the targets of a dependency that bring warning flags of their own build without warnings through `haylen_disable_warnings`, since only that dependency can act on them.
- The tool `clang-format` does not format project lambdas acceptably. Wrap non-trivial lambdas in `// clang-format off` and `// clang-format on` markers, and format the lambda manually. Multi-line Lua sources in tests get the same markers.
- Run `haylen engine format` before finishing a change. It applies `.clang-format` to every C, C++, Objective-C and Objective-C++ file of the engine, the samples and the templates, except the files of the plugin template whose names hold a token such as `{{NAME}}`, which become code only once `plugin new` replaces their tokens, lists multi-line lambdas that are missing their `clang-format off` and `on` markers, and formats the Python of `tools/` with Ruff. The command `haylen engine format --check` fails on any of these problems and on a lint problem of Ruff, and runs in CI.
- The Python of the tooling follows the same rules as the C++: one class per module, whose nested types belong to it alone, no free functions, since every function is a method and helpers are static methods, no module-level variables, which are class constants instead, empty `__init__.py` files, no `TYPE_CHECKING` and no `from __future__`, and no import cycles. Expected failures are the typed errors of `haylen.core.errors`, whose messages are complete sentences that say what is wrong and what to do, and the core layers never import a concrete backend. The tests `tools/tests/test_architecture.py` check these rules. The tooling runs with uv, which installs the Python of `.python-version` and the packages that `uv.lock` pins, and Ruff lints and formats it with the settings of `pyproject.toml`.

## Writing standard

These rules apply to every text the project writes: code comments, documentation, `README.md`, `PROJECT.md`, error, log and console messages, the output of `haylen` and the other tools, and the texts apps and samples show. Logs and messages to people are sentences with the ordinary case of a sentence. Commit messages are the one exception, all lowercase, as the working rules say.

- Every sentence starts with a capital letter. When a sentence would begin with a command, identifier, path, key or value written in lowercase, keep its exact spelling and put a capitalized word in front of it, such as "The command", "Run", "The function" or "The file".
- The same holds for every text that is not a full sentence: titles, button and menu texts, captions, hints, labels and each line of an on-screen readout start with a capital letter, such as `Name %s, %d coins`. Only code shown as code keeps its own form.
- Reserved expressions are always marked, so they never read as part of the prose: commands, code, identifiers, file names and paths, keys, option names and values. Markdown documents and code comments wrap them in backticks. Plain-text messages, logs and command output wrap them in double quotes, for example `Name the device with "--device". Use the command "xcrun devicectl list devices" to list them.`
- The terminal output of `haylen` is calm: short steps after a marker, reserved expressions in one soft color instead of quotes, URLs underlined because terminals open them, and paths bare with no style. It shows the steps and keeps the output of the tools it runs in the log of the command in `build/logs`, which only `--verbose` prints, while the log of a running app, the results of tests and benchmarks and other output the developer reads always print. Every listing and report, such as `devices`, `doctor`, `sdk list`, `plugin list`, `project inspect`, the results of benchmarks and of Device Farm and the summary of a running app, draws through the groups, tables, items and signs of `haylen.terminal.Terminal`, and no command formats them by hand. A group is a bold title with its count in dim after two spaces, set apart by a blank line. A table has a row of dim titles and columns aligned by the width of their text, an empty cell shows a dim dash, and on a terminal narrower than the table its columns that shrink give up room in their order, wrapping between words or cutting their middle, while an identifier to copy, such as the one that `--device` takes, never shrinks and moves to a line of its own under its row when the table does not fit. A sign in front of a state or a result tells it at a glance: a green filled dot for ready, booted or connected, a dim hollow dot for off or not yet built, a yellow cross for out of reach, a green check for what passed, which also starts every success, and a red cross for what failed. A table colors whole columns, such as identifiers in the soft color of reserved expressions, so its cells never carry quotes. Without color, the same structure, alignment and signs print as plain text, the signs become plain ASCII characters only where the encoding of the output lacks their symbols, and `--json` prints the result alone. A running app shows its summary under the title `Running`, with the app, the device and the configuration, and the keys that act on it under the title `Keys`, one per line, before its log. In its source, messages mark reserved expressions with double quotes and paths and URLs with backticks, and without color the output keeps the double quotes and drops the backticks.
- Every message of the tooling, in the terminal, the logs of commands, `--verbose` and the errors of `--json`, speaks to an app developer who never saw the code of the engine: it says what happened, to which thing and what to do, and holds no internals, such as paths into a JSON document, internal keys or class names, lists of what a validator expects or dumps. A problem of `haylen.json` or `plugin.json` names the file and the key as the person writes it, such as `window.orientation` or item 2 of `plugins`, and a problem of a file that the tooling writes, such as the manifest of an SDK or the record of a preparation, says that the output is outdated or damaged and names the command that builds it again, as `tools/tests/repository/test_message_paths.py` checks.
- Every message of the engine, its Lua bindings and the content tool speaks to the same developer, in the errors that reach Lua, the error screen, the log, the development console, the debugger and the reports of `haylen-content`: it says what happened, to which file, asset, key of `haylen.json` or `plugin.json`, Lua function or plugin, and what to do, and holds no names of classes, members, constants or enum values of the code, no wording of a library that the engine uses, such as the JSON reader or the standard library, and no offsets or dumps. A failure of the JSON reader names the file with the line and column of the mistake or the key it lacks, through `core::JsonValidator`, and a file of a binary format that a reader refuses, such as a shard or a manifest of a release, is damaged or was not made by this version of Haylen, with no field or offset. An image that does not decode names its file, a refused `.shader` package names its file and says to compile it again with `haylen app shaders`, and a call that breaks the contract of a GPU device, which only a bug of the engine or of a port makes, throws `gpu::ContractError`, whose message says that Haylen hit an internal error and asks the person to report it. The reason of such a failure is a typed value that tests check, such as `ShaderPackageError::Problem` or `ContractError::Rule`, and never part of the text, as the tests `EngineMessagesTest` of `tools/tests/repository/test_engine_messages.py` check in the texts of every throw, Lua error and log line of the engine and in the throws of the GPU devices.

## Comment standard

- Every comment is a complete sentence that starts with a capital letter and ends with a period, following the writing standard above.
- If a sentence needs to begin with a lowercase identifier, keep its exact spelling and rewrite the sentence so the identifier does not start it.
- A comment above a function, method, class, or module explains what callers need to know, not its internal implementation.
- Comments exist only where they are truly necessary, because well-named classes, methods and variables already make the code readable. Never comment what the code says, and never narrate a change or a request.
- Keep comments concise and natural.
- Do not split one sentence across multiple lines.
- Do not continue one sentence on the next line.
- End the current sentence with a period before starting another sentence on the next line.
- Do not join sentences with semicolons, in comments or in documentation.
- Avoid verbose, fragmented, or narrative comments.
- Code and comments are written in English.

## Tests

- Every engine capability has GoogleTest tests when the logic can run without a real graphics device or platform runtime. The headless host (the null GPU device, a mixer without a device, the scheduler of Varn) makes the renderer, UI, Lua bindings and the engine loop testable. The tests run as two programs: `haylen-tests`, the tests of the core in `engine/tests/`, which links no Lua and whose `test::EngineFixture` runs a real engine with a C++ application on an in-memory package, and `haylen-lua-tests`, the tests that run Lua in `engine/lua/tests/`, whose `test::LuaFixture` runs a Lua application, and `haylen test` builds both and runs every test of both once.
- Lua bindings are tested by running Lua through the headless engine and asserting on engine state, returned values, error messages and asynchronous results.
- Every fix comes with a regression test that fails without it.
- Tests verify behavior that matters. Do not write redundant tests, generated tests or tests that only restate the implementation.
- Test files follow the code rules: they live in the namespace of the context they test, hold one fixture class each with the types only it uses nested in it, keep helpers in fixtures or support classes of `engine/tests/support` and `engine/lua/tests/support`, and name suites after their subject with a `Test` suffix and tests after the behavior they verify. Every wait of a test has a bound and fails the test when it runs out, every optional or pointer that may be empty is asserted before a test reads through it, and setup that fails fails the test, such as the files that `test::TestFiles` reads and writes.
- Test data lives in `engine/tests/data/`, so engine tests never read files of the samples.
- Both test programs replace the global allocation functions for `test::AllocationTracker`, so tests show that an operation never allocates a whole file or package.
- Behavior that only a person sees on a device, such as windows that resize, the system UI, the prompts of permissions, notifications, gestures, the back button and the remote, is covered by UI tests, which `haylen test --ui <app>` runs from the `ui-tests/` folder of the app on the Apple simulators and devices, the Android emulator and devices, and the phones of AWS Device Farm with `--device-farm`. A UI test opens what it checks through the launch arguments of the app, as the test project opens a test with `--test <code>`, and reads its results through the accessibility tree.
- Run `haylen test`. Changes to threading, lifetimes or memory handling also pass `haylen test --sanitizers thread` and `--sanitizers address`.
- Every platform, GPU and device runs its tests from the command line, without continuous integration, as `docs/tools/hardware-testing.md` explains: machines at hand, simulators, emulators, real devices, and GPUs and phones rented on Amazon Web Services and Microsoft Azure. Rented machines run only after every binary is built, in one batch, with a shutdown timer, and everything they created is deleted and checked right after. Credentials stay in environment variables and never reach a file, a log or the repository.
- The tooling and the rules of the repository that need no build are tested with pytest from `tools/tests`, by classes named `<Subject>Test` with the doubles of `tools/tests/support`, with `uv run pytest`, which CI runs. The tests prove the extension points with a fake backend and a fake engine port that the registry matches by what they describe, the backends with recorded native tools, and the rules of the repository in `tools/tests/repository`.
- Engine coverage is kept as close to 100 percent as the code allows. Run `haylen engine coverage`.

- The tests `DocsTest` of `tools/tests/repository/test_docs.py` check the tree, the tables of the indexes, that every row of a table has as many cells as its header, the titles, that no section heading carries an emoji, the code blocks, the paragraphs, every relative link and its heading, and that no long sentence of a guide repeats in another page.
