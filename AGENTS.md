# 🧭 Haylen — project guide

Haylen is a reusable engine for games, multimedia apps and applications. It is 2D and organized so that 3D can grow next to it without renaming anything. Its core is C++20, and its whole API is exported to Lua through [Varn](https://github.com/varn-org/varn). Lua is the primary way to write apps, and every capability stays fully usable from C++. The repository holds the engine, the platform templates, the tools and the sample apps.

This file is binding for every change. It describes the project as it is and the rules every feature and fix follows, so read it before working and follow it exactly instead of re-deriving conventions. When a rule or a design decision changes, update this file in the same change and describe the new state in the present tense. `PROJECT.md` holds the master plan, the owner's requests, the decisions and the feature checklist.

## Core principles

- No shortcuts, hacks, kludges, ad hoc workarounds, silent fallbacks, dead or obsolete code, legacy compatibility paths, backward-compatibility shims, or speculative abstractions. Fix root causes instead of masking symptoms. Implement the intended design directly, using the simplest correct, robust, and maintainable solution. Remove superseded implementations rather than preserving parallel code paths. Introduce abstractions only when justified by concrete requirements. Handle errors explicitly, never conceal failures, and never sacrifice correctness or architectural integrity for convenience.
- The engine respects the limits of every system it runs on. It never tries to get around a restriction, a permission or a policy of a platform, never guesses what the system decides on its own, and never piles up attempts to beat it. A limit is handled as what it is, through the APIs the platform offers for it: an explicit error or exception with a clear message, a documented requirement, or a documented gap.
- Replace or refactor code that no longer fits instead of carrying it forward, whatever the size of the change. There are no aliases for old names and no checks for how something used to work.
- Only change what makes sense to change. Do not add code, tests, comments or files just to show work, and do not guard against situations that cannot happen.
- Every change is finished only when it is implemented, exported to Lua, tested and documented.
- Performance matters everywhere. Hot paths avoid allocations and per-item calls across the Lua boundary, and heavy work leaves the frame thread. A frame that draws what the frame before it drew allocates nothing in the renderer, the text system or the UI, and the engine tests check it with `test::AllocationTracker`.
- The engine holds general capabilities. The mechanics of a particular game belong in apps and samples, never in the engine.
- The engine holds only what every app needs to run: windows, displays and outputs, rendering, keyboard, mouse, touch, gamepad and TV remote input, text input with the system keyboard and the clipboard, audio output with its session, video, files, storage, the network, the lifecycle, locale, theme, battery and system information, the safe area, accessibility, the mechanisms of plugins and the development tools. Every optional capability of the device or the system, such as location, camera, microphone, bluetooth, notifications, vibration, native dialogs and pickers, links and sharing, lives in a plugin, which owns its permission through the permission contract.
- This repository holds only what is general to the engine. Anything specific, such as the native plugins of system capabilities and third-party SDKs, the runner or the shader compiler, lives in a sibling repository and changes there, so nothing in this repository has to change with it and nothing here names it beyond the description of the sibling repositories.
- Code, comments and repository documentation are written in English. `PROJECT.md` is the exception and is written in Portuguese for the project owner.
- Never mention other engines or their tools anywhere in the repository: not in code, comments, docs, test names, commit messages or the project plan, and not even as a comparison or an inspiration. Describe what Haylen does in its own terms.
- Never mention third-party games, apps, companies, studios or artists, and never use images made by others for the samples. A sample may take the idea of something that exists, never its name, its art or its exact look, and the art of the repository is made for it. Sounds of the samples are made for the project or released into the public domain (CC0), so no credit names their authors. Fonts come from open licenses, and their license file, which the license requires, is the only third-party credit the repository keeps. The platforms, systems and stores that apps run on and ship to, such as Steam, the App Store and Google Play, are named where the engine targets them.
- The repository never records its own history. Code, comments, docs, `README.md`, `PROJECT.md` and this file describe what exists now, without earlier names, earlier designs, what something was renamed from or dated change notes. Git holds the history.
- This file cites a version or a number only when a rule depends on it, such as the C++ standard of the code or the coverage the tests aim for. Secondary values that change often stay out of it: the versions of libraries, tools, SDKs and of the engine itself, and the limits, sizes, counts and durations the code declares. For those it names the kind of bound a rule keeps, such as "a bounded queue", and points to the file that holds the value, such as `engine/VERSION`, `engine/cmake/haylen-dependencies.cmake`, the templates and the CI workflow.

## Working rules

- Every request of the owner goes into the checklist of `PROJECT.md` before the work starts, so nothing is lost, and an item is checked only when it is implemented, tested where possible and documented.
- The engine comes first. Its base, the core, the Lua bindings, rendering, text, the UI, input, audio, assets and content packaging, and the platform hosts, is finished, tested and verified on every platform before work on samples goes on, and samples come second. A sample never hides a flaw of the engine: the flaw is fixed in the engine first.
- Commit and push to `main` after each finished block of work, once the build, the tests and the format check pass. A block that is committed builds and passes its tests on its own, so separate unrelated changes into separate commits and verify a commit from a clean checkout when the working tree holds other work.
- CI only tests and publishes nothing, and the GitHub release of the repository is the source archive alone, because developers build the engine themselves. The jobs of one run hand the engine artifacts that one of them built to the others as artifacts of the run, which nothing outside the run reads and which leave after a day, so no build repeats within a run.
- Every job of CI that builds starts from the action `.github/actions/build-environment`, which restores the dependency sources, the tools that the builds download (the shader compiler, XcodeGen, the Emscripten SDK with its ports and ccache on Windows) and, for the jobs that compile the most, the compiler cache, under keys that change with everything they depend on, so a run compiles only what changed, downloads only what a new pin names and no cache hides a failure. One job of each cache of the sources and the tools saves it in the runs of the default branch once the job succeeds with a new key, deleting the copies of earlier keys, while every other job reads it. A job that keeps a compiler cache ends with the action `.github/actions/compiler-cache`, which in the runs of the default branch keeps only the objects that the run used, saves the cache and deletes the copies that earlier runs saved, while other branches and pull requests read the caches of the default branch, so one build of every job fits in the cache storage of the repository, as `docs/tools/testing.md` describes. To keep one build of every job within that storage, the Debug trees of CI compile with `HAYLEN_DEBUG_INFO` set to `LINES`, which keeps only the file and line of each instruction.
- Haylen is free for personal and commercial work, forever, under the MIT License of `LICENSE`, and every contribution, whether code, art, sounds or any other content, becomes part of it under the same license, as `CONTRIBUTING.md` states. Nothing in the repository adds a fee, a royalty, a revenue share or a paid tier.
- A commit message is one short lowercase sentence after a type prefix, `feature: ...`, `fix: ...`, `refactor: ...`, `perf: ...`, `test: ...`, `docs: ...`, `build: ...` or `chore: ...`, for example `feature: add scene loading lifecycle`. It has no body, no co-author and no other trailer, and never names Claude or anyone else.
- Before every commit, review what is staged (`git status` and `git diff --cached --stat`) and make sure nothing private or temporary goes in: build outputs, caches, generated projects under `build/`, local tool folders, logs, screenshots, secrets, API keys, tokens, signing keys and keystores, `local.properties`, `.env` files, machine-specific paths or settings, and personal data. Anything like that belongs in `.gitignore`, never in the repository.
- Screenshots used to check a change capture only the app window or the page, never the whole screen.
- Automated checks run emulators and simulators without a window, shut them down afterwards and never send input to a device or window that a person may be using. They use only the simulators and the emulator that already exist on the machine, never create or delete one, and uninstall every app they install when the check ends.
- Features that touch rendering, input, audio, text input, windows or platform code are run on the platforms they affect (desktop player, iOS and tvOS simulators, Mac Catalyst, Android emulator, browser), and a sample shows each of them working.
- A change to rendering, textures, shaders, the UI or text is compared before and after on the test categories it affects, in captures that are looked at closely, and a visual change that nobody asked for is a regression fixed before the change lands. Every visual defect that anyone sees, such as blur, smear, distortion, aliasing, seams or wrong colors, is fixed at its root at once.
- Simulators, emulators and the browser carry the checks. A physical device runs only what they cannot show, such as hardware they lack or limit, real performance, signing and store delivery, or behavior that needs the attention of a person, and it never repeats a check that already passed on a simulator or an emulator.

## What the engine is

- **Library first.** The folder `engine/` is a standalone CMake project that other projects consume with `add_subdirectory`, CPM or `find_package(haylen)`. It exports the `haylen::engine` library, the `haylen::runtime` host library and the `haylen_add_app` CMake function.
- **Layered architecture.** The engine stands on three layers. The platform layer opens the window, runs the frames, reads the input and holds the entry points: the layer of SDL3 in `engine/src/platform/sdl/` on macOS, Windows, Linux, iOS, iPadOS, Mac Catalyst, tvOS and the web, and the native runtime of `engine/src/platform/android/` on Android. Each one implements a host derived from `platform::NativeHost`, which adds what its window does to the services of the platform, and a `platform::NativeWindow`, which hands the services the native handles of its window, and it calls `platform::Player` as the window opens, draws its frames, receives its events and closes. The render hardware interface is `gpu::Device` of `engine/include/haylen/gpu/Device.hpp`, with one device per graphics API in `engine/src/gpu/<api>/` that `gpu::DeviceFactory` makes, and the platform layer opens its window for the first API of the order of the app that starts on the machine, so a build carries every device of its platform and chooses at run time. The renderers draw through that interface alone, through `graphics::Device`, which owns the device and makes textures, render targets and readbacks for them: `graphics2d::Renderer` in `engine/src/2d/graphics/` today, and a 3D renderer next to it in its own `3d` folder. The player, the services of each platform folder, the engine and the Lua API stay the same on every platform and graphics API. The file `docs/graphics/rhi.md` describes the contract, the capabilities of each API and the status of every device on every platform.
- **Ports.** A platform whose SDK comes under a license that keeps its code private, such as a game console, joins the engine through a port: a folder outside the repository that the cache path `HAYLEN_PORT_DIR` names, whose `port.cmake` describes it with `haylen_port`. It brings the runtime, host, window and services of its platform and, for a graphics API the engine has no device of, the device of the reserved API `gpu::Device::Api::Port` with the reserved shader language `Language::Port`, whose code its shader command writes into the `port` target of each shader package. The repository holds only the mechanism, the test port of `engine/tests/data/port`, which `haylen test --port` builds and plays on a desktop, and `docs/platform/ports.md`, and never holds code or facts that an SDK license covers.
- **Lua through Varn.** The engine links Varn's C++ core (`varn-core`), which stays an implementation detail: no line of the log names Varn, the log of the platform is named `haylen` through `varn::log::Log::setName`, and every record is its time, its level and its message. One `varn::runtime::Runtime` owns the Lua state, the event loop and the worker pools. Engine modules are installed into that Lua state through `Runtime::addModule`, which puts them in `package.preload` next to Varn's own modules (`async`, `http`, `socket`, `json`, `fs`, `zip`, `crypto`, `log`, `platform`, `process`, `datetime`, `xml`, `dataview`, `ffi`). Memory that the app and native code share without a copy is the data view of Varn, and the engine reuses it instead of a pointer type of its own: `varn::dataview::DataView` in the `views` of `platform::Bridge::Payload`, `varn_dataview` in `HaylenNativeApi`, `VarnDataView` on Apple platforms, Android and the web, and the `dataview` module in Lua, so the headers of Varn's data view, `varn/varn.h` and the JavaScript class of `src/wasm/varn-dataview.js` reach apps through the SDK and the artifacts. The JSON names a view with Varn's token, every boundary of the bridge takes its own reference before it returns, and the views of a call belong to it until its handler answers.
- **Everything in C++ is exported to Lua.** Every public C++ capability has a Lua binding in the same change, with Lua tests and a reference page under `docs/lua-api/`. This is a rule, not a goal. The one exception is the bootstrap of protected releases in `haylen/content/` (`Bootstrap`, `KeyProvider` and `EmbeddedKeyProvider`), which handles content keys, and keys never reach Lua.
- **App packages.** The runtime runs an app package, which is either a folder or a `.zip` file containing `app.json`, the Lua modules under `source/` and the assets under `content/`. Nothing else in the folder belongs to the package, so platform projects, notes and build files can sit next to it. The file `app.json` configures the identity, window, design resolution, orientation, splash screen, lifecycle, audio session, debug options, content delivery and updates, autoloads and native libraries before any Lua runs, and unknown keys and invalid values are errors with clear messages. Its `version` is the version that people see, and its `build`, a whole number that grows with every upload and is 1 when it is missing, is the one source of every build number: `CFBundleVersion` on Apple platforms, `versionCode` on Android, the last number of the Windows version resource and the app build of protected releases and their content updates, so nothing derives a build number from the version. The file `source/main.lua` is the entry point. Every package reads its files in ranges through `io::PackageReader`, so files of any size stream in bounded memory, and a whole read refuses a file larger than `Package::kMaxReadSize`, as a range read refuses a longer range. A zip package stays on disk and reads each entry when it is asked for. The command `haylen.py new` gives an app its `.gitignore`, `.editorconfig` and `.clang-format`, which are not part of the package, and the package of a C++ app is the folder of its CMake project.
- **Asset paths.** Every asset path passed to the engine is relative to the package `content/` folder and never includes the `content/` prefix. The function `require("scenes.menu")` resolves Lua modules from the `source/` folder, so it loads `source/scenes/menu.lua`.
- **Prebuilt engine.** Lua apps never compile the engine. The command `haylen.py engine` builds it once into prebuilt artifacts under `build/artifacts/` (`Haylen.xcframework` with `haylen-frameworks.json`, the engine's `PrivacyInfo.xcprivacy` and its Swift helpers `HaylenBridgeAsync.swift`, the `haylen` AAR with the `haylen-plugins`, `haylen-links`, `haylen-playback` and `haylen-coroutines` libraries in a local Maven repository and the SDK of each Android ABI, the web player, which draws through WebGPU or WebGL2, and the desktop player with the content tool `haylen-content` and the SDK of this machine). The command `haylen.py run` builds the artifacts it needs when they are older than the engine sources, and on Apple platforms only the slices of `Haylen.xcframework` of the device and the simulator of the family it runs on, which the manifest of the artifacts records slice by slice, with the framework holding only the slices of the current sources and signed ad hoc, while `engine`, `prepare` and `platform xcodegen` build every slice. C++ apps compile the engine through CMake, where `haylen_add_app` deploys the package into the app of each platform.
- **Platform projects belong to the developer.** The folder `platform/<template>/` of the app is the whole project of that platform, which `haylen.py` builds in place, and an app without it uses a copy of the template that `haylen.py` keeps under `build/apps/<app>-<hash>/<template>/`. The script `haylen.py` writes only the gitignored folder `haylen/` inside a project, which the files of the developer include through a few visible lines (`include: [haylen/project.yml]` with `templates: [HaylenIOS]` and the other target templates, `#include "haylen/Haylen.xcconfig"`, `haylen/haylen.properties` with `haylen/assets`, `haylen/res`, `haylen/jniLibs` and `haylen/plugins` on Android, and `include(haylen/haylen.cmake)` with `haylen_app(app)` in the CMake projects of Windows and Linux), and never edits `project.yml`, `project.pbxproj`, Gradle scripts, CMake scripts, manifests, resource scripts, desktop entries, `Info.plist` or entitlements. The target templates bring the engine itself, so a target that leaves them out links the engine on its own. The command `haylen.py prepare` writes that folder, `haylen.py platform xcodegen` generates `App.xcodeproj` again, `haylen.py check` validates a built app against the requirements of the engine and its plugins, and `haylen.py platform add` and `platform diff` create a project from a template and compare it with the current one. The guide `docs/tools/upgrading.md` says how a person or an AI assistant brings an older app, its platform projects and its plugins up to the current templates, and it changes in the same change as any template.
- **Content tool and keys.** The tool `haylen-content`, which `engine/tools/content/` builds from the format library of the engine and its writing side `haylen-content-writer`, which apps never link, builds, verifies, inspects, compares and publishes protected releases, writes the bootstrap that a release build compiles in, and `haylen.py content` runs it. A release build of an app compiles its own bootstrap, with the identity of the app, its public signing key and its content keys sealed so the binary never holds a key in plain form, and the runtime opens the release that ships with the app with it, so no key is shared between apps and no key sits in a resource, a manifest or `app.json`. The keys of each app live in its key folder under the configuration folder of the user, or under the folder that `HAYLEN_KEYS_DIR` names in continuous integration, which never creates keys, and never in a repository, a project or a build folder. No tool prints a key, only key IDs and public keys.
- **Release builds.** The Release configuration of `haylen.py run` and `prepare` ships the package of an app only as its protected release, with the Lua modules as bytecode, and a binary of the app that compiles in its bootstrap: the executable of the Windows or Linux project, linked against the SDK of the desktop artifacts, the app of the Apple project, whose target templates compile `haylen/HaylenBootstrap.cpp`, on Android a library of the app, `haylen-app`, linked against the SDK of each ABI in the Android artifacts, which the activity loads instead of the Lua player, with a release too large for the base module of Google Play in install-time asset packs that the project includes from `haylen/asset-packs`, and on the web a runtime of the app, whose page downloads only the manifests and the app domain and streams the content by range into the content store of the browser. The release binaries that haylen.py links ship without symbols, which stay in symbol files of the build folder for crash reports, and Release builds of the engine and its SDK compile with link-time optimization, so the link of each app optimizes it as one program, except the SDK of Windows, whose one library would outgrow what a library of Windows holds. C++ apps ship the same release with the same bootstrap through `haylen_add_app` with `HAYLEN_PROTECTED_RELEASE`, which `run --config Release` turns on, and `haylen.py distribution steam` lays a desktop release out as Steam depots. The command `run` inspects every release build and stops before it launches when the app holds Lua text, a file of the package as it is, symbol files or a key in any form, and `check --config Release` fails on the same, as the `release` job of CI does. The Debug configuration ships the package as it is.
- **The command haylen.** The commands of `haylen.py` name what they do with the words that app developers know: `new`, `run`, `devices`, `capture`, `prepare`, `check`, `package`, `shaders` and `serve` for apps, the groups `platform`, `plugin`, `content` and `distribution` whose actions act on one subject, and the commands of the engine, `engine`, `tools`, `configure`, `build`, `test`, `bench`, `fuzz`, `coverage`, `format`, `sdk` and `clean`. A command that serves one company, store or tool, such as Steam, is an action of the group of what it does, such as `distribution steam`, and never a command of its own. One command serves both kinds of apps where they do the same thing, such as `run`, which builds a C++ app with its CMake project. The command `devices` lists the identifiers that `--device` takes, and every error about a device points to it.
- **The player.** The command `haylen --dev <folder|zip>` runs any app package on desktop with hot reload, which reloads changed Lua modules in place with the state of the app and restarts the app only when a change cannot apply in place. Only `--dev` turns on development behavior, watching the package folder, or `--dev-server`, which connects to the development server that pushes saved files instead, and on the web the page field `Module.haylen.development`, which the template sets only for the page that `haylen.py run --platform web` serves, so apps built from the templates, shipped apps and sites that `prepare` makes never run in development mode. An app that another app launches with the address of a development server in the option `developmentServer` of `haylen.launch` plays in development with a session of its own, while the app that launched it keeps its own session, or none, for its return, such as an app that downloads the package that `haylen.py serve <app>` serves on the local network with its development server. A launched app always leaves through the hold of `platform::ReturnHold`, Escape, play and pause of a TV remote, the back button of Android or of a gamepad, or three still fingers held for a moment, which the app hears as plain input and cannot take, and the release that ends the hold never reaches the app that starts again. The links that open the process belong to the app that the process installed, so a link that arrives while a launched app plays ends every launched app, and the first app hears it as `linkOpened` once it starts again, which on the web is a link that the page or the web module of a plugin hands over with `openLink`, since the page is the link that opened it. A launch with `nativeAccess` set to `false` plays the app and every app it launches without the `ffi`, `process` and `haylen.native` modules and the functions `io.popen` and `os.execute`, so an app that comes from an address reaches the system only through the engine and the plugins of the process. The command `haylen.py run` hands `--dev-server` to the player of this machine and, in the Debug configuration, to apps on simulators, devices and the Android emulator as a launch argument, or an intent extra that only a debuggable Android app reads, and an app with a release bootstrap ignores it. Development lives in the `platform::DevelopmentSession` of the host, which outlives every app that restarts under it, and nothing of hot reload or of the Lua debugger, such as the module graph that replaces `require` and the hooks of Lua, exists without it.
- **The debugger.** The Lua debugger of `engine/src/debug/` belongs to the development session, so its breakpoints outlive reloads and restarts of the app. Editors attach to it with the Debug Adapter Protocol on a port of `haylen.py run`, `--debugger-port`, and the development server carries its messages to the app through the development connection, on every platform. It offers breakpoints with conditions, counts of hits and log messages, pauses, steps that follow a coroutine across the `await` of the async library, halts on errors that no protected call of the app catches before their stack unwinds, the stack with its scopes and values, and evaluations. Coroutines have no hook while nothing is watched, and watched ones report lines only in the functions whose lines hold a breakpoint or while a step needs them. Looking at values reads them raw and holds the collector, so it never runs code of the app, and the only code the debugger runs is what the person writes, evaluations, conditions and log messages, on a coroutine of its own with a time bound. A web page cannot halt, so it keeps only the log points.
- **The developer tools.** In development, the terminal of `haylen.py run` reaches every running app on every platform: its keys reload, restart, open the developer console, show the statistics, the inspector and the debug drawings of the app and capture a frame of its GPU, and the console is a line at the bottom of the terminal, completed from the commands that the app sends, which the log of the app never mixes with. The app draws the statistics window and the inspector as windows of `debug::DebugWindow`, which stay inside the safe area, move by their title bar and scroll under a finger, and it has no console window of its own.
- **Plugins.** Every subsystem is a plugin: a self-contained unit with a name, a uniform lifecycle (`start`, `installLua`, `event`, `beginFrame`, `fixedUpdate`, `update`, `render`, `renderUi`, `renderOverlay`, `endFrame`, `packageChanged`, `stop`, `isCapturingBack` for the back button and `isFrameComplete` for the first frame that shows the app) and its own Lua module installation. Built-in subsystems use exactly the same plugin interface that other projects use to extend the engine, and plugins never reach into each other's internals.
- **Native access.** Apps reach anything native through native plugins, which package a Lua API with its Swift or Objective-C, Kotlin or Java, JavaScript and C or C++ implementations and their SDK dependencies. Underneath, plugins talk through the asynchronous platform bridge, whose JSON calls native handlers answer with typed errors, timeouts and cancellation. Apps can also call native libraries from Lua through `haylen.native` and Varn's `ffi` (for example the flat C APIs of game platform and online services SDKs), and apps that compile the engine add C++ engine plugins. Answers and native callbacks always reach Lua on the frame thread. The engine library never bundles or calls a third-party SDK itself, because SDKs such as those of ads or analytics live in native plugins.
- **Every kind of desktop app.** Besides normal windows, the engine supports frameless, transparent, always-on-top and click-through windows that apps move themselves, for apps that live on the desktop or above the taskbar, and every mode can change while the app runs. macOS apps are regular apps with the standard main menu, and every request to quit, from the menu, Command+Q, the Dock or the system, closes the window through the engine as its close button does.
- **Errors never stop the runtime.** An error in app code shows the error screen with the message, the file and line, the source around it and the Lua stack, which the user can scroll, copy and restart from. The web page receives the same error, and hot reload restarts the app from the error screen.
- **Sibling repositories.** Three repositories of https://github.com/haylen-org sit next to this one and follow the same rules, each with its own `README.md` in the pattern of this one and its own `AGENTS.md`: `haylen-shader-compiler`, the Haylen shader compiler that the engine pins, `haylen-runner`, Haylen Runner, a Lua app of Haylen that runs other Haylen apps from an address, a QR code or a link, which anyone builds and installs on their own devices, and `haylen-plugins` (https://github.com/haylen-org/haylen-plugins), the native plugins of system capabilities and third-party SDKs, one folder each, which apps take with `git` and `path`. The runner and the plugins each keep exactly one commit on `main`, which every change amends and force-pushes, with no tag and no release. They use only the documented Lua API, the plugin architecture and the general capabilities of the engine, so a flaw they show is fixed in the engine, and nothing else of this repository names them.
- **Web editor ready.** A future website edits Lua code and assets in the browser and runs the app with the WebAssembly runtime (WebGPU or WebGL2). The web runtime therefore loads packages supplied at runtime (a zip or a set of files in memory), edits the package that plays under an overlay, restarts an app without reloading the page, reloads changed scripts and assets in place in development, forwards logs, statistics and errors with Lua stack traces to JavaScript, and shows the error screen instead of stopping when a script fails. The website itself lives in another repository.

## Platforms

- The engine runs on macOS, Windows, Linux, iOS and iPadOS, Mac Catalyst, tvOS, visionOS, Android (phones, tablets and Android TV from one APK) and the web (WebGPU with WebGL2 as the alternative where WebGPU does not start). Scripts see Mac Catalyst and visionOS apps as iOS apps, and watchOS is not possible because its SDK lacks the graphics, input and audio frameworks the engine needs. The file `docs/tools/distribution.md` records the support table and the minimum versions.
- Minimum operating system versions are as low as the toolchain and the dependencies allow, and each limit is explained in `docs/tools/distribution.md`.
- Every feature works on every platform, or the docs say exactly where it does not and why. Input covers mouse, touch, keyboard, gamepads with their motion sensors and touchpads, whose sensors stay off until a request of the app wants them and stop while the app is in the background, and TV remotes, and text input uses the native text field of each platform so input methods, composition and on-screen keyboards work everywhere.
- The text input of the system is on only while a field edits or the plain keyboard of `window.setKeyboardVisible` is open, so keys pressed in play never open the accent menu of macOS or a composition window, and only one text input of a platform reads each key: the native field on macOS, iOS, Android and the web, where the runtime never starts the text input of SDL, and the text input of SDL on Windows and Linux.
- The native text field that edits a field of the UI stays hidden on every platform, never transparent, so the system draws none of its caret, selection, autocorrection bubbles or predictions, and it never predicts, completes or rewrites text, which the user would not see. Autocorrection is off unless a field asks for it with `autocorrect`, and then only the on-screen keyboard offers it. A finger edits a field only once it taps it, a field that the accept of a keyboard, a gamepad or a remote opens reaches the platform once the press ends, so the release never types into the keyboard of the system, such as on the Apple TV, a drag that starts on a field scrolls the area around it, and the GUIs hold their place under the keyboard while a press is down, so a press that closes the keyboard lands on what it pressed.
- The languages the person prefers come from the API of each platform, `NSLocale.preferredLanguages` on Apple platforms, the locales of the configuration on Android, `navigator.languages` on the web, `GetUserPreferredUILanguages` on Windows and the variables of gettext on Linux, and reach `platform::System` through `SystemState`, which keeps every tag once in the canonical form of BCP 47 that `localization::LanguageTag` writes, such as `pt-BR` for `pt_br`. The engine publishes `systemLanguagesChanged` when the list changes while the app runs, the current language of `localization::Catalog` follows the list until the app picks one, in the order of matching of `docs/core/localization.md`, and `languageChanged` tells of every change of it. The section `localization` of `app.json` loads the folder of the languages before any Lua runs.
- Displays are known by ids that stay the same while a display stays connected, never by their place in the list, and `platform::Displays` publishes each display that connects, disconnects or changes. The app runs in one window with one engine and one Lua state, and it shows more on other displays through outputs of `platform::Outputs`: each one a render target that the app draws into and that the engine presents into another swapchain of the same `gpu::Device` at the end of the frame, on the frame thread. Every GPU device draws into several surfaces, OpenGL and OpenGL ES through other drawables of the one context of the window, so one set of objects serves every output. From iOS 27, UIKit connects the scene of an external display only for an app that registers the scene accessory of external displays, which `system.requestPermission('screens')` does, and a browser opens the window of an output only shortly after a gesture of the person. The file `docs/platform/displays.md` records where outputs work and why they do not elsewhere.
- An app caps the framebuffer pixels in each point of its window with `window.maxPixelDensity`, and on a denser display the drawable shrinks to the cap while every size in points and design units stays the same. The platform hands the GPU device the drawable and its window in `gpu::Surface::Size`, the system stretches the drawable where it can, as the `CAMetalLayer`, the swapchain of DXGI and the native window of Android do, and the devices of Vulkan, OpenGL and WebGPU scale it into a window whose size the system fixes, as `docs/graphics/rendering.md` describes.
- The `Info.plist` of iPhones and iPads lists every orientation, and the runtime allows the orientations of `app.json`, since a foldable iPhone shows an app that lists fewer in a box on its inner screen.
- Mobile apps follow the platform lifecycle: app states (`active`, `inactive`, `background`), audio sessions and interruptions, low-memory warnings with their level and orientation. Every moment of the system, the app and its screen that a platform reports reaches the app as an event of the one lifecycle vocabulary of `core::LifecycleEvent` with a state it reads, such as `powerSavingChanged` with `system.powerSaving()` and `timeZoneChanged` with `system.timeZone()`, and `docs/core/lifecycle.md` lists the source of each event on every platform. Every link that opens the app reaches it as `linkOpened` through `platform::LinkRelay`, on every platform but the web, whose page is the link that opened it, besides the native parts of the plugins that declare it. An app that declares `audio.background` in `app.json` keeps its output running in the background while a voice plays, while the rest of the app halts as its lifecycle options decide: the tools add the mode `audio` of `UIBackgroundModes` on Apple platforms and the library `haylen-playback` with its foreground service on Android, UIKit runs the frames from a timer there, and the media notification keeps an Android app in the foreground while what plays shows as playing. UI positions itself in the safe area the engine reports. An app whose `orientation` is `any` turns its design with the screen, so a rotation keeps the size of its design units and the UI lays out again like a native app. The status bar stays hidden unless `window.statusBar` of `app.json` or the app shows it with `auto`, `light` or `dark` content, the Info.plist and the Android manifest launch the app with that value, and the engine paints `statusBarColor` behind it, since the app draws under it. The system gestures at the edges of the screen follow `window.systemGestures`, which defers them to a second swipe unless the app lets them act at once or hides the home indicator until a touch, through the root view controller on iPhones and iPads and through the navigation bar and the gesture exclusion of `HaylenActivity` on Android, within the height of each side edge that Android lets an app keep. Foldable and dual-screen devices report their fold, posture and screen areas, through Jetpack WindowManager on Android, the division region and the hinge of UIKit on the foldable iPhone and the viewport segments of the browser on the web, and `debug.fold` of `app.json` simulates them on any screen. The cutouts of the screen, such as a notch, a dynamic island or the hole of a camera, reach `viewport.cutouts` where the platform reports their shapes, through the occluded regions of UIKit on iPhones, the display cutout of Android and the camera housing of notched Macs, and the device presets of the safe area simulation bring theirs.
- The Apple template is an XcodeGen `project.yml` that includes `haylen/project.yml`, with the generated `App.xcodeproj` always committed next to it. After editing the `project.yml` of the template, run `haylen platform xcodegen --template` and commit both. The completed `Info.plist`, entitlements and privacy manifest follow one rule: the value of the developer wins, the keys of plugins and `app.json` only fill what is missing, arrays gain the items they lack, and two plugins that disagree stop the build.
- Android apps run in `dev.haylen.HaylenActivity`, a GameActivity of AndroidX (an `AppCompatActivity`, so also a `FragmentActivity` and a `ComponentActivity`) that draws the app into a `SurfaceView`. The native runtime of `engine/src/platform/android/` runs GameActivity through its callbacks, with the frames on a thread of its own, and draws through Vulkan or, where Vulkan does not start, through OpenGL ES, whose EGL context asks for the newest version the device declares and lasts while the activity lives. Plugins therefore use the Activity Result API with stable keys, fragments and Compose, and native views are normal views above the game. The activity launches as `singleTop`, and links and notification taps enter through `HaylenLinkActivity`, which only the `haylen-links` library declares, so the launcher icon never destroys a screen opened above the game and an app without link or notification plugins exports nothing besides its launcher. The activity registers the Activity Result launchers of the engine under keys that start with `haylen.`, `haylen.permissions` for the permissions and `haylen.<id>.<screen>` for the screens of plugins, and keeps the screen that shows in its saved state, so a result that arrives after the end of the process reaches the next app as `screenRestored`.
- The Windows and Linux templates are CMake projects that include `haylen/haylen.cmake`, whose `haylen_app` builds the executable of the app from the Lua player, the bootstrap and the SDK of the desktop artifacts in the Debug and Release configurations, and `haylen.py` installs the app into `build/apps/<app>-<hash>/installed/<platform>/`. The Windows project embeds the icon, the version resource with the values of `app.json` and the application manifest, signs release builds with `signtool` and the certificate that the environment names, and stays unsigned with a note without one. The Linux project installs the executable with a `RUNPATH` of `$ORIGIN` and `$ORIGIN/lib`, and the desktop entry, the AppStream metainfo and the hicolor icons named after the identifier, which is also the class of the window, and `haylen.py` completes the desktop entry and the metainfo of the developer with the values of `app.json`. Windows and Linux start a new process of the app for every link of a URL scheme, with the link after `--link`, which hands the link to the instance that runs, through a named pipe of the session on Windows and the method `Open` of `org.freedesktop.Application` on the session bus on Linux, and the installer of Windows and the desktop entry of Linux register the schemes that the plugins declare, which `haylen.py run` also registers for the installed app of the build folder. The command `haylen.py distribution installer` makes the installers through CPack: the Inno Setup installer of Windows, and the `.deb` and the AppImage of Linux. Desktop apps reach native code through the native libraries of the `native` section of `app.json`.
- The templates of apps are layers: `templates/common` holds what Lua and C++ apps share, and `templates/lua` and `templates/cpp` what only their kind has. The command `haylen.py new` with `--kind lua` or `--kind cpp`, `platform add`, `platform diff` and the copies of `build/apps` take the common layer first and then the layer of the kind, whose file replaces a common file of the same path, and no file repeats between the layers. A folder with `CMakeLists.txt` is a C++ app. A platform template is a folder under `platform/` of a layer, and a new platform is such a folder and its run target in `haylen.py`. Both templates ship a working example of the bridge, the method `app.greet` and the event `app.greeted`, which Lua or C++ calls and native code answers in Swift or Objective-C, Kotlin, JavaScript, and C++ on Windows and Linux.
- The Android template is a Gradle app without C++ that depends on the haylen AAR and reads `haylen/haylen.properties`, and its modules find the engine version in the extra property `haylenEngineVersion`. Every template has the place where the native code of the app registers its bridge handlers and sends its events: `source/main.m` of the Apple template, `src/AppBridge.mm` of the C++ template, the application class `App` of the Android template and `app.js` of the web. Release builds sign with the upload key that `haylen.py distribution android-key` writes into `platform/android/keystore/`, or with the key that CI gives through Gradle properties or environment variables, and stop with a clear message without one. Build products go to `build/apps/<app>-<hash>/`, outside the projects of the developer, and Apple apps declare the APIs with required reasons of the engine in a privacy manifest merged from the engine, the plugins and the developer. The web template is a loading page with the app or engine logo, a progress bar with its percentage, the graphics API that the address asks for and the error screen, and the variables at the top of its `loader.css` restyle the splash. The default shell of C++ web apps shows the same splash, which the progress that the runtime reports through `onLoadProgress` feeds.
- Splash screens follow `app.json` and work in landscape and portrait on every device. The splash screen, and on desktops the window, which opens hidden except on Wayland, where a hidden window takes no frames, gives way only to the first complete frame of the app, which `core::Engine::isFrameComplete` reports: the first scene loaded, every picture of the UI arrived and every GUI laid out in an earlier frame, so no empty frame and no picture that pops in follows the splash.

## Async and threading

- The frame thread owns the GPU, the Lua state, scenes, UI, audio control and physics. It never blocks, so the audio device opens on a thread of its own and the app runs without sound until the system answers.
- The one exception is a halt of the Lua debugger in development, at a breakpoint, a step, a pause or an uncaught error, which holds the frame thread inside the code of the app until the editor lets it go on. While it halts, the host keeps processing the events of the window and the system through `Host::pumpHaltedEvents`, so the platform never marks the app as hung, and those events reach the app only after the halt. The platform layer runs no frame, nothing else of the app runs, the development connection carries only the messages of the debugger, and the sounds that already play go on in the mixer. A quit, a window that goes away or an activity that ends lets the frame finish without halting, and a web page, whose one thread delivers every message, never halts.
- The platform layer plays a frame at every refresh of the display, at the highest refresh it has, or at the frame rate the app asks for with `window.frameRate`, which displays that vary their refresh follow through the system API of each platform, while `platform::FrameRateGate` picks the refreshes of a faster display that play, and iPhones get past 60 hertz through the `CADisableMinimumFrameDurationOnPhone` that the tools add to the `Info.plist`.
- Varn's event loop is advanced once per frame with `Runtime::poll(budget)`, whose budget is a share of the frame time within bounds that `core::Engine` declares, so no amount of ready work holds a frame up. Promises resolve, coroutines resume, timers fire and socket and HTTP callbacks run inside that call, on the frame thread, in passes that repeat while they make progress and the budget lasts, and what the poll reports reaches the debug overlay and `debug.stats()`.
- Long-running CPU work (image and audio decoding, map parsing, path finding, procedural generation, data-parallel updates) runs on Varn's `taskPool()` through `core::JobSystem`. Blocking I/O runs on `ioPool()`. Results return to the frame thread through the event loop and, for Lua, through a Varn `Promise` that a coroutine can `:await()`. Slow Lua APIs offer an asynchronous version that returns a promise.
- A GPU device that compiles a shader when its program is made, such as the Metal device, starts compiling the programs of the renderer and of every `.shader` file on the I/O pool as soon as they are known through `gpu::Device::prepareProgram`, and each program is made the first time a draw needs it. Apple builds of the engine precompile the programs of the renderer into Metal libraries with the Metal toolchain of Xcode, so the Metal device loads them and compiles only the `.shader` files of the app.
- A compilation that its graphics API cannot stop, such as one of the compiler of Direct3D, runs on threads of its GPU device that nothing waits for, so a quit or a restart never waits for a program that was prepared ahead.
- Lua code never runs on worker threads. Long Lua computations run as `haylen.jobs` coroutines that share a time budget each frame.
- Never iterate a container while the loop body can run Lua or a user callback. Snapshot first, into storage that the next snapshot reuses, then iterate the snapshot, or reach a container that only grows by index up to the count it had before the loop.
- A job posted to a pool or to the loop never lets an exception escape. The job system hands failures to the frame thread, where they become engine errors.
- GPU resource creation and destruction stay on the frame thread. Handles released on any thread hand their GPU objects to the device, which destroys them after the frame is submitted.
- Static objects that other threads may still use at process exit are created with `new` and never destroyed.
- The web build is single-threaded like Varn. Pool jobs run when the poll drains them, and `JobSystem::parallelFor` runs inline there, so pages need no cross-origin isolation.

## Lifecycle and ownership

- One `core::Engine` owns every service of one running app, and one engine runs at a time in a process, which the engine enforces. Restarting an app destroys the engine between frames and creates a new one with a fresh Lua state once the platform prepared its GPU device, which WebGPU hands over only in a later turn of the event loop of the page, and the engine shuts down in a fixed order that releases Lua values before the Lua state closes.
- Scene changes run as one pipeline: the transition covers the current scene, the next scene loads asynchronously in its `load` hook (with progress, optionally behind a loading view), enters, and the transition reveals it. Effects that show both scenes at once load first. Transitions are optional and scenes pass through the states `created`, `loading`, `loaded`, `entering`, `active`, `covered`, `exiting`, `exited` and `unloaded`.
- Everything a scene or another owner creates (timers, tweens, event listeners, signal connections, async tasks, GUIs) belongs to it and ends with it, so no callback or coroutine ever runs for an owner that is gone. APIs that register callbacks take an `owner`, and without one they take the default of `lua::Owners::pushDefault`, which in development is the owner of the module that runs its top level, so a reload of the module ends what it registered.
- The game pause gates scenes, autoloads, timers, tweens and audio buses through process modes (`inherit`, `pausable`, `whenPaused`, `always`, `disabled`), and the app states halt the app in the background as the lifecycle options decide.
- The engine holds the start of an app with `Engine::holdStart` while the content it needs to start downloads behind the update screen, and the app starts in the first frame after the last hold ends.
- Engine and app events travel on the `EventBus` with one lifecycle vocabulary for the app, scenes, windows, input devices, network and objects, and signals connect objects directly. Both support priorities, one-shot and deferred delivery, and connections that end with their owner.
- Autoloads are app-wide singletons that live for the whole app and receive the lifecycle callbacks. The ones `app.json` lists load in order before `source/main.lua` runs, and `haylen.autoload` adds more while the app runs.

## Naming

- Types, enums and enum values use `PascalCase`. Functions, methods, variables, parameters and members use `camelCase`. Constants use `k` + `PascalCase`.
- Members have plain names with no prefix or suffix: never `m_`, `_` or a trailing underscore.
- Accessors: getters use `get` (`getPosition`), boolean queries use `is`, `has` or `can` (`isVisible`, `hasFocus`), and setters use `set` (`setPosition`). Container-like classes keep the standard library names (`size`, `empty`, `begin`, `end`, `clear`). Plain data structs without invariants expose public fields instead of accessors.
- A parameter or local variable never reuses the name of a member of its class, so nothing shadows a member (setters take `value`).
- Names say what something is. A plugin, class or module named after a verb or a vague word (like a plugin called `save`) is renamed to the thing it owns.
- The product name is Haylen, written `haylen` in identifiers, targets, modules and files. Things the engine runs are apps, never games: `app.json`, `haylen_add_app`, `core::Application`.
- Every app of the repository, its samples, templates, benchmarks and the apps of the tests, has the identifier `com.haylen.<product>` with a short product name, such as `com.haylen.music`, and the native code of the plugins of the samples and of the plugin template lives in packages under `com.haylen.plugins`. The prefix `dev.haylen` names only the engine itself: its Java and Kotlin packages, its Android libraries and the keys it reads from manifests.
- A tree of UI components mounted and shown together is a GUI: `ui::Gui` in C++, `haylen.Gui` in Lua, `gui` in fields, variables and event tables, such as `self.gui` of a scene.
- Lua names use the same words as the C++ API: modules are `haylen.<module>`, functions, methods, fields and option keys use `camelCase` and types use `PascalCase`. Accessor prefixes do not reach Lua: a C++ `getX`/`setX` pair is the Lua property `x` (`sprite.x`), and a read-only getter is a Lua property or method without the prefix (`world:bodyCount()`).
- Every name the Lua API takes or returns as a string is `camelCase` too: enum values, which are the C++ enum value with a lowercase first letter (`ProcessMode::WhenPaused` is `'whenPaused'`), event names, input control names, cursor names, easing names and asset type names. The keys of `app.json` and of engine data files are `camelCase` as well.
- Lua modules of 2D subsystems end with `2d`, such as `haylen.graphics2d`, `haylen.physics2d` and `haylen.animation2d`, so a future 3D module never conflicts. Dimension-agnostic modules keep plain names, such as `haylen.graphics` for textures, render targets, fonts and shaders, and `haylen.tiled` keeps its name because Tiled maps are 2D by nature.
- C and C++ source files (`.h`, `.hpp`, `.c`, `.cpp`, `.mm`) use `PascalCase` named after their class, for example `FrameClock.hpp` and `Renderer.cpp`. Lua files use `dash-case`, for example `main-menu.lua`, and every package keeps `source/main.lua` as its entry point. Lua modules are required with the same name, for example `require("scenes.main-menu")`.
- CMake module files use `dash-case`, for example `haylen-dependencies.cmake`. Sample folders use `dash-case`, for example `samples/games/tiny-island`.
- Every CMake target, project and install component, and every library, executable and other file that the build generates, uses dashes, such as the targets `haylen-engine` and `haylen-tests`, the install component `haylen-sdk`, the library `libhaylen-app.so` of Android release builds and the desktop library `native-demo` of a plugin. An underscore appears only where a name must be an identifier: CMake functions and variables, such as `haylen_add_app` and `HAYLEN_PLATFORM`, C and C++ symbols, such as the init function `native_demo_haylen_init` of that library, Java and Kotlin packages, Python modules that other files import and Android resources, while a prebuilt library of a third party keeps the name of its files. The tests of `tools/test_haylen.py` fail on a target, project or install component with an underscore in a tracked CMake file or in the CMake text that `haylen.py` writes, and name it.
- All folders are lowercase. File and folder names, assets among them, use dashes and never underscores, such as `docs/platform/platform-bridge.md` and `content/audio/fire-loop.ogg`. An underscore appears only where a name must be an identifier or a platform requires it: Python modules that other files import and the tests that `unittest` discovers by `test_*.py`, while a script run only as a command takes dashes, and Android resources under `res/`, whose names allow only letters, digits and underscores. GitHub reads the issue templates only from the folder `.github/ISSUE_TEMPLATE` and the funding links only from `.github/FUNDING.yml`, so those two keep the names GitHub requires, while the templates inside that folder use dashes, such as `bug-report.md`. The tests of `tools/test_haylen.py` fail on any other tracked file or folder with an underscore and name it.

## Code organization

- Every context has its own namespace, matching its folder: `haylen::core`, `haylen::math`, `haylen::io`, `haylen::assets`, `haylen::graphics`, `haylen::text`, `haylen::input`, `haylen::audio`, `haylen::ui`, `haylen::platform`, `haylen::localization`, `haylen::conversation`, `haylen::storage`, `haylen::ai`, `haylen::debug`, `haylen::net`, `haylen::content`, `haylen::gpu`, `haylen::lua` and `haylen::plugins`, and the code of the platform layer of SDL and of each GPU device lives in the namespace of its folder, `haylen::platform::sdl` and `haylen::gpu::<api>`, such as `haylen::gpu::vulkan`. Folders under `2d/` map to namespaces with the `2d` suffix, the same names as their Lua modules: `haylen::graphics2d`, `haylen::animation2d`, `haylen::particles2d`, `haylen::lighting2d`, `haylen::physics2d`, `haylen::navigation2d`, `haylen::spatial2d`, `haylen::procedural2d`, `haylen::nodes2d`, plus `haylen::tiled`. Nothing lives directly in the `haylen` namespace.
- A type name does not repeat its namespace when a precise name exists: `haylen::physics2d::World`, `haylen::physics2d::Body`, `haylen::tiled::Map`, `haylen::graphics2d::Camera`, `haylen::text::Layout`, `haylen::lua::Promise`. Types in the shared `haylen::plugins` namespace name their dimension (`Physics2DPlugin`).
- One class per file. A header and its source file hold one class and are named after it. Types owned by a single class (its options, events, results and enums) are nested in that class. A type shared by several classes gets its own file.
- There are no free functions. Every function is a method of a class: utilities are static methods (`math::Easing::apply`, `math::Geometry::intersects`), helpers of a source file are private methods of its class, operators are hidden friends defined inside the class, and each Lua binding is a class whose Lua entry points are static methods. The only exceptions are entry points whose names the platform dictates (`main`, `WinMain`, `JNI_OnLoad` and `Java_*` JNI functions, Emscripten exports and C callbacks with fixed signatures), and each one only forwards to a class.
- There are no namespace-scope variables or constants in source files. They are static members of the file's class.
- Every enum has exactly one table of its string names, and every Lua binding and file parser uses that table.
- Plugins live in `engine/include/haylen/plugins/` and `engine/src/plugins/`, in the `haylen::plugins` namespace, together with the `Plugin` interface. A plugin wires its subsystem into the engine and installs its Lua module, and the subsystem itself stays in its context folder. Plugins that apps construct or reference have public headers, and the others keep their headers in `engine/src/plugins/`. The class `plugins::BuiltInPlugins` registers the built-in plugins in dependency order.
- Everything specific to 2D lives in a `2d` folder (`engine/include/haylen/2d/`, `engine/src/2d/` with the Lua bindings of the 2D modules, and `engine/tests/2d/`), and dimension-agnostic code never depends on it.

## Lua bindings

- Each context keeps its Lua binding class next to it, such as `engine/src/2d/physics/Physics2DLua.cpp`, built with the public toolkit in `engine/include/haylen/lua/` (`Binding`, `ClassBuilder`, `Userdata`, `Stack`, `Converter`, `EnumNames`, `Table`, `Promise`, `Reference`, `TypeConverter` and `Runtime`). Projects that extend the engine use the same toolkit.
- Every public C++ and Lua API follows `docs/tools/api-policy.md`, which says what is public and stable and how an API grows without breaking apps: options in a trailing table, returns that describe something as tables, event payloads as one table or at most two values in a fixed order, the same words for the same ideas across modules, and an `owner` on everything that registers a callback, a task or a job.
- The Lua API is the same on every platform and graphics API. A Lua binding never includes a host or a platform folder, which `tools/test_haylen.py` checks, so what a script sees never depends on what draws the app.
- Options are passed as tables whose unknown keys raise `Unknown option "<key>".`, and enums are passed as their string names.
- Option tables read on every draw or for every item go through `Table::readFields`, which reads the keys a table holds in one pass with `Table::readValue`, instead of one `Table::readField` per known option.
- Error messages are complete sentences that start with a capital letter and end with a period, and they say what was wrong and what is expected, such as `No canvas is active. Call "beginWorld", "beginScreen" or "beginTarget" before drawing.`. The only exceptions are the short reasons of `luaL_argerror` and `luaL_typeerror`, which Lua wraps into its own `bad argument` sentence.
- A yield of Lua jumps straight back to its `lua_resume` with `_longjmp` on every compiler but MSVC and except in thread sanitizer builds, and runs no destructor of the C++ frames it leaves. A C++ function that calls `lua_callk`, `lua_pcallk` or `lua_yieldk` therefore keeps no destructible local alive across that call, never makes it inside a `catch` block or inside `Binding::guarded`, and hands what its continuation needs over the Lua stack, an upvalue or its `lua_KContext`. An error stays a C++ exception and runs every destructor. Each such function has a test that yields through it.
- Userdata keep their Lua callbacks in their user value, so a callback that refers back to its owner never keeps it alive. C++ code that keeps a Lua value alive uses `lua::Reference` and releases it in `stop`.
- Hot paths offer fast Lua access: number fields next to vector properties, native properties that tweens animate in C++, float buffers shared with C++ and bulk APIs that move many objects in one call.
- App code loads Lua chunks only as text (`"t"` mode): `load` and `loadfile` refuse bytecode, `dofile` runs only text, and `string.dump` and `package.loadlib` do not exist. The one exception is the module loader of the engine, which loads a module as bytecode only when the authenticated catalog of a protected release holds it as `LuaBytecode`, compiled by the content tool with the Lua of the engine for the ABI that the app manifest records.
- Code that may fail runs in an `Engine::Phase`: lifecycle steps, such as the start of the app, scene hooks that load, enter, exit, unload, pause or resume, autoloads that start or stop and tasks that failed, open an `Engine::PhaseScope` of `Lifecycle`, so their errors restart the app in development, while errors of frame code and of reloads resume it once a fix reloads.
- Every failure that no caller receives reaches the error screen through the handler of `async.onFailure` that the engine installs, and a promise that rejects while nothing awaits or catches it is such a failure. A binding rejects with `lua::Promise::reject` when the promise is the only way its failure reaches the app, and with `rejectHandled` when the engine reports the failure another way or the app asked for it, such as a cancellation.

## Native plugins

- A native plugin is a folder named after its dash-case id with `plugin.json`, a `README.md` with the complete Lua API and the setup per platform, the Lua API in `source/` (`init.lua` is `require('<id>')`), and one folder per implementation: `apple/` (Swift or Objective-C), `android/` (a Gradle library module in Kotlin or Java), `web/` (an ES module) and `native/` (a CMake project of a C or C++ library for desktops). The file `docs/platform/plugins.md` GUIs every field of `plugin.json`.
- The file `plugin.json` declares the platforms, the plugins it requires, the permissions it owns, typed parameters with their platforms, defaults and descriptions, and what each platform brings: Swift packages pinned to one exact version, system frameworks, the binary frameworks it ships, Info.plist keys, entitlements, privacy declarations, resources, build scripts and app extensions on Apple, the module, the Maven repositories of its SDKs, Gradle plugins, manifest placeholders and files on Android, and on both the delivery of the named packs of the content as asset packs of the store, the module on the web, the URL schemes of the links that open the app on Windows and Linux in `desktop`, and the native library. The placeholder `${parameter}` in those values is replaced with the app's value.
- Apps list their plugins in the `plugins` section of `app.json`, each entry an object with the parameter values under `parameters` and where the plugin comes from: the folder `plugins/<id>/` of the app without `path` and `git`, which `haylen.py plugin add` copies, a folder that `path` names, absolute or relative to the app folder, or a git repository that `git` names at `ref`, which `haylen.py` fetches into a cache under `build/` keyed by the address and the ref. The `id` of the `plugin.json` equals the key of its entry, and `plugin add --reference` writes a reference instead of a copy. A value that differs per platform uses parameters with different names (`iosAppId`, `androidAppId`), so nothing resolves platform values at runtime. Missing parameters take the defaults of `plugin.json` on every platform.
- The package carries `plugins/<id>/plugin.json` and `plugins/<id>/source/` of every listed plugin, wherever it comes from, so the runtime never resolves a reference. Nothing else of a plugin reaches the package. A folder that the player runs directly and that lacks a referenced plugin fails with a sentence that says to run the app with `haylen run`, which on this machine runs a copy of the package in the build folder of the app, whose development server watches the referenced folders and pushes their files under `plugins/<id>/`. C++ apps receive the folders of their plugins from `haylen.py` through `HAYLEN_PLUGIN_FOLDERS_FILE`.
- The tool `haylen.py` validates every manifest and the app's values before it builds, and brings every platform part into the generated folder of the project: on Apple the target templates of `haylen/project.yml` with the sources, packages, frameworks, resources and scripts, and the completed `Info.plist`, entitlements and privacy manifest, on Android the modules in `haylen/plugins` with the keys of `haylen/haylen.properties`, on the web the modules of the site with `config.json`, and on desktops the native library like the `native` section of `app.json`. Plugin `files` go into a copy of the template that haylen.py owns, and `check` names the ones a project of the developer lacks. A C++ app takes every part of every plugin too: its Android project and its site are prepared like those of a Lua app, and on Apple platforms `haylen.py run` writes `haylen-plugins.cmake`, from which `haylen_add_app` compiles the sources, links and embeds the shipped frameworks, builds and embeds the app extensions, runs the build scripts and merges the `Info.plist` keys, entitlements and privacy declarations, while the Swift packages, which CMake cannot build, build with `xcodebuild` into one dynamic framework that the app embeds, and the app links the binary frameworks of the packages itself, its plugin sources take the module maps and public header folders of their C-family targets, and its build scripts reach their checkouts through `BUILD_DIR`, as in a Lua app.
- A plugin repository keeps the `.gitignore`, `.editorconfig` and `.clang-format` of `templates/plugin`. The skeleton of `templates/plugin` answers its method and sends its event on every platform, so a new plugin runs everywhere from its first build, and its desktop library takes the id, the name that `native.load` finds, while its init function takes the id with underscores, such as `native.load('camera-scanner', {init = 'camera_scanner_haylen_init'})`. The features of `templates/plugin-features` that `plugin new --with` names fill the blocks of the skeleton with working code of every native part, built on platform APIs alone, and a desktop library answers the methods of a feature it cannot serve with `unsupported`.
- Native plugin methods are named `<id>.<method>` and events `<id>.<event>`, with camelCase method and event names, and a plugin offers the same Lua API on every platform it supports. Calls a platform cannot serve fail with the code `unsupported` and a clear message.
- Native parts carry data in the form the bridge gives it: bytes, such as images, recordings and files, travel next to the JSON in the byte type of each language and never as text, large data that changes often, such as the frames of a camera that the app works on, crosses as data views whose memory every language shares, continuous video and audio go through the streams of the plugin, which keep the newest video frame and a lock-free ring of samples, and events that fire many times per frame are sent batched, so Lua receives one list per frame. A plugin declares the permissions it owns in `plugin.json`, its native part registers each one with its context, `HaylenPermission` on Apple platforms and Android and `context.registerPermission` on the web, and asks for it through `requirePermission` of its context before it uses the capability, while the runtime checks the requirements of the permission, shows the prompt only while the system still asks and on Android asks through the one launcher of the Activity Result API of the engine, so no plugin keeps a launcher of permissions of its own, and a plugin that posts notifications adopts `HaylenNotificationPlugin` on Apple platforms and starts `HaylenLinkActivity` from its taps on Android, sending the tap as a retained event so it reaches an app that the tap launched. The demo plugin of the test project tests each of these mechanisms on every platform.
- The Apple runtime reads the plugins, their order and their parameters from the bundled package (`app.json` and each `plugin.json`), never from a list in the platform project. The Android runtime loads its plugin classes when the process starts, before the engine opens the package, so it reads them from `haylen-plugins.json`, which `haylen.py prepare` writes into the assets with only the ids, versions and parameter values of the plugins with an Android part, and never from `app.json` or a `plugin.json`, which a protected release keeps encrypted.
- An Android plugin module depends on `dev.haylen:haylen-plugins`, plus `haylen-links` for links and notifications and `haylen-coroutines` for suspending handlers.
- The plugins of system capabilities, such as the camera, the location or notifications, and the plugins that bring third-party SDKs, such as ads, analytics, crash reporting, sign-in, purchases or game services, live in the sibling repository `haylen-plugins`, one folder each, and never in this repository, which uses no third-party library beyond the dependencies of the engine. This repository holds the plugin architecture, the engine and platform capabilities they build on, and the demo plugin of the test project, built on platform APIs alone, which tests every capability. The command `haylen.py plugin add` takes a plugin folder, or a plugin repository at a branch, tag or commit that holds the plugin at its root or in the folder that `--path` names, and an entry of `app.json` references the same with `path`, or with `git`, `ref` and `path`.

## Architecture rules

- Engine code lives under `engine` and never depends on samples, templates or apps.
- Apps consume only public engine headers from `engine/include` and the Lua API.
- The portable engine library never calls SDL, a graphics API or OS APIs. It reaches them only through the internal `Host` interface in `engine/src/platform/Host.hpp` and the `gpu::Device` it creates. The target `haylen-runtime` implements the host for real platforms with the native host, the player, the services of the platform folder and the platform layer, the target `haylen-gpu` holds the GPU devices, and `haylen-headless-host` implements it for tests with the null GPU device `gpu::NullDevice`, which checks every call against the contract of `gpu::Device` and records what each frame did.
- Only `engine/src/platform/sdl/` and its tests include the headers of SDL or call it, and only the GPU devices in `engine/src/gpu/` and their tests include the headers of a graphics API, which `tools/test_haylen.py` checks.
- Rendering goes through the Haylen graphics API down to the `gpu::Device` that draws, whose graphics API every device names with the one table `gpu::Device::kApiNames`. Apps never include SDL, a graphics API, Box2D, miniaudio, Dear ImGui backend, Varn internals, JNI, UIKit, AppKit or Emscripten headers, while the public headers of Varn's data view are part of the API of the bridge.
- Every GPU device captures frames with the capture tool of its graphics API, which `gpu::Device::getCaptureSupport` names with what is missing where it has none: the frame capture of Metal, which the Debug runs of `haylen run` turn on with `MTL_CAPTURE_ENABLED` when they start an Apple app or the player, PIX on Direct3D 12 and RenderDoc on Direct3D, Vulkan and OpenGL, while browsers and the null device have none. The engine never bundles or loads RenderDoc or PIX, which hook the graphics API only when they launch the app, and `debug.captureGpuAsync`, the console command `gpuCapture`, the key `g` of `haylen run` and `haylen capture` write the capture into the storage of the app.
- Every curve has an edge that fades over one pixel of its destination at any size, zoom, rotation, density and graphics API, without multisampling. Circles, rings, arcs and shapes draw as one quad of the shape program, whose shader turns the exact distance to the edge into coverage, with the border inside the same edge, and polygons and meshes fade their outline over a fringe one pixel wide. Paths flatten their curves and arcs within a quarter pixel of the destination, resolve their outlines by their fill rule into simple outlines and holes, and fill and stroke through the same fringes, keeping their triangles between draws. The UI draws every curve of its components, their borders, focus rings and shadows as these shapes through callbacks of the ImGui draw list, and ImGui tessellates and fades what it draws itself in pixels of the screen. Nothing depends on the `sampleCount` of the window, which render targets and captures never have.
- Services the engine offers on every platform, such as system information, the clipboard and the permissions of the engine that the person grants at run time, such as the local network of Android 17, go through the `Host` interface and the `Services` of each platform folder, and complete asynchronously on the frame thread. The engine exposes them as its own C++ and Lua APIs (`platform::System`, `haylen.system`), never as bridge methods.
- Every capability that at least one platform gates behind a permission, a prompt or a policy has one API shaped for the strictest platform, as `docs/tools/api-policy.md` describes: asynchronous everywhere, answered with a state of one vocabulary (`granted`, `prompt`, `denied`, `unknown`, `unsupported`) instead of a boolean, checked and requested through `system.permission` and `system.requestPermission`, with each platform's answers listed in its reference page, so an app runs the same complete flow on every platform. The kinds of `platform::Permission` are only the permissions that the engine uses itself, `screens` and `localNetwork`, which the host answers. Every other permission belongs to the plugin that declares it in the `permissions` of its `plugin.json`, a camelCase name that no other plugin of the app declares and that is no kind of the engine, which `haylen.py` and the engine check. The engine reaches it through the bridge methods `<id>.permission` and `<id>.requestPermission` with `{"name"}`, which the runtime of Apple platforms, Android and the web answers for the permissions that the native part registered, and a desktop library registers as handlers of its own. A use that the person or the platform refused fails with the code `denied` or `unsupported` and the sentence that names the capability and how to ask for it again.
- The `platform::Bridge` carries only the methods and events of apps and native plugins, as JSON requests and asynchronous callbacks delivered on the frame thread. It has no built-in methods.
- The engine libraries carry only what every app needs, and the templates declare the rest, such as the permissions of Android for the network, the local network and the rumble of gamepads, as visible defaults the developer may delete. A feature checks its platform requirement before it calls the system API, and when the requirement is missing it logs once what is missing and how to add it, then fails with `unsupported` and `data.missing`, or does nothing when it answers nothing. Plugins check theirs with `HaylenRequirements` on Apple platforms and Android and with `context.require` on the web.
- The engine links no framework that only some apps need. It reaches such frameworks, such as UserNotifications, through the Objective-C runtime or loads them at run time, and the plugins that use them declare them in the `frameworks` of `plugin.json`. Notification plugins adopt `HaylenNotificationPlugin`.
- Every JNI call from C++ into Java checks for a pending exception, which is described to logcat, cleared and logged as an engine error that names the method.
- A finger that travels past the slop of `ScrollArbiter` or shares the screen with another finger never clicks: the UI backend lets go of the item it pressed, unless the component that holds it calls `Context::keepDrag` because it follows the finger, and the gestures of `haylen.input` never end such a finger as a tap. The mouse that a finger drives through `input.touchAsMouse` reaches the app alone, so the UI follows the finger and a drag always scrolls the area under it.
- All gameplay input goes through the action map, and UI input goes through focus navigation that works with every device. The game and the UI share the devices through the play area of a GUI: while the play area has the focus, the directions, accept and menu reach the action map, while a control has it, the UI captures every navigation key, button and stick, and a press stays with the side that took it until it is released.
- UI positions itself in the engine-provided safe area.
- A UI node names its ImGui items by its id, or by its kind and its place among its siblings, never by its address, so a node that its GUI builds again keeps its focus, the text being edited with the keyboard, a press in progress and the place of its scroll, and new children draw in the frame they arrive in.
- Screen readers read the UI through the tree of accessible elements that the GUIs build as they draw, only while the platform or the app wants it, and the host receives it only when it changed. Every component kind describes itself with its role, label, value and state, and the actions of screen readers reach the controls through the focus navigator, the way the keyboard and gamepads do.
- The UI and the motion of the engine follow the accessibility settings of the system: the text scale scales the fonts of the UI, higher contrast switches to the high contrast theme of the active theme, reduced transparency draws the surfaces of the theme opaque, and tweens and transitions that opt in shorten or skip their motion.
- Scroll bars never cover or touch their content, and a `scroll`, a `collection` and a `textArea` fade the alpha of their content out to transparent along each edge where it continues past the area, over the theme metric `scrollFade`, through the fades of `graphics2d::Renderer`, so whatever lies below shows through and no color is painted over the content. Every area that scrolls keeps its bar in a lane of its own along its end edge, with the theme gap `scrollbarGap` between the content and the bar, which never spans fewer than 4 points of the screen at any UI scale, and the lane takes room from the content only while the content is longer than its area. Every area that scrolls moves by the points of the screen that a trackpad reports, at once, and by the theme metric `scrollLine` for each step of a wheel, gliding there, through `Context::takeWheel`, never by the steps of ImGui, and `input.scrollSpeed` multiplies both. A trackpad that reports the phases of its gestures, as macOS does through `Event::scrollPhase`, drags the content of a `Scroller` the way a finger does and releases it when the fingers leave, so the inertia and the bounce are the motion of the engine, while the momentum of the system reaches only the areas without a motion of their own, and a precise device without phases moves the content within its range without stretching it. An item that the player drags scrolls the innermost area under it near its ends through `Context::takeEdgeScroll`, and a finger lifts an item only after a long press, so it never takes a scroll from the area or loses its item to one. A gesture of the wheel or the trackpad keeps the axis it starts along and the area it starts in, the innermost area under the pointer that can move along that axis, until it pauses or fingers touch the trackpad again, and a finger goes to the innermost area it pressed whose axis its drag follows, through `Context::takeDrag`, so a vertical gesture over a horizontal list scrolls the vertical area around it.
- Videos decode with the decoder of each platform through `Host::openVideo`, never with a decoder the engine ships, open on the I/O pool and decode ahead of the playback on the task pool, so the frame thread only presents the frame of the current time, and their sound plays through the mixer.
- Physics goes through the Haylen Box2D wrapper, whose handles detect a destroyed world. A world runs the tasks of each Box2D step on `core::JobSystem` once enough of its bodies are awake, and the helpers that act on a world every step, such as vehicles, force fields and fluids, run in C++ through its step hooks, never as a Lua call per body.
- Every common physics problem, such as tunneling, ghost collisions at tile joints, slopes, moving platforms and stretching joints, has an engine option or helper that solves it, explained in `docs/2d/physics.md`, and a test of the test project shows the problem and the solution side by side.
- Protected content goes through `haylen::content`: immutable HPAK shards of chunks that are compressed and encrypted one by one, signed manifests and encrypted catalogs, as `docs/content/content.md` describes. Its cryptography comes from Monocypher alone, and nothing in the repository implements a cryptographic primitive. Every parser of a binary format treats its bytes as hostile, checks every offset, size and count before it uses them, and has hostile input tests and an entry for the fuzzer that `HAYLEN_BUILD_FUZZERS` builds. Font files are read only through HarfBuzz, by `text::FontFile`, both for the distance fields of `text::TrueTypeFont` and for Dear ImGui through the font loader `ui::ImGuiFontLoader`, so no reader that trusts the bytes of a font is in the build. Image files decode only through `graphics::Image::decode`, which refuses a size its header declares beyond `Image::kMaxSide` or the longest side the caller names before it allocates a pixel, caps every buffer of the decoder at what that size needs and keeps the pixels the decoder wrote without a copy.
- Content reaches the device through `content::ContentManager`: the `content` section of `app.json` makes an asset `required`, `prefetch` or `onDemand`, a synchronous load never waits for the network and fails for an asset that is not on the device, and every asynchronous load and preload brings what is missing first. Stores that deliver packs plug in as the `content::PackSource` of their native plugins, which the manager asks before the content server, so app code never knows where an asset comes from. Downloads and updates go through the local content store, never write a plain byte, and an update becomes active only as one transaction that plays from the next start. Development applies the same delivery to the folder of the app.
- Tiled runtime code targets current Tiled JSON files and does not read obsolete formats.

## Dependencies

- The engine compiles its shaders, and apps theirs, with the Haylen shader compiler `haylen-shaderc` of the repository https://github.com/haylen-org/haylen-shader-compiler, pinned in `engine/cmake/haylen-shader-compiler.json` to a release and its commit. The script `engine/cmake/haylen-shader-compiler.cmake` provides it for CMake, whenever `HAYLEN_SHADERC` names no build, and for `haylen.py`, which keeps it in `.tools/` and hands it to CMake unless `HAYLEN_SHADER_COMPILER` names a build: it downloads the binary of the release for the system and processor of the machine, checking its SHA-256, and builds the compiler from the source of the commit, checked the same way, only on a machine whose binary the release does not ship. The releases of the compiler, unlike those of this repository, carry prebuilt binaries, so app developers never build the compiler. It compiles the Haylen shader language into `.shader` packages with the reflection and the code of every shader language, and the engine embeds only the languages of the graphics API of its build. A change to the language or the package format lands in the compiler first and reaches the engine with a new pin. The compiler keeps one commit and one version, `1.0.0`, whose release, named by the version alone, every change of the compiler rebuilds, so a new pin names a new commit and new hashes under the same version, and the script keeps each pinned commit in a folder of its own.
- Dependencies are declared with CPM in `engine/cmake/haylen-dependencies.cmake`, pinned with a SHA-256 hash to their latest release or, when a project has no releases, to its latest default-branch commit. Every dependency, tool and SDK of the engine, the templates and the CI stays at its latest version, and a newer release is adopted as soon as it exists.
- The package the engine shares with Varn, nlohmann/json, is declared before Varn, so Varn reuses it and the whole build resolves a single copy of it.
- A change to a dependency's source is a patch in `engine/cmake/patches/` that CPM applies, documented in `docs/tools/distribution.md` or `docs/tools/build.md` with the reason. The patch fixes the real problem and stays as small as possible. A patched package keys its source cache with `haylen_patched_package_key`, from the hash of its archive and the contents of its patches, so an edited patch reaches every checkout.
- When a dependency is updated, adopt its current API everywhere and drop patches it no longer needs. Do not keep code paths for the previous version.

## Samples

- Samples are Lua apps grouped by category under `samples/`: `tests/` is the test project with a test of every engine feature, `games/` holds complete games, `apps/` holds apps of real kinds of products with fake data, such as a store or a music player, `stress/` holds samples that measure how much the engine carries, each with an on-screen readout of the frame time and the counts, `cpp/` holds C++ projects, and every other kind of app gets its own category folder. Commands take a sample's folder like any app folder, such as `haylen run samples/games/tiny-island`. No command names a sample or treats one as special, and a tool that only one sample uses lives in its `tools/` folder.
- A Lua sample holds `app.json`, `README.md`, `source/` and `content/`, its native code lives in local plugins under `plugins/`, and its UI tests, when it has them, live in Swift in `ui-tests/`. Samples keep no platform projects, so they build copies of the templates. Only `app.json`, `source/`, `content/` and the Lua of the listed plugins are deployed.
- The test project opens a menu of categories and then the tests of a category. A category is a folder `source/categories/<category>/` with its `manifest.lua` (prefix, title, description and tests, with the platforms a test runs on and the reason for each other platform), one file per test and the modules its tests share, and its assets live in `content/<category>/`. Every test has a code made of the prefix of its category and three digits, such as `PHY-004`, which the menu, the header and every log line show, which never changes and is never reused, and which `samples/tests/README.md` lists. A new test takes the next number of its category.
- Every test of the test project shows, in a card under its play area or its content, a few lines of the Lua that does what it shows, with the real calls and options of the API, so a person goes from what they see to how it is done. The card keeps one height in every test, and the region of the test, its play area or its content, fills the room between its header and the card and scrolls content taller than it, so a test keeps its touch controls, overlays and GUIs of its own inside that region and never draws under the card or the hint. Every test of the test project has a Back button in the safe area, with Escape, the east gamepad button, the TV menu button and the Android back button going back to its list. Game input reaches it through a play area, a platform that cannot run it shows the exact reason instead, and its errors return from the error screen to the list without restarting the project. A test that changes a setting `app.json` gives the whole project changes it at run time and restores it when it ends. Every test runs clean on the headless player (`haylen-headless samples/tests`) or names `headless` with its reason, and the CI job `tests-project` runs the whole project on every push.
- Samples use only documented Lua APIs, work with mouse, touch, keyboard, gamepads and TV remotes, run on every platform and clean up everything they create through owners. When a sample needs something the engine lacks, the engine gains the capability instead of the sample working around it.
- Samples use as few images as they need to look good. Generated art goes where it makes the difference, such as games, nine-slices, UI themes and the interface of an app, and everything else is drawn with SVG or primitives, so a sample never carries one image per item of its data, such as a picture for every product of a store, and the repository never fills with images.
- Sample and template art (sprites, tiles, UI themes, icons, backgrounds and effects) is made for the project, polished, in high definition and in one visual style per project. Images are generated with the `codex` command line and its `$imagegen` skill, run without `OPENAI_API_KEY` so it uses the subscription of the owner: `env -u OPENAI_API_KEY codex exec --sandbox workspace-write --skip-git-repo-check '<prompt>'`. The prompt describes the style, names the exact size and the transparency, and asks for the file to be cropped or resized locally to that size, and the result is checked before it is used. The art of Tiny Island is the standard of the whole repository: every other sample, the test project, the UI themes and the templates follow its style guide in `samples/games/tiny-island/README.md`, with the same way of drawing, the same proportions and the same polish, so the repository reads as one family of art. A sample keeps the style guide of its art in its README, with the palette, the outline, the light and the sizes of each kind of asset, and every prompt carries the key words of that guide. Art painted in high definition loads with the `linear` filter, and the UI theme of the sample sets `imageFilter` to `linear` for the pictures of its components. The frames of an animated sheet hold one pivot, the feet on one line under the head and torso for characters and objects that stand on the ground, the lowest part for things fixed at their base, such as a torch whose flame flickers, and the middle for items that spin, so no animation dances, and every animated sheet of the samples is declared in `tools/sprite-sheets.json`, which `tools/check-sprite-sheets.py` checks, aligns with `--align` and the tests of `tools/test_haylen.py` run. Every image of the samples and the templates has clean edges, with nothing left of the magenta it was painted on and no jagged outline, which `tools/check-image-edges.py` checks and cleans with `--clean`, and the pixel art and data images that keep hard edges on purpose are listed in `tools/image-edges.json` with the reason.

## Mandatory formatting standard

- Preserve the visual, structural, and architectural style already present in the project.
- Keep code compact, professional, and consistent.
- Avoid excessive vertical whitespace.
- Use only the spacing required to separate reading contexts.
- Organize complex methods and functions into logical blocks that are easy to scan.
- Separate blocks with different responsibilities with one blank line.
- Do not visually glue multiple conditions, validations, loops, state mutations, and returns together.
- A function's flow must be understandable at a glance.
- Complex functions must have a visually clear beginning, middle, and end.
- Important blocks inside genuinely complex functions may have a short comment that explains intent.
- Comments explain context or intent. They do not restate the code.
- Do not add obvious, decorative, artificial, or redundant comments.
- Do not add artificial section comments such as helpers, validators, or public methods.
- Extract focused functions when one function is accumulating unrelated responsibilities.
- Do not extract functions only to reduce the visible line count.
- Avoid abstractions that make the main flow harder to understand.
- Avoid unnecessary nesting.
- Prefer early returns when they simplify control flow.
- Do not use an unnecessary else after return.
- Keep includes direct, minimal, and ordered.
- Do not keep dead code, legacy code, generic fallbacks, or unexpected implicit behavior.
- Avoid macros, unsafe casts, and raw owning pointers when a safer project-consistent alternative exists.
- Use const, references, RAII, and smart pointers when they improve ownership and safety.
- Keep headers, implementation files, namespaces, types, names, and responsibilities consistent.
- The code must look like product code written by an experienced C++ engineer.
- Do not add comments in headers merely to describe methods, sections, or members.
- The build is warning-free on every platform with the warnings of `engine/cmake/haylen-warnings.cmake`. Those warnings apply to the targets of the engine alone, and the targets of a dependency that bring warning flags of their own build without warnings through `haylen_disable_warnings`, since only that dependency can act on them.
- The tool `clang-format` does not format project lambdas acceptably. Wrap non-trivial lambdas in `// clang-format off` and `// clang-format on` markers, and format the lambda manually. Multi-line Lua sources in tests get the same markers.
- Run `haylen format` before finishing a change. It applies `.clang-format` to every C, C++, Objective-C and Objective-C++ file of the engine, the samples and the templates, except the files of the plugin template whose names hold a token such as `{{NAME}}`, which become code only once `plugin new` replaces their tokens, and lists multi-line lambdas that are missing their `clang-format off` and `on` markers. The command `haylen format --check` fails on either problem and runs in CI.

## Writing standard

These rules apply to every text the project writes: code comments, documentation, `README.md`, `PROJECT.md`, error, log and console messages, the output of `haylen.py` and the other tools, and the texts apps and samples show. Logs and messages to people are sentences with the ordinary case of a sentence. Commit messages are the one exception, all lowercase, as the working rules say.

- Every sentence starts with a capital letter. When a sentence would begin with a command, identifier, path, key or value written in lowercase, keep its exact spelling and put a capitalized word in front of it, such as "The command", "Run", "The function" or "The file".
- The same holds for every text that is not a full sentence: titles, button and menu texts, captions, hints, labels and each line of an on-screen readout start with a capital letter, such as `Name %s, %d coins`. Only code shown as code keeps its own form.
- Reserved expressions are always marked, so they never read as part of the prose: commands, code, identifiers, file names and paths, keys, option names and values. Markdown documents and code comments wrap them in backticks. Plain-text messages, logs and command output wrap them in double quotes, for example `Name the device with "--device". Use the command "xcrun devicectl list devices" to list them.`
- The terminal output of `haylen.py` is calm: short steps after a marker, reserved expressions in one soft color instead of quotes, URLs underlined because terminals open them, and paths bare with no style. It shows the steps and keeps the output of the tools it runs in the log of the command in `build/logs`, which only `--verbose` prints, while the log of a running app, the results of tests and benchmarks and other output the developer reads always print. A running app shows one summary with the app, the device and the configuration, and the keys that act on it, one per line, before its log. In its source, messages mark reserved expressions with double quotes and paths and URLs with backticks, and without color the output keeps the double quotes and drops the backticks.

## Comment standard

- Every comment is a complete sentence that starts with a capital letter and ends with a period, following the writing standard above.
- If a sentence needs to begin with a lowercase identifier, keep its exact spelling and rewrite the sentence so the identifier does not start it.
- A comment above a function, method, class, or module explains what callers need to know, not its internal implementation.
- Comments exist only where they are truly necessary, because well-named classes, methods and variables already make the code readable. Never comment what the code says, and never narrate a change or a request.
- Keep comments concise and natural.
- Do not split one sentence across multiple lines.
- Do not continue one sentence on the next line.
- End the current sentence with a period before starting another sentence on the next line.
- Do not join sentences with semicolons, in comments or in documentation.
- Avoid verbose, fragmented, or narrative comments.
- Code and comments are written in English.

## Tests

- Every engine capability has GoogleTest tests when the logic can run without a real graphics device or platform runtime. The headless host (the null GPU device, a mixer without a device, Varn runtime) makes the renderer, UI, Lua bindings and the engine loop testable, and `test::EngineFixture` runs a real engine on an in-memory package.
- Lua bindings are tested by running Lua through the headless engine and asserting on engine state, returned values, error messages and asynchronous results.
- Every fix comes with a regression test that fails without it.
- Tests verify behavior that matters. Do not write redundant tests, generated tests or tests that only restate the implementation.
- Test files follow the code rules: they live in the namespace of the context they test, keep helpers in fixtures or support classes, and name suites after their subject with a `Test` suffix and tests after the behavior they verify.
- Test data lives in `engine/tests/data/`, so engine tests never read files of the samples.
- The test program replaces the global allocation functions for `test::AllocationTracker`, so tests show that an operation never allocates a whole file or package.
- Behavior that only a person sees on a device, such as windows that resize, the system UI and gestures, is covered by UI tests on the simulators, which `haylen test --ui <app>` runs from the `ui-tests/` folder of the app.
- Run `haylen test`. Changes to threading, lifetimes or memory handling also pass `haylen test --sanitizers thread` and `--sanitizers address`.
- Every platform, GPU and device runs its tests from the command line, without continuous integration, as `docs/tools/hardware-testing.md` explains: machines at hand, simulators, emulators, real devices, and GPUs and phones rented on Amazon Web Services and Microsoft Azure. Rented machines run only after every binary is built, in one batch, with a shutdown timer, and everything they created is deleted and checked right after. Credentials stay in environment variables and never reach a file, a log or the repository.
- The rules of `haylen.py` that need no build are tested by `tools/test_haylen.py`, with `python3 -m unittest discover -s tools -p "test_*.py"`, which CI runs.
- Engine coverage is kept as close to 100 percent as the code allows. Run `haylen coverage`.

## Documentation

- Every change updates the docs it affects in the same change.
- The docs form one tree that a reader walks from the top: the main `README.md`, which presents Haylen, gives the quick start and links the documentation once, through `docs/README.md`, the index of the blocks, whose tables lead to the index of each block, `docs/<block>/README.md`, whose tables list its pages. The blocks of guides follow the contexts of the engine, `core`, `graphics`, `2d`, `ui`, `audio`, `input`, `platform`, `network`, `content` and `tools`, and every module of `docs/2d/` has its own guide, so a 3D block gets its own folder next to them. The block `lua-api` holds the reference.
- The tables of the indexes have three columns, `Name`, `Description` and `Link`, with the rows in alphabetical order of their names and the path of the page as the text of its link. A table never mixes guides with reference pages: the index lists the blocks of guides and the reference in sections of their own, and a block index lists its guides and the reference pages of its modules in separate tables.
- Guides explain concepts: what a system is, how it works, when to use what and how its parts fit together. Reference pages list the API of one Lua module: every function, type, method, property, option, default, event and error message. A subject lives in one page, so a guide links to the reference instead of repeating its options, and a reference links to the guide instead of explaining its concepts.
- Every Lua module has a reference page in `docs/lua-api/<module>.md`, which `docs/lua-api/README.md` and the index of its block list.
- The guides explain the architecture, the lifecycle, the build, distribution, embedding, testing and each system in depth. The file `docs/tools/testing.md` describes the test support, `docs/tools/distribution.md` the commands, templates and platform support, `docs/core/architecture.md` the libraries, source layout, plugins, frame and threads, `docs/2d/physics.md` the physics system, its common problems and its performance, `docs/tools/api-policy.md` what is public and stable, and `docs/tools/ci-installers.md` the installers that CI builds.
- Every page follows one pattern. Its title starts with one emoji, such as `# 🎨 Rendering` or ``# 📖 `haylen.timer` ``, its first paragraph says what the page covers, its sections carry no emoji, so their anchors stay plain, code, names, paths, keys and values are in backticks, and every code block names its language.
- The docs are written in easy English: short sentences, common words, one idea per sentence and every term explained where it first appears. Every capability has a code example.
- Markdown prose is never hard-wrapped. One paragraph is one line.
- The tests `DocsTest` of `tools/test_haylen.py` check the tree, the tables of the indexes, the titles, the code blocks, the paragraphs, every relative link and its heading, and that no long sentence of a guide repeats in another page.
