# Text input

Text fields of the UI type through the native text input of each platform. A hidden native field sits over the focused field of the UI and edits its text, so phones, tablets and TVs open their software keyboard, and every platform brings its input methods for languages such as Japanese and Chinese, autocorrection, dictation, the emoji picker and native paste, copy and undo. The UI still draws the field, its text, its selection and its caret. This guide explains how the two sides stay in step and what each platform does. The [UI guide](ui.md#text-entry) shows how apps use text fields, and the [haylen.ui reference](lua-api/ui.md#inputs) lists their keyboard options.

## How a field edits

When a text component of [haylen.ui](lua-api/ui.md) takes the focus, the UI publishes it to the platform: an id, a revision, the UTF-8 text, the selection in code points, the rectangles of the field and of its caret in framebuffer pixels, the keyboard (text, multiline, number, decimal, phone, email, url, search or password), the label of the return key (default, done, go, next, search or send), autocorrection, capitalization and the length limit. The platform places its native field over the field and shows the keyboard.

What the user types comes back as the whole text of the native field, its selection and the range the input method composes, together with the revision the native field last received. The UI applies it inside the ImGui callback of the field on the frame thread, which keeps the undo history and the caret of the field right. The revision grows only when the UI itself changes the field, such as a click that moves the caret, the length limit cutting the text, or an app that sets a new value. An edit made against an older revision answers a text the field no longer shows, so the UI drops it and the platform receives the new text instead. While the input method composes, the UI publishes nothing, so the composition is never interrupted, and it underlines the composing text in the field.

Return, tab and escape of the native field arrive as actions. Submit reports `submit` and lets the field go, next moves the focus to the next field like tab, cancel brings back the text the field had when it took the focus and lets it go, and a keyboard the user closed lets the field go and keeps its text. A return key labelled next moves on like tab. While a platform edits the field natively, the UI ignores the character events and the editing keys that reach it for that field, so nothing types twice.

The platform also reports the frame of the on-screen keyboard. When the keyboard would cover the focused field, every mounted document moves up together until the field shows above it with a small margin, never past the top of the screen, and moves back when the keyboard closes. The engine publishes `keyboard_shown`, with the frame in design units, and `keyboard_hidden` on the [event bus](lua-api/events.md).

`window.showKeyboard(true)` of [haylen.window](lua-api/window.md) opens the same native field without a text field of the UI, for apps that read typing themselves. The runtime turns its edits into the `character` events and `backspace`, `enter`, `tab` and `escape` key events that a physical keyboard would send, and text inside an open composition types once the input method commits it. ImGui text inputs of [haylen.imgui](lua-api/imgui.md) use this plain keyboard too.

## Web

The web runtime, `engine/platform/web/haylen-runtime.js`, edits through the browser's own fields. A hidden `<textarea>` edits text, text areas and every keyboard except passwords, which a hidden `<input type="password">` edits. Both are siblings of the canvas, positioned over the field (framebuffer pixels scaled to the canvas box on the page), with opacity 0, a transparent caret and a font of 16 pixels, which keeps Safari on iOS from zooming into the page. The element gets `inputmode`, `enterkeyhint`, `autocapitalize`, `autocorrect`, `spellcheck` and `maxlength` from the options of the field.

The element reports its text on `input`, its composition on `compositionstart`, `compositionupdate` and `compositionend`, and its selection on `selectionchange`. Enter of a single line, Tab and Escape become the submit, next and cancel actions. The element stops the propagation of its key events, so the listeners of `sokol_app` on the window never apply a key twice, and paste, copy, cut and undo stay native. A `blur` while the page keeps the focus means the user left the field or closed the keyboard, which sends the dismissed action, and `resize` and `scroll` of the `visualViewport` report the part of the canvas the keyboard covers.

Safari on iOS opens the keyboard only when an element takes the focus inside a user gesture, while the engine learns about a tap only on its next frame. The engine therefore publishes the rectangles and options of every text field on screen, and the page focuses the right element synchronously in `pointerup` when a tap lands on one. Desktop browsers take the same path, which gives them input methods as well. The plain keyboard leaves key events to `sokol_app` and takes only the text, and a page on iOS opens it only from such a tap, so a text field of the UI is the reliable way to type there.

The runtime also follows the page. A hidden tab (`visibilitychange`) sends the app to the background and a visible one brings it back, and `pagehide` makes the user data durable once more. Browsers keep audio suspended until the user interacts, and Safari on iOS suspends it again after interruptions, so every `pointerdown`, `touchend` and `keydown` resumes the audio contexts of miniaudio that the app keeps playing, unless the app is in the background or the page paused it. `online` and `offline` report the network, and the Screen Orientation API reads and locks the orientation where the browser allows it, which usually means a fullscreen page on a phone.

## Android

`HaylenActivity` adds a hidden `HaylenEditText` to the activity with `addContentView`, with alpha 0, and the engine places it over the focused field in window pixels. Its `inputType` follows the keyboard, capitalization and autocorrection of the field, and its `imeOptions` carry the action of the return key with `IME_FLAG_NO_EXTRACT_UI` and `IME_FLAG_NO_FULLSCREEN`, so the input method never covers the app with its own editor. Every call from the engine runs on the UI thread through `runOnUiThread`. After `afterTextChanged` and `onSelectionChanged`, once the input method finishes its batch of changes, the field sends its text, selection and composing span through JNI, and `onEditorAction` sends the submit action.

Touches and gamepads never reach the field: the native activity takes them first, so the engine keeps them. Keys of a hardware keyboard type into the field while it has the focus, where tab, escape and return become actions. The activity uses `adjustNothing`, so the keyboard lies over the app without resizing it, and its insets listener reports the IME insets as the keyboard frame. A keyboard that closes while a field is edited, such as with the back button, sends the dismissed action, and back never leaves the app while a field is edited. The keyboard opens only when a field starts editing, so a field that moves or changes never brings back a keyboard the user closed. Android 11 and later report the IME insets of an edge-to-edge window. Android 8.1 to 10 may not report them with `adjustNothing`, and there the UI does not move above the keyboard.

The activity also holds the audio focus in the foreground and abandons it in the background. Another app that takes it, for a phone call or an alarm, interrupts the app: the engine makes it inactive and the audio plugin pauses every voice until the focus comes back. A loss that lets the app play quieter needs nothing, since the system lowers the volume itself. `HaylenNetwork` follows the default network with a `ConnectivityManager` callback, and `window.lockOrientation` calls `setRequestedOrientation`.

## iOS, iPadOS, tvOS and Mac Catalyst

The runtime adds a hidden `UITextField` for single lines and a hidden `UITextView` for text areas to the root view, over the field in points, with alpha 0, so touches still reach the view of the app. They get `keyboardType`, `returnKeyType`, `secureTextEntry`, `autocorrectionType` and `autocapitalizationType` from the field, without smart quotes and dashes. The editing changed event and `textFieldDidChangeSelection`, or their text view equivalents, send the text, the selection and the `markedTextRange` of the input method, converted from UTF-16 offsets to code points. Return sends the submit action, tab and escape of a hardware keyboard send next and cancel, and a field that stops editing on its own sends the dismissed action. `UIKeyboardWillChangeFrameNotification` reports the keyboard frame. `sokol_app` no longer shows its own keyboard.

On tvOS the text field presents the fullscreen keyboard of the system, and a text area edits in a text field too. Mac Catalyst uses the same path as iOS with the keyboard of the Mac. On iPhone and iPad, `window.lockOrientation` asks UIKit for the new orientations through the application delegate and turns the screen with `requestGeometryUpdate`. `NWPathMonitor` reports the network on every Apple platform.

## macOS

While a field is edited, an invisible `NSTextView` over it is the first responder of the window. It brings marked text, dead keys, the emoji picker and dictation. `insertNewline:` submits a single line, `insertTab:` moves on and `cancelOperation:` cancels. Clicks pass through it to the view of the app, which places the caret itself, and when editing ends the view of the app becomes the first responder again. Password fields accept only Roman input sources, like secure text fields.

## Windows and Linux

Windows types through `WM_CHAR`, which `sokol_app` turns into character events, and the input method composes in its own window. The text input places the composition window at the caret of the focused field with `ImmSetCompositionWindow` and the candidate list below the caret line with `ImmSetCandidateWindow`, so it never covers the text being typed. Linux types through the key and character events of X11. Neither has a native field, so the UI edits the text itself. While a field edits, the keys it types never reach the navigation actions, so Space types a space and Enter starts a new line in a text area, while Enter submits a single line, Escape cancels and the gamepad buttons of `ui_accept` and `ui_cancel` end the editing.

## Complex scripts and right-to-left text

The UI draws the text of a field with the shaped layout of the engine, so a field shows joined Arabic letters, Indic conjuncts, the marks of every script and the bidirectional order of mixed text like a label does, and a password shows one bullet per character. ImGui still keeps the text, the undo history and the editing keys, but its own glyphs know no shaping or direction, so the field places the caret again by the shaped text. The caret stops only between characters, never inside a letter with its marks, a conjunct or a ligature. It stands on the side of the character it follows, the right of a right-to-left letter, and a selection across a change of direction covers every run it spans, which may be apart on screen.

A press puts the caret at the character under the pointer, a double press selects the word there, and a drag selects up to the pointer, on every platform. Where the UI edits the text itself, on Windows and Linux, the left and right arrow keys move the caret one character the way they point on screen, and the up and down arrow keys of a text area move it to the nearest character of the line above or below. Where a native field edits, the native field moves the caret with the keys by the rules of the platform, and the UI draws the caret the field reports.

A field lines its text up with the side where the direction of the UI starts, the right of a right-to-left interface, and each paragraph of the text reads in the direction of its first strong letter. A text longer than the field scrolls toward the side it grows to.

Some limits remain. Word jumps with a modifier key on Windows and Linux follow the reading order of the text rather than the order on screen, and Home and End go to the start and the end of the line in reading order. Backspace deletes one code point, which removes the last mark of a letter before the letter itself. A caret at the boundary between a left-to-right and a right-to-left run stands on one of the two places the position has on screen, the side of the character it follows. Text areas break lines only at line breaks the text holds and scroll sideways, like a single line does.

## From C++

`haylen::platform::TextInput` (`haylen/platform/TextInput.hpp`) is the protocol, and `Window::getTextInput()` returns the text input of the platform. `edit(field)` starts or follows the editing of a `TextInput::Field`, `finish()` ends it and `setVisibleFields(fields)` lists the fields on screen. A native platform answers with `TextEdited` events that carry a `TextInput::Edit`, `TextAction` events with a `TextInput::Action`, and `KeyboardChanged` events with the keyboard frame, which the engine delivers to the UI on the frame thread. A text input that keeps the defaults of the class, as on Linux, leaves the typing to key and character events. `ui::Backend::getKeyboardOffset()` returns how far the UI moves up above the keyboard.
